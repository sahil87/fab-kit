# _cli-fab

## Summary

Fab CLI command reference — the exhaustive companion to the **Common fab Commands** headline table in `_preamble.md`. The preamble documents the 6 most-used command families (`preflight`, `score`, `log command`, `change`, `resolve`, `status`); this partial documents everything else plus the full flag/argument surface, the calling convention, the extended `fab score` formula and `.status.yaml` schema details, and the common error messages. It is a **reference catalog**, not a procedure: skills look up command signatures here rather than running a defined flow.

This is an internal partial (`user-invocable: false`, `disable-model-invocation: true`, `metadata: internal: true`) — never invoked directly. It is loaded selectively via a skill's `helpers: [_cli-fab]` frontmatter (per `_preamble.md` § Skill Helper Declaration); `/fab-operator` is its primary consumer (`helpers: [_cli-agents, _cli-fab, _cli-external]`). Canonical source is the flat `src/kit/skills/_cli-fab.md`; `fab sync` deploys it to `.claude/skills/_cli-fab/SKILL.md`.

> **No prior SPEC mirror existed** (260620): the two CLI-partial mirrors (`SPEC-_cli-fab.md`, `SPEC-_cli-external.md`) were missing while every other `src/kit/skills/*.md` had a `docs/specs/skills/SPEC-*.md` twin. This file backfills the gap so the constitution's SPEC-mirror rule (every skill/partial edit pairs with its mirror) holds across the whole `src/kit/skills/` tree.

| Calling Convention | How fab commands are invoked (paths relative to repo root), exit-code/stderr contract, the best-effort vs. fail-fast distinction. Documents the **`fab-go` exit-code convention** (toolkit principle №4, 260717-swon): `0` success / `1` operational failure / `2` **usage error** (unknown/malformed flag, arg-count violation, unknown subcommand, mutually-exclusive flags-group conflict). Classification **rides on execution phase, not message strings** — `main()`'s testable `run()` helper wraps every `RunE` so a shared flag records whether the resolved command's run phase began; every usage class surfaces during cobra's `execute()` before any `RunE` runs (flag parse, `ValidateArgs`, unknown-subcommand `Find`/`legacyArgs`, `ValidateFlagGroups`) → exit `2`, while an operational error originates inside a `RunE` → exit `1` (same error-value discipline as `paneValidationExitCode`). **Coexistence (no renumbering)**: the pane family (`2`/`3`) and `memory-index --check` (`0`/`1`/`2`) set non-1 codes via in-handler `os.Exit`, which bypasses this mapping — their codes are unchanged and per-subcommand exit `2` is intentionally ambiguous between "usage error" (parse-time) and the domain meaning (in-handler), documented rather than renumbered. `--provider` re-derives `dispatch=` from the NAMED provider — so the emitted `dispatch=` presence can differ from the stage's unoverridden one, documented as a **query result, not an adapter move**: `fab dispatch start` takes no override flags and re-resolves the stage from config, so an override-only `dispatch=` line is NOT actionable and relocating a stage between the native and CLI adapters needs a **config/tier** override (`agent.tiers.<tier>.provider` + a `providers:` entry). The two remedies are documented as NOT interchangeable: dispatching the stage natively with the overridden model/effort works only for a **within-claude** `--model`/`--effort` override (the native seam is the Agent tool's `model` param, a Claude-alias enum), so for a cross-provider `--provider` override the config/tier override is the **sole executable path**. A `--provider` swap also does not retain the old provider's model/effort (they refill from the new provider's fill, then empty — the same **cross-provider fill** rule tier resolution applies to a tier that explicitly sets `provider:`). That cutoff is documented as **provider-NAME-based, not vendor-based** — fab compares two names and knows nothing about the vendor behind either, so a differently-named entry fronting the same vendor also loses the tier's model/effort inheritance — and the doc calls out the **swap-back-to-claude** case: `--provider claude` from a non-claude tier lands on an **empty** `model=` (claude's fill lives on the built-in *tiers*, not on the provider, so there is no `providers.claude.model` rung to refill from), so that swap needs an explicit `--model`, while `--provider claude` against an already-claude tier is not a swap and refills nothing. `--model`/`--effort` are valid WITHOUT `--provider` here (a within-tier override), the documented asymmetry with `fab agent`. All three flags key on whether the flag was **SUPPLIED** (cobra's `Flag.Changed`), not on value emptiness — so `--model=` explicitly **clears** the model (emitting the inherit signal) rather than being ignored, and `--provider=` is a supplied-but-unresolvable name, not an absent flag. | fab dispatch | Process manager for CLI-dispatched pipeline stages (`start`/`restart`/`status`/`wait`/`logs`/`kill`/`clean`) in **two modes** — the two non-native dispatch adapters. Neither mode is an unconditional default: `start` resolves the mode per invocation via an **explicit-first ladder ending in auto** (260805-l9ng) — `--pane` ⇒ pane, `--headless` ⇒ headless, `--timeout` ⇒ headless, `--server` ⇒ pane (each keyed on whether the flag was *supplied*), else **auto**: `$TMUX` non-empty ⇒ pane, unset (or empty) ⇒ headless; the ladder is the pure, table-tested `dispatch.SelectMode` in `internal/dispatch`, `--pane`+`--headless` is a cobra-flag-group **usage error** (exit 2, pre-`RunE`, nothing persisted) while `--headless`+`--timeout` composes, an auto-selected pane targets the **current** server (no `-L` unless `--server` given), and the `dispatched …` line appends the selection source (`auto: tmux` / `auto: no tmux` / `auto: tmux unreachable` / `auto: no session_command`) when auto fired while an explicitly-selected mode's line stays byte-identical. **Headless** (tmux-independent): `start` launches the resolved tier's provider `dispatch_command` detached via `sh -c` with `setsid` semantics, `status` reports all five byte-stable states (`running`/`done`/`failed`/`failed (no-result)`/`orphaned`) from `{stage}.exit` + pid liveness + result presence, `kill` SIGTERMs the process group, `--timeout` is enforced in-wrapper; POSIX-only v1. **Pane** (`--pane`, 260805-zxe0): runs the worker interactively in a tmux pane composing the provider's **`session_command`** (no new config field; **no cross-fallback in either direction**), delivering a **prompt file + one-line pointer** embedded at spawn as a single **shell-quoted** argument (the resolved command itself stays verbatim), requiring a reachable tmux server — probed by a real tmux query (the *validation* step, distinct from `$TMUX`, which is only the *defaulting* signal) so `--server`/`-L` works from outside tmux — with **two prerequisites** (a reachable server **and** a `session_command`) whose failure is **asymmetric by selection source** (260805-l9ng): under an **explicitly** selected pane (`--pane`, or `--server` as the pane signal) either missing prerequisite keeps the **hard error** (nothing launched, nothing persisted — the reachability message, or the `providers.<name>.session_command` hint), while under **auto** either **soft-falls-back to headless** with a one-line stderr notice per shape — `pane auto-selection: tmux unreachable, falling back to headless` (shape (a), reason `auto: tmux unreachable`) or `pane auto-selection: provider has no session_command, falling back to headless` (shape (b), reason `auto: no session_command`) — re-composing from `dispatch_command` (so the no-cross-fallback rule survives; a provider with **neither** field still errors) and producing a headless-shaped record. Pane-command composition is **deferred until the mode is validated** so shape (b) is reachable: a stale `$TMUX` must never break an unattended dispatch, and a `dispatch_command`-only provider must dispatch identically inside and outside tmux. **WHERE the pane opens is a second, independent decision (260806-mnri)** — the pure, table-tested `dispatch.SelectPaneShape` (`$TMUX_PANE` + whether `--server` was supplied; both env reads stay in the cobra layer, per the `SelectMode` precedent): `$TMUX_PANE` set **and** no `--server` ⇒ **split** the dispatching agent's own window (`tmux split-window` + `select-pane -T fab-{id}-{stage}`), stacked in a **right-hand column** — `-v` off the **last** `fab-`-titled sibling pane in that window, else `-h` off `$TMUX_PANE`, with a failing sibling probe degrading to the `-h` split plus a stderr warning rather than failing the dispatch; otherwise ⇒ the **`fab-{id}-{stage}` new window** (`tmux new-window -n`), which survives as the **fallback** for a dispatcher with no pane of its own to split (a headless orchestrator passing `--pane`) and for `--server <name>`, whose socket may not be the one the caller's pane id lives on. This is the **two-tier tmux hierarchy**: operator→worktree agents stay **windows**, agent→stage workers become **panes**, so a worker no longer costs a window in the operator's tab bar. The `fab-{id}-{stage}` identity string is **unchanged and shape-independent** — carried by the pane **title** when split and the window **name** otherwise, recorded in the record's same `window` field (no schema change, no migration), and carrying **no operator `»`/`›` marker in either shape**. A failed title set is **non-fatal** (stderr warning; the pane ID is the real identity). Everything downstream is **pane-ID keyed and therefore shape-blind**: `PaneAlive`/`status`, `kill` (killing a split worker's pane leaves the agent's window and any sibling worker intact), `fab pane capture`, refuse-if-running, and `DerivePaneState` are all unchanged. The `dispatched …` line reports the shape (`pane %N, split, title fab-…` vs. the byte-unchanged `pane %N, window fab-…`), and `restart` inherits the whole decision from the shared launch tail. Pane mode is also **mutually exclusive with `--timeout`** (only the explicit `--pane` conflicts — a bare `--timeout` is itself a headless rung of the ladder); `status` derives a **subset of three** (`done` on result presence — which **wins over** pane liveness — else `running`/`orphaned` by pane liveness; the two exit-code-derived states are unreachable), `kill` kills the tmux pane idempotently (post-kill ⇒ `orphaned`), `logs` reports the no-log fact naming `fab pane capture <pane>` — carrying the recorded socket as `-L <server>` when the record has one, since a socket-scoped pane is unreachable from a default-socket capture (making that report the copy-pasteable source; `status --json` exposes `pane` but not `server`). Both modes share `.fab-dispatch/{id}/`, refuse-if-running + last-attempt-only (the prior record's own mode's **finished signal** applied — `{stage}.exit`+pid headless, `{stage}-result.yaml`+pane liveness pane, so `start` and `status` never disagree about a finished-but-still-alive pane worker), and a record whose **mode is derived** from which identity keys are present (`pid`/`pgid` vs `pane`/`window`/`server`, each `omitempty` — a headless record's shape is unchanged); `status --json` gains a `mode` discriminator with the other mode's keys omitted. Cleanup is archive-time deletion + `fab dispatch clean` only (no auto-GC), and `clean` is **mode-blind**. `start`'s tier→provider re-resolution reads **CONFIG ONLY** — it carries no `--provider`/`--model`/`--effort` surface, so `fab resolve-agent`'s invocation-time overrides never reach either mode (they bind the native Agent-tool arm; an adapter move requires a config/tier override — 260805-j3cm). **`restart` (260806-mnri)** relaunches a **non-running** dispatch from the prompt `start` persisted at `{stage}-prompt.md` — the family's recovery verb, added because the orchestrator that needs to relaunch may have lost the block prompt to compaction. It is `start` with **exactly one difference** (the prompt's source), sharing one Go launch path (`runDispatchLaunch` + a `promptSource` seam — `promptFromStdin` vs `promptFromStateDir`), hence the same prologue (resolution → pane validation → **refuse-if-running** → stale exit/result/log clearing), the same flag set and exclusions, and the same output/record byte-shape (the `auto: …` suffix rules included). The launch **mode — and the pane shape — are re-derived from the CURRENT environment, never inherited** from the prior attempt (there is no stored discriminator to inherit from), which is the point: a pane dispatch orphaned *by* a dead tmux server relaunches headless instead of re-failing, and a restart issued from inside a tmux pane splits that pane's window even when the prior attempt opened a window. A restart **is** a fresh attempt under last-attempt-only, so it adds **no state string, no attempt counter, no history, and no `restarted:` marker** — `status` cannot tell it from a `start`. The prompt file is the **input**, read and left byte-identical (re-writing it with its own bytes would only risk corruption on a partial write) while the *prior attempt's* exit/result/log are still cleared; refuse-if-running **precedes** the prompt read (a live dispatch gets the actionable kill-first message even with no prompt on disk); and a missing prompt is a clear `nothing to relaunch; run \`fab dispatch start\` with the prompt on stdin` error that launches nothing and leaves any prior record intact. The observation policy that *spends* a restart is skill-side (`_preamble.md` § CLI-Adapter Dispatch → *Recovery policy*), not a CLI concern. **`wait` (260806-mkfj)** is `status`'s **blocking** sibling and the family's seventh subcommand — `fab dispatch wait <change> <stage> [--timeout <secs>] [--json]` — added so an orchestrator on the CLI path can be **woken by a state change** instead of burning an inference turn every 30s asking whether one happened (the skill wiring runs it as a **background** command, the harness's notify-on-exit seam, with a foreground blocking fallback). It blocks while the state is `running`, re-deriving it on an internal **~2s tick** through the **same loader and the same per-mode derivation `status` uses** (`DeriveState`/`DerivePaneState`, selected by the record's derived mode), so `wait` and `status` **cannot disagree** by construction; the tick is a package constant (`dispatch.TickInterval`) with no flag and no config field, and is deliberately **not fsnotify** — a watcher can see a result file appear but cannot see the pid/pane death that produces `orphaned`, so a periodic liveness probe is required regardless. **`--timeout <secs>` bounds the block and expiry is NOT an error**: it prints the still-current state (necessarily `running`) and exits **0**, making the **state string the sole discriminator** (a distinct exit code would add a second channel for the same fact, and `124` in this family already means the *worker* was killed by `start`'s wrapper); absent or `0` ⇒ wait indefinitely. An **already-terminal** dispatch returns immediately at zero tick cost, so the verb is idempotent and safe to re-arm after a `restart`. Non-zero exit is reserved for real errors — no dispatch record, unresolvable change — with the **same message surface as `status`**, and `--json` emits the **same object through the same render path**. Purely additive: `status`/`start`/`restart`/`kill`/`clean` are untouched, no new state string, no record-schema change, no migration; `wait` writes nothing and signals nothing (`wait --timeout` bounds the *observer*, `start --timeout` the *worker*).
