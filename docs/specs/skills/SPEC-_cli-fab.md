# _cli-fab

## Summary

**Source organization:** `_cli-fab` is the present command catalog; removed command families and release archaeology are not operational sections.

**Prose packaging (260808-s2sz):** command behavior is unchanged, but dense contracts now expose their dimensions structurally: `pane map --json` uses a field table; dispatch retains its shape/mode ladders and condenses pane/restart prose; PR Impact uses a five-row taxonomy; memory-index uses one severity table plus one three-tier exit table; batch uses a subcommand/flags/guards table; config provenance points to `docs/specs/config.md`.

Fab CLI command reference — the exhaustive companion to the **Common fab Commands** headline table in `_preamble.md`. The preamble documents the 6 most-used command families (`preflight`, `score`, `log command`, `change`, `resolve`, `status`); this partial documents everything else plus the full flag/argument surface, the calling convention, the extended `fab score` formula and `.status.yaml` schema details, and the common error messages. It is a **reference catalog**, not a procedure: skills look up command signatures here rather than running a defined flow.

This is an internal partial (`user-invocable: false`, `disable-model-invocation: true`, `metadata: internal: true`) — never invoked directly. It is loaded selectively via a skill's `helpers: [_cli-fab]` frontmatter (per `_preamble.md` § Skill Helper Declaration); `/fab-operator` is its primary consumer (`helpers: [_cli-agents, _cli-fab, _cli-external]`). Canonical source is the flat `src/kit/skills/_cli-fab.md`; `fab sync` deploys it to `.claude/skills/_cli-fab/SKILL.md`.

The built-in command policy exposed by this reference is deliberately full-auto for unattended workers: codex carries `--dangerously-bypass-approvals-and-sandbox` on both its session and dispatch forms, and agy `--dangerously-skip-permissions` on its interactive and headless forms, while kimi carries **no approval flag on its dispatch form at all** (`kimi -p` already auto-approves tools and errors when combined with `--yolo`/`--auto`) and carries `--auto` on its interactive form instead. All four built-ins (`claude`, `codex`, `agy`, `kimi`) ship an `interactive_command` and are fully pane-eligible. Their first-run behavior (like agy's and kimi's workspace trust prompts) is cleared by an ordinary readiness-gate judgment round (remembered per folder) and their input boxes verify under the box-drawing-tolerant echo check. Profile token-drop removes only empty model/effort tokens and their flags; fixed bypass flags remain, so a provider-addressed launch with no model is model-free rather than necessarily a bare binary invocation.

> **No prior SPEC mirror existed** (260620): the two CLI-partial mirrors (`SPEC-_cli-fab.md`, `SPEC-_cli-external.md`) were missing while every other `src/kit/skills/*.md` had a `docs/specs/skills/SPEC-*.md` twin. This file backfills the gap so the constitution's SPEC-mirror rule (every skill/partial edit pairs with its mirror) holds across the whole `src/kit/skills/` tree.

| fab dispatch | Process manager for CLI-dispatched pipeline stages (`start`/`open`/`ready`/`deliver`/`restart`/`status`/`wait`/`logs`/`kill`/`reap`/`clean`) in **two modes** — the two non-native dispatch adapters. The two modes have **separate entry verbs**, because they hand a worker its prompt in fundamentally different ways: `start` launches headless with the prompt on stdin, while pane mode takes `open` → `ready` → `deliver`. Neither mode is an unconditional default: a launch verb resolves its invocation through the pure, table-tested `dispatch.SelectMode` ladder in `internal/dispatch` except where the verb itself IS the selection (`open` forces pane; `start` launches only headless). Explicit signals retain precedence and hard semantics wherever they are still accepted — `--headless` ⇒ headless, `--timeout` ⇒ headless, and on `restart` `--pane` ⇒ pane and `--server` ⇒ pane (each keyed on whether the flag was *supplied*) — then automatic selection starts at the configured `dispatch.mode` preference and descends only through `pane → native → headless`. Pane requires reachable tmux plus `interactive_command`; native requires `native: true`; headless requires `headless_command`. Missing automatic prerequisites skip rungs, never ascend, and never substitute one capability field for another; a no-rung result errors actionably. Because this command manages only the two non-native adapters, an automatic native result also errors before persistence with `fab resolve-agent` re-resolution guidance. `--pane`+`--headless` — registered together only on `restart`, the one launch verb that still takes both — is a cobra-flag-group **usage error** (exit 2, pre-`RunE`, nothing persisted), `--headless`+`--timeout` composes, and an automatically selected pane targets the **current** server (no `-L` unless `--server` was supplied). Automatic success appends `mode: <rung> (preferred)` or `mode: <rung> (descended: <reason>[; <reason>])` to the launch line — `dispatched …` headless, `opened …` pane; the exact reason vocabulary is `pane unavailable: no tmux`, `pane unavailable: tmux unreachable`, `pane unavailable: no interactive_command`, and `native unavailable`, while an explicitly selected mode's line stays byte-identical. **Headless** (tmux-independent): `start` launches the resolved provider's `headless_command` detached via `sh -c` with `setsid` semantics, `status` reports all five byte-stable states (`running`/`done`/`failed`/`failed (no-result)`/`orphaned`) from `{stage}.exit` + pid liveness + result presence, `kill` SIGTERMs the process group, `--timeout` is enforced in-wrapper; POSIX-only v1. **Pane** (entered at `open`; 260805-zxe0, re-entered by 260809-3oz7): runs the worker interactively in a tmux pane by composing the provider's **`interactive_command`** and nothing else — the resolved command reaches tmux **verbatim**, with no prompt argument appended to it. The prompt is persisted to `{stage}-prompt.md` and handed over **post-spawn**, as a typed one-line pointer verified by `deliver` behind the readiness gate. A real tmux query validates reachability — distinct from `$TMUX`, which is only the resolver-side availability signal — so `--server`/`-L` works from outside tmux. Explicit pane selection (`open`, whose verb is the selection, or `--pane`/`--server` on `restart`) preserves hard prerequisite errors for unreachable tmux or missing `interactive_command`, with nothing launched or persisted. Automatic pane selection already requires tmux plus `interactive_command`; if the launch-time probe finds stale tmux, selection reruns with `tmux unreachable` and descends through native then headless, emitting `dispatch selection: <mode reason>` on stderr. Landing on native returns the re-resolution error; landing on headless composes `headless_command`. Pane composition is deferred until validation so every rung composes only its own capability and the same descent ladder governs resolver and launcher. **WHERE the pane opens is a second, independent decision (260806-mnri)** — the pure, table-tested `dispatch.SelectPaneShape` (`$TMUX_PANE` + whether `--server` was supplied; both env reads stay in the cobra layer, per the `SelectMode` precedent): `$TMUX_PANE` set **and** no `--server` ⇒ **split** the dispatching agent's own window (`tmux split-window` + `select-pane -T fab-{id}-{stage}`), stacked in a **right-hand column** — `-v` (unsized) off the **last live sibling worker pane** in that window, else `-h -l <n>%` off `$TMUX_PANE`, **CARVING** the column at `dispatch.column_width` (default 35, so the dispatching agent keeps the rest — 260807-g4a5). Sibling detection is keyed on the **dispatch records' pane IDs** (the `pane:` field of every `.fab-dispatch/*/{stage}.yaml` in the checkout **whose `server:` matches the probed socket** — pane ids are per-server, so an unfiltered set would let a `--server` record's `%N` false-match the same `%N` on the default socket, whose records carry `server: ""` — intersected with the window's live `list-panes` output), **not** pane titles: a pane id is server-global and stable for the pane's lifetime, whereas the harness running inside a worker rewrites its pane title within seconds, so the former title-keyed probe found nothing and every later worker re-split the dispatcher into another full-height column. The intersection *is* the liveness + same-window filter, and "last" stays `list-panes` (pane-index) order. This is the **column invariant**: the vertical left/right separator is created once by the carving split and never re-touched — no `select-layout`, no rearranging user-made panes, no fighting a manual resize — a creation-time rule, not a repair pass (an already-mangled window is left alone until its panes die). **Placement stays cosmetic and degrades warn-only**, with the warning naming both the failure and the placement it resolved to so a degraded probe is never silent: a failing `list-panes` leaves no window to intersect and falls back to the same *sized* `-h` carve off `$TMUX_PANE` (sizing the fallback too, since a fallback column that halved the dispatcher would reintroduce the squeeze), an unreadable dispatch dir or corrupt `{stage}.yaml` warns identically but **keeps the records that did read** (an unread record can only fail to *find* a sibling, never invent one, so a partial failure still stacks when a live sibling is among the readable ones) while an **absent** `.fab-dispatch/` tree is the ordinary first-dispatch case and warns not at all, and a tmux that rejects `-l <n>%` (every tmux before 3.1, or a window too narrow for the percentage) retries the split **unsized** with a stderr warning naming both causes; otherwise ⇒ the **`fab-{id}-{stage}` new window** (`tmux new-window -n`), which survives as the **fallback** for a dispatcher with no pane of its own to split (a headless orchestrator running `open`) and for `--server <name>`, whose socket may not be the one the caller's pane id lives on. This is the **two-tier tmux hierarchy**: operator→worktree agents stay **windows**, agent→stage workers become **panes**, so a worker no longer costs a window in the operator's tab bar. The `fab-{id}-{stage}` identity string is **unchanged and shape-independent** — carried by the pane **title** when split and the window **name** otherwise, recorded in the record's same `window` field (no schema change, no migration), and carrying **no operator `»`/`›` marker in either shape**. Titles are set at spawn for **identification only** — placement no longer reads them — so a failed title set is **non-fatal** (stderr warning; the pane ID is the real identity). Everything downstream is **pane-ID keyed and therefore shape-blind**: `PaneAlive`/`status`, `kill` (killing a split worker's pane leaves the agent's window and any sibling worker intact), `fab pane capture`, refuse-if-running, and `DerivePaneState` are all unchanged. The `opened …` line reports the shape (`pane %N, split, title fab-…` vs. the byte-unchanged `pane %N, window fab-…`), and `restart` inherits the whole decision from the shared launch tail. The **`--pane`/`--timeout` mutual exclusion** survives exactly where `--pane` does, on `restart` (a bare `--timeout` is itself a headless rung of the ladder, so it never errors on its own); `status` derives a **subset of three** (`done` on result presence — which **wins over** pane liveness — else `running`/`orphaned` by pane liveness; the two exit-code-derived states are unreachable), `kill` kills the tmux pane idempotently (post-kill ⇒ `orphaned`), `logs` reports the no-log fact naming `fab pane capture <pane>` — carrying the recorded socket as `-L <server>` when the record has one, since a socket-scoped pane is unreachable from a default-socket capture (making that report the copy-pasteable source; `status --json` exposes `pane` but not `server`). Both modes share `.fab-dispatch/{id}/`, refuse-if-running + last-attempt-only (the prior record's own mode's **finished signal** applied — `{stage}.exit`+pid headless, `{stage}-result.yaml`+pane liveness pane, so `start` and `status` never disagree about a finished-but-still-alive pane worker), and a record whose **mode is derived** from which identity keys are present (`pid`/`pgid` vs `pane`/`window`/`server`, each `omitempty` — a headless record's shape is unchanged); `status --json` gains a `mode` discriminator with the other mode's keys omitted. Cleanup is archive-time deletion + `fab dispatch clean` only (no auto-GC), and `clean` is **mode-blind**. `start`'s role→provider re-resolution reads **CONFIG ONLY** — it carries no `--provider`/`--model`/`--effort` surface, so `fab resolve-agent`'s invocation-time overrides never reach either mode (they bind the native Agent-tool arm; an adapter move requires a config override — `agent.workers`/`agent.session`, or `agent.profiles.<role>.provider` — 260805-j3cm). **`restart` (260806-mnri)** relaunches a **non-running** dispatch from the prompt the entry verb (`start` headless, `open` pane) persisted at `{stage}-prompt.md` — the family's recovery verb, added because the orchestrator that needs to relaunch may have lost the block prompt to compaction. It differs from `start` in **exactly two ways** — the prompt's source, and what a pane landing means (`start` refuses pane outright; `restart` performs the `open` step alone and hands the gate back) — while sharing one Go launch path (`runDispatchLaunch` + a `promptSource` seam — `promptFromStdin` vs `promptFromStateDir`), hence the same prologue (resolution → pane validation → **refuse-if-running** → stale exit/result/log clearing), the full four-flag launch surface with the `--pane`/`--headless` exclusion `start` no longer registers, and the same output/record byte-shape (the `mode: <rung> (preferred|descended: …)` suffix rules included). The launch **mode — and the pane shape — are re-derived from the CURRENT config, capabilities, and environment, never inherited from the prior attempt**. A pane dispatch orphaned by a dead tmux server re-descends: a native landing returns re-resolution guidance, while a non-native provider can continue headless; whenever pane resolves, placement uses the restart caller's current tmux position. A restart **is** a fresh attempt under last-attempt-only, so it adds **no state string, no attempt counter, no history, and no `restarted:` marker** — `status` cannot tell it from a `start`. The prompt file is the **input**, read and left byte-identical (re-writing it with its own bytes would only risk corruption on a partial write) while the *prior attempt's* exit/result/log are still cleared; refuse-if-running **precedes** the prompt read (a live dispatch gets the actionable kill-first message even with no prompt on disk); and a missing prompt is a clear `nothing to relaunch; run \`fab dispatch start\` (headless) or \`fab dispatch open\` (pane) with the prompt on stdin` error that launches nothing and leaves any prior record intact. The observation policy that *spends* a restart is skill-side (`_preamble.md` § CLI-Adapter Dispatch → *Recovery policy*), not a CLI concern. **`wait` (260806-mkfj)** is `status`'s **blocking** sibling and the family's seventh subcommand — `fab dispatch wait <change> <stage> [--timeout <secs>] [--json]` — added so an orchestrator on the CLI path can be **woken by a state change** instead of burning an inference turn every 30s asking whether one happened (the skill wiring runs it as a **background** command, the harness's notify-on-exit seam, with a foreground blocking fallback). It blocks while the state is `running`, re-deriving it on an internal **~2s tick** through the **same loader and the same per-mode derivation `status` uses** (`DeriveState`/`DerivePaneState`, selected by the record's derived mode), so `wait` and `status` **cannot disagree** by construction; the tick is a package constant (`dispatch.TickInterval`) with no flag and no config field, and is deliberately **not fsnotify** — a watcher can see a result file appear but cannot see the pid/pane death that produces `orphaned`, so a periodic liveness probe is required regardless. **`--timeout <secs>` bounds the block and expiry is NOT an error**: it prints the still-current state (necessarily `running`) and exits **0**, making the **state string the sole discriminator** (a distinct exit code would add a second channel for the same fact, and `124` in this family already means the *worker* was killed by `start`'s wrapper); absent or `0` ⇒ wait indefinitely. An **already-terminal** dispatch returns immediately at zero tick cost, so the verb is idempotent and safe to re-arm after a `restart`. Non-zero exit is reserved for real errors — no dispatch record, unresolvable change — with the **same message surface as `status`**, and `--json` emits the **same object through the same render path**. Purely additive: `status`/`start`/`restart`/`kill`/`clean` are untouched, no new state string, no record-schema change, no migration; `wait` writes nothing and signals nothing (`wait --timeout` bounds the *observer*, `start --timeout` the *worker*). **`reap` (260807-zfl7)** is the family's eighth subcommand and its **hygiene** verb — `fab dispatch reap <change> <stage>`, **no flags** (no `--json`; no `--server`, since the socket comes from the record) — added because a pane worker never exits on completion, so across a pipeline the carved worker column fills with finished panes and the panes the user watches shrink with every completed stage. It owns the **whole three-condition guard** — pane-mode record **AND** derived state `done` **AND** `dispatch.reap_done` (bool, **default `true`**, scope `both`) resolving true — which is why the skill-side call in `_preamble.md` § CLI-Adapter Dispatch step 3's `done` bullet is **unconditional and dumb wherever a record exists** (that owner also decides *when* each stage's reap fires, and gates apply's deferred one on the pane arm — a missing record errors rather than no-ops): the knob is read through the four-tier environment/system/project/default cascade, which a skill parsing `fab/project/config.yaml` directly would get wrong (it would miss both the machine-wide system layer, which outranks it, and the environment overlay). Everything else is a **no-op that names its reason and exits 0** — headless record (the process already exited), non-`done` state (the report points at `kill`), knob `false`, or a pane already gone (a benign already-gone report mirroring `kill`'s idempotence, so a re-reap is safe); only a **missing record / unresolvable change** exits non-zero, sharing `status`/`wait`'s message surface — an **unreadable project config is deliberately not in that set**, since the wiring calls reap without inspecting mode or config wherever it calls it at all: the knob is resolved **lazily**, only once the mode and state conditions already hold (so a headless or non-`done` no-op reads no config at all), and where it is read an unparseable file **warns on stderr and fails open to the built-in default**, the same value an absent key resolves to. **`reap` is NOT `kill`**: `kill` is *recovery*, valid in any state and ungated; `reap` is *hygiene*, fires only on `done`, is knob-gated, and can never terminate a running/orphaned/failed dispatch — so the Recovery policy (peek-on-suspicion, the single restart budget, escalation, classification (c) never-kill) is untouched, and the pipeline's verb set grows to peek/kill/restart/notify/stop/**reap**. It is **shape-blind** (pane-ID keyed, so a split worker's death leaves the dispatcher's pane, its window, and any sibling worker intact) and **cleans no state**: record, result, prompt, and log all survive, which is exactly why a reaped dispatch still reads `done` forever (`DerivePaneState` gives result presence precedence over pane liveness) and why the no-auto-GC posture — archive-time deletion + explicit `fab dispatch clean` as the only two cleanup moments — is unchanged. Implementation follows the family's split: the pure, table-tested `dispatch.DecideReap` guard in `internal/dispatch` (mode → state → knob, so the never-kill-a-live-worker rule is config-independent) plus thin cobra wiring in `cmd/fab/dispatch_reap.go`.
