# Glossary

> Quick reference for all terminology used in Fab Kit. Terms are grouped by category and alphabetized within each group.

---

## Core Concepts

| Term | Definition |
|------|-----------|
| **Artifact** | A markdown file generated by a skill at a specific stage — `intake.md` or `plan.md`. Each artifact lives inside a change folder. |
| **Memory files** | The source-of-truth documentation in `docs/memory/`. Organized by domain, updated by `/fab-continue` (hydrate) and `/docs-hydrate-memory` ingestion. Contrast with **plan.md** (change-scoped). |
| **Canonical home** | The location a `/fab-dedupe` cluster's consolidated utility should live in — an existing shared package/module when one fits, otherwise a new one, chosen by reading the repo's own layout conventions from neighboring directories rather than importing a convention from another project. |
| **Change** | A unit of work tracked as a folder under `fab/changes/`. Contains all artifacts from intake through hydrate. Identified by its folder name (e.g., `260115-a7k2-add-oauth`). |
| **Change folder** | The directory `fab/changes/{YYMMDD}-{XXXX}-{slug}/` that holds all artifacts and status for a single change. The primary unit of identity in Fab — not branches. |
| **Cluster** | A group of two or more functions that solve the same problem regardless of name, signature, or implementation, identified by `/fab-dedupe`. Recorded as a **shared core plus opt-in variation layers** (the base every member needs, then each layer with the members requiring it) — never as one flat signature. A cluster of one is not a cluster. |
| **Constitution** | The file `fab/project/constitution.md`. Defines immutable project principles using MUST/SHOULD/MUST NOT keywords. Loaded as context by most skills; violations are flagged during review. |
| **Detector** | An optional third-party duplicate-detection CLI (jscpd, `similarity-ts`, `dupl`, …) configured via `consolidate.detectors` that **seeds** a `/fab-dedupe` sweep. Probed with `command -v` and skipped silently when absent; a non-zero exit is a finding, not an error. Detectors never perform the clustering — the agent does. |
| **Domain** | A topic area in `docs/memory/` (e.g., `auth/`, `payments/`). Each domain has its own `index.md` and one or more memory files. |
| **Hydration** | The process of integrating knowledge into `docs/memory/`. Two modes: (1) **pipeline hydration** — merging change artifacts (`plan.md` `## Requirements`) into memory files via `/fab-continue` (hydrate stage) on change completion, and (2) **source hydration** — ingesting external documentation, generating from codebase analysis, or backfilling `description:` frontmatter into an existing tree via `/docs-hydrate-memory` (ingest, generate, and backfill modes). |
| **Kit** | The Fab engine content — templates, skill definitions, and migrations. Distributed to the system cache at `~/.fab-kit/versions/<version>/kit/` (managed by the `fab` binary); canonical source is `src/kit/` in the fab-kit dev repo. User projects contain only deployed copies — everything outside the kit is project-specific. |
| **Pointer file** | `.fab-status.yaml` — a symlink at repo root pointing to the active change's `fab/changes/{name}/.status.yaml`. Read by all skills to resolve the working context. Removed by `/fab-archive`. |
| **Skill** | A markdown prompt file in `src/kit/skills/` that defines behavior for an AI agent. Skills are the primary interface to Fab — invoked as `/fab-*` commands. |
| **Design specs** | Human-curated, pre-implementation design documents in `docs/specs/`. Capture architectural intent, design rationale, and the "why" behind the system. Not managed by Fab tooling — organized however makes sense for the project. Contrast with **memory files** (post-implementation, AI-maintained via hydration). |
| **plan.md** | A change-level plan file inside a change folder. Carries `## Requirements` (RFC 2119 keywords + GIVEN/WHEN/THEN scenarios, co-generated at apply entry — formerly `spec.md`), `## Tasks`, and `## Acceptance`. Not to be confused with **design specs** (the project-wide design documents in `docs/specs/`). |
| **Stage** | One of the 6 sequential phases a change passes through: intake, apply, review, hydrate, ship, review-pr. Tracked in `.status.yaml` via the `progress` map (the entry marked `active` is the current stage). The former `spec` stage was merged into `apply` in 1.10.0. |
| **Sub-agent** | A second AI agent context spawned by the primary agent to perform an isolated task — most commonly the review stage, which validates against the plan's requirements and constitution with a fresh context. Spawned via subagent dispatch in `_preamble.md`. Has no shared memory with the calling agent. |
| **`dispatch.mode`** | A `pane | native | headless` config preference (default `native`, scope `both`). It is a ceiling, not a command: automatic resolution begins at the named rung and descends only through `pane → native → headless`, using tmux + `interactive_command`, `native: true`, and `headless_command` as the respective prerequisites. Missing prerequisites skip rungs and selection never ascends. `fab resolve-agent` omits `dispatch=` iff native resolves; pane/headless emit their substituted command. |
| **Dispatch descent ladder** | The shared pure selection rule used by `fab resolve-agent` and `fab dispatch start`/`open`/`restart`. Provider fields are independent capabilities whose presence says how, never whether; the configured `dispatch.mode` chooses the starting rung. Explicit `--headless` (and `--pane` on `restart`, the one launch verb that still takes both) remains a hard override; `open` forces pane by being the pane entry verb, and `start` is headless-only. Automatic output uses `mode: <rung> (preferred)` or `mode: <rung> (descended: <reason>[; <reason>])`. |
| **`dispatch.column_width`** | An integer `config.yaml` field (default `35`, scope `both`, so it can be set once machine-wide in `~/.fab-kit/config.yaml`) giving the pane-worker column's width as a percent of the tmux window. The first pane worker of a window **carves** the column out of the dispatching agent's pane (`split-window -h -l <n>%`), so the agent the user is watching keeps the remaining `100 − n`%; later workers **stack** inside that column with unsized `-v` splits, leaving the left/right separator untouched (the **column invariant**). An absent key is indistinguishable from `0`, so it — and any value outside `1..99` — resolves to the default. |
| **`dispatch.reap_done`** | A boolean `config.yaml` field (default `true`, scope `both`, so it can be set once machine-wide in `~/.fab-kit/config.yaml`) governing whether `fab dispatch reap` reclaims a **done** pane worker's tmux pane. A pane worker never exits on completion — it writes `{stage}-result.yaml` and sits at its prompt — so without reaping every finished stage keeps its slice of the worker column for the rest of the run. **Reap is not kill**: it fires only on `done`, is a reported no-op for a headless record, and never touches a running, orphaned, or failed dispatch. It also removes no `.fab-dispatch/` state, so a reaped dispatch still reads `done` forever. Set `false` to keep a done worker's pane and its scrollback. Modeled as a `*bool` in Go (unlike its two siblings) because a default-*true* bool cannot ride the zero value — an absent key must stay distinguishable from an explicit `false`. |
| **Dispatch adapter** | The mechanism that turns "run stage S as a worker" into a launched worker and an observed result. Three exist, selected by the dispatch descent ladder and sharing one protocol, whose obligations bind every *dispatch* prompt (result file + standard context files + terminal `fab status refresh`): **native Agent-tool** (in-harness sub-agent), **headless CLI** (`fab dispatch start` — detached process), and **interactive pane** (tmux worker observed via result-file presence + pane liveness, so only `running`/`done`/`orphaned` are reachable). Resolution of the profile remains adapter-independent; mode/capability resolution chooses the adapter. See [harness-adapters](harness-adapters.md). |
| **Worker continuation** | Reusing the **apply** worker across auto-rework cycles instead of dispatching a fresh one. Two adapters carry it, with the same shape and different handles: the **native** arm names its worker `apply-{id}` (4-char change ID) and resumes it through the harness's own send, and the **pane** arm delivers a continuation prompt into the still-live pane with `fab dispatch deliver <change> apply --prompt-file …`. Either way the continuation carries the triaged findings and the chosen rework action, and instructs the worker to RE-READ from disk every artifact the orchestrator edited at that item — always plan.md — because its in-context copy predates those edits. A continued worker keeps its first-dispatch `{model, effort}` (no re-resolution) and stays bound by the block contract, but is not re-sent the standard context files it already holds. Any failure to reach the worker falls back to an ordinary fresh dispatch, so continuation is an optimization and never a correctness dependency. Review workers are never continued, and the headless adapter is deliberately non-resumable. Mechanics: `_preamble.md` § Worker Continuation; see [harness-adapters](harness-adapters.md). |

## Stages

| Term | Definition |
|------|-----------|
| **Intake** | Stage 1. Captures intent, scope, and approach for a change. Output: `intake.md`. Created by `/fab-new`. |
| **Apply** | Stage 2. Two sub-steps in a single skill invocation: (1) entry — co-generate `plan.md` (`## Requirements` from `intake.md` + `## Tasks` + `## Acceptance`) via the Plan Generation Procedure; (2) main — execute the unchecked tasks under `## Tasks`, run tests after each, mark `[x]` on completion. Resumable via `plan.md`'s checkbox state. |
| **Review** | Stage 3. Validates implementation against the plan's `## Requirements` and `## Acceptance` items, runs tests, applies code-quality checks. Can loop back to earlier stages on failure. |
| **Hydrate** | Stage 4. Validates review passed and hydrates change artifacts into memory files. The change folder remains in `fab/changes/` — archiving is a separate step via `/fab-archive`. |
| **Ship** | Stage 5. Commits all local changes, pushes to the remote branch, and creates a GitHub PR in draft state. Handled by `/git-pr`. Idempotent — skips steps already done. |
| **Review-PR** | Stage 6. Fetches PR review comments (from humans or automated reviewers — Copilot, Codex, or Claude), triages each as fix/defer/skip, applies fixes, and posts replies. Handled by `/git-pr-review`. |

## Skills

| Term | Definition |
|------|-----------|
| `/fab-setup` | Bootstraps the `fab/` structure in a project. Generates `config.yaml`, `constitution.md`, `memory/`, and skill deployments (via `fab sync`). Provides subcommands for config, constitution, and migrations. Idempotent. |
| `/docs-hydrate-memory` | Ingests external documentation (Notion, Linear, local files) into `docs/memory/` with domain mapping. Three modes: ingest from sources, generate from codebase analysis, or backfill `description:` frontmatter into an existing tree (e.g. a pre-fab-kit memory tree adopting the convention). |
| `/fab-new` | Starts a new change from a description. Creates the change folder, `.status.yaml`, and `intake.md`. Adaptive SRAD-driven questioning with gap analysis and conversational mode. |
| `/fab-continue` | Advances to the next stage, or resets to a given stage and regenerates from there. The step-by-step progression skill. |
| `/fab-ff` | Fast-forward — confidence-gated pipeline from intake through hydrate. Single intake gate, no clarify steps inside the bracket (`/fab-clarify` is the user-invoked escape valve before the gate); sub-agent review with autonomous rework and bounded retry. Resumable. |
| `/fab-fff` | Fast-forward-further — confidence-gated pipeline from intake through review-pr (extends ff through ship and PR review). Same gates and behavior as ff, wider scope. Resumable. |
| `/fab-dedupe` | Sweeps a scoped area for duplicated utilities, clusters them by behavioral shape (shared core + variation layers), and drafts one intake per accepted cluster group. Read-only until you accept; it never refactors — the pipeline does. Stops at intake `ready` like `/fab-draft`, but fans out to 0..N changes. |
| `/fab-clarify` | Deepens and refines the **intake** artifact (intake-only, 1.10.0) without advancing. Resolves `[NEEDS CLARIFICATION]` markers and `<!-- assumed: ... -->` comments, then recomputes the intake score. Idempotent and non-advancing. |
| `/fab-adopt` | Brings a completed off-pipeline change (scenario B — a branch authored without fab, with an OPEN or not-yet-created PR) into the pipeline. The real pipeline entered late with **apply** marked `skipped`; intake is reconstructed from the diff, review runs diff-only (the single review agent with the plan-conformance steps omitted), hydrate/ship/review-pr run for real. A MERGED PR (scenario A) is out of scope. See **Adopt**. |
| `/fab-continue` (apply) | Co-generates `plan.md` (`## Requirements` from `intake.md` + `## Tasks` + `## Acceptance`) at the entry sub-step and executes the unchecked tasks under `## Tasks` (main sub-step). Resumable — re-invoking skips plan generation when `plan.md` already exists and picks up from the first unchecked task. |
| `/fab-continue` (review) | Validates implementation against `plan.md` `## Acceptance` items, the plan's `## Requirements`, and constitution. On failure, offers rework options (fix code, revise plan, revise requirements). |
| `/fab-continue` (hydrate) | Completes the pipeline — hydrates change artifacts into memory files. |
| `/fab-archive` | Standalone housekeeping skill — moves completed changes to `fab/changes/archive/`, updates archive index, clears pointer. Not a pipeline stage. Supports restore mode. |
| `/docs-reorg-memory` | Analyzes memory files for themes and proposes reorganization. Read-only unless user approves changes. No active change required. |
| `/docs-distill-memory` | Rewrites an existing memory domain's topic files to the FKF present-truth style — strips transition narration and superseded-state prose, caps/de-ids `description:` frontmatter, relocates rationale into Design Decisions. Named `<domain>` distills that one domain; no-arg surveys all domains and loops every flagged one sequentially. One domain per approval unit (per-domain gate retained); read-only unless user approves. No active change required. |
| `/docs-reorg-specs` | Analyzes spec files for themes and proposes reorganization. Read-only unless user approves changes. No active change required. |
| `/fab-switch` | Changes the active change by creating the `.fab-status.yaml` symlink. Supports partial/slug matching. |
| `/fab-status` | Displays current change state — stage progress, plan counts (tasks + acceptance), suggested next command. |
| `/docs-hydrate-specs` | Identifies gaps between `docs/memory/` and `docs/specs/`, proposes additions with interactive confirmation. No active change required. |
| `/fab-discuss` | Primes the agent with project context for an exploratory session — loads the always-load layer and reports an orientation summary of the repo landscape. Session entry point, not a pipeline stage. Read-only; ends with a ready signal rather than a `Next:` line. |
| `/fab-operator` | Multi-agent coordination layer. Runs in a dedicated tmux pane, observes agents across every session on its tmux server, routes commands, auto-answers prompts, and drives autopilot queues. Coordinates but never implements — all pipeline work is spawned into a fresh worktree agent. See [operator](operator.md). |
| `/git-branch` | Creates or checks out the git branch matching the active (or specified) change. Standalone git command — never modifies fab state. Idempotent. |
| `/fab-help` | Prints an overview of available Fab skills and their purposes. |

## Files and Structure

| Term | Definition |
|------|-----------|
| `.status.yaml` | The status manifest inside each change folder. Tracks progress of all stages, plan counts (tasks + acceptance), and confidence score. Current stage is derived from the `active` entry in the progress map. Single source of truth for where a change is. |
| `config.yaml` | Project configuration at `fab/project/config.yaml`. Defines project identity, source/test paths, true-impact excludes, plan-acceptance categories (`checklist.extra_categories` for backward-compat), the `/fab-dedupe` seed commands (`consolidate.detectors`), independent provider capabilities (`interactive_command`, `headless_command`, and `native`) plus per-role fills (`providers:`), the two agent depth knobs (`agent.session`/`agent.workers`) and sparse per-role overrides (`agent.profiles`), the `dispatch.mode` preference ceiling and its `pane → native → headless` descent, pane placement/reaping settings, and optional stage hooks. (Automated PR reviewer toggles moved to `code-review.md` § Review Tools.) |
| `providers` | Top-level `config.yaml` table mapping an opaque provider name to independent launch capabilities: `interactive_command` (interactive session/pane), `headless_command` (one headless stage task), and `native` (Agent-tool support), plus the per-role fill map `profiles.<role>.{model, effort}`. Capability presence says how a rung runs and never chooses `dispatch.mode`; no field substitutes for another. fab-kit ships claude with all three capabilities and an exhaustive fill map; codex with both command grammars, no native capability, and sparse fills; agy with both command grammars, no native capability, and sparse model-only fills; and kimi with both command grammars and deliberately NO fills (its `-m` takes a user-config model alias, so it resolves an empty model and the CLI's own `default_model` applies). All four ship an `interactive_command`, so all four are pane-capable — pane capability rides launch grammar plus the provider-neutral readiness gate, while headless grammar is the half that varies per CLI; an absent `interactive_command` is a user-config shape the ladder descends past. A block is for overriding built-ins or defining a custom provider. A depth knob or `agent.profiles.<role>.provider` names one; `fab agent --provider` addresses one directly. See [stage-models](stage-models.md). |
| **Role** | One of six fixed agent slot names — `default`, `operator`, `doing`, `review`, `hydrate`, `fast` — with a **fixed, fab-owned** stage→role mapping and role→depth partition (neither overridable). A role is stage-named only where it maps 1:1 to a single referent (`review`/`hydrate`); `fast` keeps its role name because it is multi-referent (the ship stage plus the `/fab-proceed` prefix steps). A role resolves to a **profile**: its provider from `agent.profiles.<role>.provider`, else the role's **depth knob**, else the built-in claude; its model/effort per field from `agent.profiles.<role>`, else the resolved provider's `profiles.<role>`, else that provider's `profiles.default`, else empty. There is NO cross-role inheritance on the agent side — the single cross-role chain lives on the provider. Resolved by `fab resolve-agent <stage\|role>`, whose `--provider`/`--model`/`--effort` flags are the top rung of that precedence. (`agent.tiers` is the pre-2.17.0 spelling of `agent.profiles`, still read.) See [stage-models](stage-models.md). |
| **Profile** | A concrete `{provider, model, effort}` value — what a role resolves *to*. Not to be confused with `agent.profiles`, the sparse per-role *override* map that is one rung of that resolution. |
| **Tier 1 / Tier 2** | Agent **depth**, and the only thing "tier" means in fab-kit. Tier 1 is an agent a user talks to (a `fab agent` session, the `fab operator` coordinator, a `fab batch` worker); Tier 2 is an agent a pipeline stage dispatches to. The defining Tier-2 property is "owes a result artifact and owns no transitions", not "never spoken to" — so a watchable pane worker is still Tier 2. The axis the two depth knobs select a provider by; it is NOT a `{provider, model, effort}` profile (that is a **profile**, keyed by **role**). |
| **Depth knob** | `agent.session` / `agent.workers` — the two advertised config keys, each naming a provider for one **agent depth**. `session` covers the Tier-1 roles (`default`, `operator` — what a user talks to; applies at launch time); `workers` covers the Tier-2 roles (`doing`, `review`, `hydrate`, `fast` — what pipeline stages dispatch to; applies at every dispatch). Both default to `claude`, both are scope `both`. This is the whole advertised agent surface: "claude for what I talk to, codex for the workers." See [stage-models](stage-models.md). |
| `plan.md` | Auto-generated apply-stage artifact. Contains both `## Tasks` (consumed by apply) and `## Acceptance` (consumed by review) sections. Replaces the legacy `tasks.md` + `checklist.md` pair. Section headings are the parser contract; phase/category subheadings under each are presentational. |
| `.fab-status.yaml` | Symlink at repo root pointing to the active change's `.status.yaml`. Read by every skill; created by `/fab-switch`; removed by `/fab-archive`. |
| `fab/changes/` | Directory holding all active change folders. Completed changes are moved to `fab/changes/archive/`. |
| `fab/changes/archive/` | Directory holding completed change folders, date-bucketed as `archive/{yyyy}/{mm}/{name}/` with a top-level `index.md`. Folder names are unchanged (no rename on archive). |
| `docs/memory/` | Memory files. Organized by domain with index files. The authoritative post-implementation source of truth. |
| `log.md` | The generated per-folder change log written by `fab memory-index` for every domain and sub-domain with attributable git history (FKF §6, C-lite). Replaces the per-file `## Changelog` tables FKF removes. Entries are date-grouped newest-first, joining git history (the *when* and *which file*) with each change's `.status.yaml` `summary:` (the *what*). Single-writer and never hand-edited; generation is **freeze-on-write** (FKF §6.4) — existing entries are immutable and regeneration only appends new ones, keyed on `(file-base, change-id)`. |
| `log.seed.md` | A curated per-folder sidecar in the same entry format as `log.md`, merged **beneath** the git-projected entries by `fab memory-index`. It preserves the pre-FKF `## Changelog` rows, which have no `.status.yaml summary:` to project from, under their own authored dates. Read-only *input* — the generator never writes it, so `log.md`'s single-writer discipline holds. Excluded from distillation like a ledger. |
| `docs/specs/` | Human-curated pre-implementation design specifications. Flat structure, not managed by Fab tooling. |
| `src/kit/` | The canonical kit source in the fab-kit dev repo — templates, skills, migrations, scaffold. Distributed to user projects via the system cache + `fab sync` (never copied into the repo). |
| `$(fab kit-path)/templates/` | Markdown scaffolds that skills fill with concrete content. Includes templates for all artifact types. |
| `fab` CLI | The Go binary surface that replaced the legacy kit shell scripts. Change and pipeline state: `fab preflight`, `fab status`, `fab change`, `fab score`, `fab resolve`, `fab log`, `fab impact`, `fab pr-meta`. Agent and worker orchestration: `fab resolve-agent`, `fab dispatch`, `fab agent`, `fab operator`, `fab pane`, `fab batch`. Docs and setup: `fab memory-index`, `fab config`, `fab sync`, `fab doctor`, `fab migrations-status`, `fab kit-path`, `fab skill`, `fab shell-init`, and the help surfaces. See `_cli-fab.md` for the full reference. |
| `fab memory-index` | The generator that is the single writer of every generated memory artifact — the root (domains-only) index, every domain and sub-domain `index.md`, the per-folder `log.md` files, and the root index's `fkf_version` frontmatter. Indexes render as a pure, byte-stable function of folder contents plus each file's `description:` frontmatter (content-only, no dates); `log.md` generation is append-only under freeze-on-write. `--check` verifies committed artifacts against a regeneration, classifying differences as benign drift (exit 1) or destructive loss (exit 2), with a separate blocking content class for malformed or over-cap frontmatter. Agents never hand-edit its outputs. |

## SRAD and Confidence

| Term | Definition |
|------|-----------|
| **SRAD** | Autonomy framework for decision-making. Stands for **S**ignal strength, **R**eversibility, **A**gent competence, **D**isambiguation. Used to grade how confidently a skill can assume a decision without asking the user. Defined in the `_srad.md` helper, loaded by the planning skills. |
| **Certain** | SRAD grade. Decision deterministically answered by config, constitution, or codebase. No marker, not mentioned in output. |
| **Confident** | SRAD grade. Strong signal, one obvious interpretation. No artifact marker; noted in Assumptions summary. |
| **Tentative** | SRAD grade (indicative — derived from composite, 20 ≤ c < 50). Reasonable guess but multiple valid options. Marked with `<!-- assumed: ... -->` in the artifact. Resolvable by `/fab-clarify`. |
| **Unresolved** | SRAD grade (indicative — derived from composite, c < 20). Cannot determine; incompatible interpretations. Surfaced (asked or deferred) — never silently assumed; blocks the gate via the penalty curve (penalty ≥ 2.0). |
| **Confidence score** | A 0.0–5.0 numeric measure of how well-resolved a change's decisions are. Demerit formula: `score = clamp(5.0 - Σ penalty(c), 0, 5)` where each row's composite `c = 0.20*S + 0.30*R + 0.30*A + 0.20*D` and `penalty(c)` is `0` for `c ≥ 80`, `(80-c)/30 * 0.50` for `50 ≤ c < 80`, and `0.50 + (50-c)/50 * 2.50` for `c < 50`. There are no hard-fail short-circuits — a genuine unknown scores `composite < 20` (penalty ≥ 2.0) and blocks the gate via the curve. Stored in `.status.yaml`. See [SRAD](srad.md). |
| **Confidence gate** | The single intake gate that `/fab-ff` and `/fab-fff` check before entering the automated bracket: the intake confidence score must meet the threshold (flat 3.0 for all types as of 1.10.0; see [Change Types](change-types.md)). Ensures the pipeline runs only when intake decisions are sufficiently resolved. Bypassed with `--force`. |
| **Assumptions summary** | A table appended to artifacts listing all Confident and Tentative decisions with rationale. Enables `/fab-clarify` to discover and resolve assumptions. |
| `<!-- assumed: ... -->` | Inline HTML comment marker placed after tentatively assumed content. Scanned by `/fab-clarify` for resolution. |
| `<!-- clarified: ... -->` | Inline HTML comment marker replacing an assumed marker after `/fab-clarify` resolves it. Informational only. |

## Tools and Environment

| Term | Definition |
|------|-----------|
| **tmux** | A terminal multiplexer that lets you split one terminal window into multiple panes or tabs. Fab Kit uses it to run one AI agent session per change in parallel — each change gets its own tmux tab. Install with `brew install tmux`. |
| **Git worktree** | An additional working directory linked to the same git repository, created with `git worktree add` (or `wt create`). Each worktree has its own branch and working files, so parallel AI sessions can modify different changes without conflicts. |

## Workflow Concepts

| Term | Definition |
|------|-----------|
| **Adopt** | Bringing a completed change that bypassed the pipeline back in (`/fab-adopt`). Scoped to **scenario B** — mid-flight adoption of a branch whose code was authored without fab and whose PR is **OPEN or not yet created**. The real pipeline entered late: only **apply** is `skipped` (the code already exists), while intake (reconstructed from the diff), review (diff-only), hydrate (writes `docs/memory/` — the permanent-loss recovery), ship (retrofits the PR `## Meta`), and review-pr all run for real. **Scenario A** — retroactive backfill of an already-MERGED PR — is explicitly out of scope. |
| **[AUTO-MODE]** | First-line invocation prefix that selects `/fab-clarify`'s autonomous, non-interactive flow and machine-readable result. Prefix placement, detection, and transitivity are defined in `fab-clarify.md` § Skill Invocation Protocol; absence selects interactive mode. |
| **Context loading** | The convention that every skill loads relevant project files (config, constitution, memory index, change artifacts) before generating output. Defined in `_preamble.md`. |
| **Fast-forward** | Confidence-gated pipeline from intake through hydrate (`/fab-ff`). Proceeds autonomously once the single intake gate passes — no clarify steps inside the bracket; ambiguity is resolved inline as graded SRAD assumptions, with a sub-agent review + auto-rework loop. |
| **Fast-forward-further** | Confidence-gated pipeline from intake through review-pr (`/fab-fff`). Same as fast-forward but extends through ship and PR review. |
| **Gap analysis** | Evaluation performed by `/fab-new` before creating an intake. Checks whether the change is already covered by existing mechanisms. |
| **Next steps convention** | The rule that every skill must end output with a `Next:` line suggesting follow-up commands. Keeps users oriented in the workflow. |
| **Preflight** | Validation performed by `fab preflight` before skill execution. Checks project initialization, active change resolution, and status file existence; outputs the change context as YAML. |
| **Resumability** | The property that `/fab-continue`, `/fab-ff`, and `/fab-fff` can be interrupted and re-invoked, picking up from the first incomplete item. The markdown checkboxes in `plan.md` `## Tasks` are the progress state; plan generation is skipped when `plan.md` already exists. |
| **Rework loop** | The review-to-apply feedback cycle. `/fab-continue` (review) can loop back to apply (fix code), revise the plan's `## Tasks`/`## Acceptance`, or revise the plan's `## Requirements` (for a fundamentally wrong intake, run `/fab-continue intake` then `/fab-clarify` first, deleting `plan.md` to force requirements regeneration). |

## Naming and Conventions

| Term | Definition |
|------|-----------|
| **Folder name format** | `{YYMMDD}-{XXXX}-{slug}` — date + 4 random lowercase alphanumeric + 2–6 word slug. All lowercase. Agent-generated, no script needed. |
| **RFC 2119 keywords** | MUST/SHALL (mandatory), SHOULD (recommended), MAY (optional). Used in the plan's `## Requirements`, memory, and constitution to express requirement strength. |
| **GIVEN/WHEN/THEN** | Scenario format used in `plan.md` `## Requirements` and memory files. Structured as precondition, action, expected outcome. |
| **[NEEDS CLARIFICATION]** | Inline marker for unresolved ambiguities — an **intake-only** construct (1.10.0). Resolved by `/fab-clarify`. Never appears in `plan.md`. |
| **[BLOCKING]** / **[DEFERRED]** | Legacy priority markers for intake open questions — removed from the intake template in 1.10.0 (SRAD grading handles prioritization; open questions are now listed unlabeled). May still appear in archived intakes. |
| **[P]** | Task marker in `plan.md` `## Tasks` indicating the task is parallelizable — can execute alongside other `[P]` tasks in the same phase. |
| **A-###** | Acceptance item ID in `plan.md` `## Acceptance` (e.g., A-001). Sequential, three-digit, zero-padded. Verified by `/fab-continue` (review). |
| **CHK-###** | Legacy acceptance item ID preserved verbatim by the migration for in-flight changes that pre-date `plan.md`. New plans use `A-###`. |
| **T###** | Task ID in `plan.md` `## Tasks` (e.g., T001). Sequential within the change. |
