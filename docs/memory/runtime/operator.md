# Operator

**Domain**: runtime

## Overview

The operator is a standalone, long-lived coordination skill (`/fab-operator`) — NOT a pipeline stage. It runs in a dedicated tmux pane, coordinates agents **across multiple repos and multiple tmux sessions on a single tmux server**, and tracks everything it watches, probes, spawns, or waits on as items in one generic `tracked` list (agent sessions in panes, GitHub PRs, Linear/Slack queries, shell probes, tasks, notes). Per tick it observes via `fab operator tick-start --diff --quiet` (the binary snapshots panes, runs every due shell probe, and evaluates completion/dependency/staleness; `fab pane map --all-sessions` remains the on-demand surface), detects pending questions by capture-classifying each candidate pane (`rk mux capture --classify`), routes commands and prompt answers via `rk mux send` (plain for command routing, `--answer` for answering a `waiting` agent, `--key` for key-name input), and takes its cadence from run-kit's operator-tick cron entry — whose schedule the binary itself derives from the tracked set and applies via `rk cron edit`. run-kit is a **hard dependency**: startup probes `command -v rk` and `rk cron list --json` once (the §2 rk Gate) and STOPs with an install hint when either half fails. Every agent is addressed by the `(session, repo, pane)` tuple: the **pane ID is the primary key** (server-global, stable), with `repo` (the agent's absolute main-worktree root) and `session` (its tmux session name) as added dimensions. `session` is a display/context dimension, **never a join key** — it is reassigned by `swap-window`/`move-window`/rename and a tracked agent's session can change mid-lifetime (run-kit's operator-relocation direction moves the window), so all correlation rides the pane ID (the identity-key contract in [pane-commands.md](/runtime/pane-commands.md) § `fab pane map`). A pane item joins on `scope.pane` plus a `scope.pane_pid` shell-pid fingerprint recorded when the pane is set — the fingerprint is the recycled-pane discriminator (tmux recycles `%N` ids across server restarts while the socket-keyed state file survives); a null fingerprint or an unreadable current pid joins on the pane id alone. A `pane` item tracks **any agent session in a pane** — a fab change, when present, is an observed, baseline-maintained field (`scope.change`, like `scope.stage`), never a prerequisite to tracking. There is **one operator per tmux server**, owning **one server-keyed state file** that spans every repo it coordinates. This file documents the operator's behavior, its tick lifecycle and state model, and the operator design decisions. For the `@rk_pane_agent_state` agent-state convention and `fab pane` primitives the operator builds on, see [runtime-agents.md](/runtime/runtime-agents.md) and [pane-commands.md](/runtime/pane-commands.md). For the Go-side mechanism (server-keyed state path derivation, the `fab operator track` verb family, the `repo` JSON field, `fab agent --print --repo`), see [kit-architecture.md](/distribution/kit-architecture.md) → "Operator State File" and [pane-commands.md](/runtime/pane-commands.md).

## Requirements

### Coordination Principles & Safety Model

`/fab-operator` is a standalone, self-contained coordination skill — NOT a pipeline stage. It runs as a long-lived agent session in a dedicated tmux pane, observing agents via the tick document and `fab pane map`, routing commands and prompt answers via `rk mux send` (plain / `--answer`), taking its cadence from the rk cron operator-tick entry (the clock block below), and auto-answering agent prompts.

#### Principles

**Coordinate, don't execute.** Every task, bug report, or idea the user hands the operator is a work request and goes to an agent: the fab pipeline when the target repo has a `fab/` project (§6 Working a Change forms 1–3 — a fresh report as the raw-text form, a `/fab-new` spawn in a fresh worktree), a plain agent in a fresh worktree otherwise (form 4); a report naming a live tracked item is a send to that item's agent. Reading code to reproduce or diagnose, or editing files, in the operator pane counts as executing and is prohibited. The operator reads whatever plan, roadmap, intake, or task document the tracked work needs, and keeps handing the next unit of work to an agent until the plan is done. Direct actions are exactly this maintenance allowlist: merge PR, archive, worktree deletion, rebase/cherry-pick for dependency resolution, `fab operator track` verbs, and pane sends/answers/nudges. The only thing the operator asks about a work request is which repo (plus the target-session tie-break in §6 Spawning an Agent step 2) — never whether to spawn; that ask-set is scoped to the work request and does not relax the §3 pre-send and destructive-action confirmations or the §6 queue confirmation, which still apply.

**Not a lifecycle enforcer.** Individual agents self-govern via their own pipeline skills. The operator does not validate stage transitions or enforce pipeline rules.

**State re-derivation.** Before every action, re-query live state via `fab pane map` (or `wt list` + `fab change list` outside tmux). Panes die, stages advance, agents finish — stale state leads to wrong actions.

#### Context Loading

The operator loads only **three** project files: `fab/project/config.yaml`, `fab/project/constitution.md`, and `fab/project/context.md` (optional — skip gracefully if missing). It is a listed exception to the `_preamble.md` §1 always-load layer — `code-quality.md`, `code-review.md`, and both doc indexes serve artifact generation and review, which the operator never does — it neither authors nor reviews artifacts (its own §1 Coordinate, don't execute work rule) — and a long-lived session re-pays every loaded file after each reload (compaction, `/clear`, or restart) (zc9m). Helpers declared in frontmatter: `_cli-fab-operator` (the `fab operator` / `fab agent` CLI reference — the `track` verb contracts and the tick document), `_cli-fab-pane` (the `fab pane` / `fab dispatch` CLI reference), `_cli-agents` (the generic agent-CLI interaction primitives — spawn composition, pre-send validation, delivery probe, peek, await — plus the per-provider grammar/discovery dictionary; see [agent-primitives.md](/runtime/agent-primitives.md)), and `_cli-external` (external tool reference for `wt`, `idea`, `hop`, `rk` (run-kit — including the fab-owned operator escalation send and the pointer to the startup role self-mark), and `tmux` — loaded only by operator, not by pipeline skills). The `_cli-agents` split is **agent primitives vs. operator orchestration**: the helper owns *how* to talk to an agent CLI, this skill owns *when and whether* to (confirmation tiers, retry budgets, repo targeting, tracking, dependency resolution, queue choreography). `_cli-external` carries **only fab-owned** content: what each tool *is* in one line plus the fab-specific integration choreography no tool's own documentation carries (the operator spawning sequence, the escalation `rk notify` usage and the role self-mark pointer, the `fab pane` notes). Each **owned** tool's *usage knowledge* is delegated at use-time to `<tool> skill` (the toolkit's per-binary usage briefing, `shll standards skill`) — **`command -v`-gated fail-silent for all four owned binaries** (`wt`, `idea`, `rk`, `hop`), which are separate sibling formulas that may all legitimately be absent (nnda) — and its exhaustive command tree to `<tool> help-dump`; both are version-locked by construction (embedded in the same binary as the flags they describe). The delegations fail silently on absence, but the worktree entry point that functionally *requires* `wt` (the agent spawn sequence below) stops with an install hint instead — see the `### wt Gate` preflight probe under Startup. A required **version-skew fallback** covers an installed binary predating its `skill` subcommand: the invocation capability-probes `<tool> skill` (non-zero exit or empty output = the probe) and falls back **silently** to the shll.ai bundle-page pointer `https://shll.ai/<tool>/skill`, so operator context loading never breaks on an older binary. It does NOT run `fab preflight` (change resolution — distinct from the startup `wt` availability probe under § Orientation).

#### Orientation

On invocation, runs `fab pane map` and displays the output, then signals readiness. Outside tmux (`$TMUX` unset), falls back to `wt list` + `fab change list` for status queries only — monitoring is disabled.

**Startup rk gate (hard dependency)**: the operator's clock, role mark, send gate, spawn readiness, and notifications are all HexoKit, so §2 Startup probes **once** — `command -v rk >/dev/null 2>&1 && rk cron list --json >/dev/null 2>&1` (the second half is the capability probe for an rk predating `rk cron`) — and STOPs with `Error: the operator requires HexoKit — brew install sahil87/tap/run-kit` when either half fails; no later call site is individually gated. This is the operator's deliberate exception to `_preamble.md` § HexoKit (rk) Reference's fail-silent rule: that rule protects skills for which rk is an optional enhancement; for the operator rk is the substrate, so absence is a startup error, not a degradation. The gate sits between the tmux gate and the role mark and is idempotent (a `/fab-operator` reload re-probes harmlessly).

**Startup role self-mark (swun)**: after the rk gate, the operator marks its own tmux window with run-kit's `@rk_win_role` window option — `rk role operator >/dev/null 2>&1 || true` — so run-kit's dashboard pins the operator row directly under its sidebar SESSIONS header. rk owns the option contract, the pinned rendering, and the one-operator-per-server radio semantics; fab is only the producer. The step is fail-silent by contract (a role-mark failure is never startup-blocking), idempotent (a restarted operator re-marks the same window harmlessly), and has no unmark counterpart — staleness and radio conflicts are rk's to resolve. Owned by `fab-operator.md` §2 Startup § Role Mark; `_cli-external.md` § rk carries the pointer.

**Startup `wt` gate (scoped to agent spawns) (nnda)**: `wt` ships as a standalone sibling formula that may legitimately be absent, and only the agent spawn path needs a worktree — tracking an existing pane, a GitHub PR, a Linear query, or a shell probe needs none — so startup does **not** probe it. When a pane item is about to spawn, the operator probes `command -v wt >/dev/null 2>&1` once per operator session; on absence it STOPs the spawn with the actionable install hint `wt is required for operator spawning — install it via: brew install sahil87/tap/wt`. This is the "stop with hint" side of the graceful-degradation split — the operator's tool-usage delegations still fail silently on absence (§ Context Loading). See [distribution.md](/distribution/distribution.md) § Homebrew Formula.

#### Safety Model

| Tier | Examples | Behavior |
|------|----------|----------|
| Read-only | Status check, pane map | No confirmation |
| Recoverable | Send `/fab-continue`, rebase | Announce before sending |
| Destructive | Merge PR, archive, delete worktree | Confirm before executing |

A queue (a chain of `pane` items) is confirmed separately, at queue creation, with text reflecting the active merge mode ("Confirm upfront (creates PRs — merge after review)." in `cherry-pick-ladder`; "Confirm upfront (merges PRs on completion)." in `merge-auto`; "Confirm upfront (creates stacked PRs — merge after review)." in `stacked-prs`) — see Queues below.

**Pre-send validation**: Before sending keys to any pane, the operator runs the two-step gate the `_cli-agents` helper owns (pane exists via a refreshed pane map — dead panes swallow keys silently; agent state fits the send intent per the three-state `@rk_pane_agent_state` read `active`/`waiting`/`idle`/`—` unknown, the same mode-aware gate `rk mux send` enforces) — see [agent-primitives.md](/runtime/agent-primitives.md) § Pre-send validation — then applies **its own policy** on the outcome: a gone pane reports "Pane for {change} is gone" and does not send; for routed commands, `active`, `waiting`, and unknown all warrant explicit user confirmation before sending, and a confirmed send rides `rk mux send` with the mode per intent (`waiting` → `rk mux send --answer`; `active` requires `rk mux send --force`, the deliberate skip-everything override; unknown warns-and-sends on plain send); only `idle` sends unattended. The §5 auto-answer flow is the unattended `--answer` consumer — the confirm policy governs routed commands, not detected-prompt answers. Two operator-specific checks follow the gate: the target change must be the pane's active change (else send rendered `fab-switch <change>` first) and the pane's git branch must match the change folder name (else send rendered `git-branch`). Every explicit skill invocation follows [agent-primitives.md](/runtime/agent-primitives.md) § Skill Prompt Rendering, using the receiving harness identity for existing panes. When a send appears to land but the agent never starts working, the operator applies the helper's **delivery probe** (the printed-prompt trap: literal sentinel → `C-u` → retype → Enter → confirm via a working indicator) rather than re-sending blind.

**Bounded retries**: Every automatic action has a bounded retry count. Unbounded retries compound errors.

| Situation | Max retries | Escalation |
|-----------|-------------|------------|
| Stuck agent nudge | 1 | "Appears stuck at {stage}. Manual investigation recommended." |
| Rebase conflict | 0 | Immediately flag to user |
| Pane death | 0 | Report pane gone. Respawn only for a queue-driven change (1 attempt) |
| Agent exited (pane survives as a shell) | 0 | Report gone (pane kept, cwd intact). Respawn only for a queue-driven change (1 attempt): kill the leftover shell pane first (`rk mux kill` — an uninstrumented/idle pane passes its gate), then spawn per the spawn sequence |
| Send to busy agent | 0 | Warn user, require explicit confirmation |
| Cherry-pick conflict | 0 | Abort, log, escalate. Do not spawn |

#### Tracking & Window Marks

The operator's durable work set is the `tracked` list in the server-keyed operator state file — every item carries its kind, probe, completion predicate, and bookkeeping (the schema is documented under "Operator State File" below). Items are created, updated, observed, and removed exclusively through the `fab operator track` verb family (the §4 never-hand-write doctrine); `track add --kind pane` with `--branch`+`--repo` also writes the `{ branch, repo }` pair into `branch_map` in the same mutation (keyed by `--change` when given, else the item id), and the tick's baseline writer adds the entry when a change is first observed on a pane item that lacks one. Any verb that sets `scope.pane` records the pane's shell pid in `scope.pane_pid` in the same mutation (null on lookup failure). `track rm` deletes the item while retaining the `branch_map` pair for downstream dependency resolution. The tracking/removal mechanics below (window marks on track, done-mark on removal) key on server-global window/pane IDs, so they are independent of the `(session, repo, pane)` addressing model described in the next section.

**Tracking triggers**: the operator sends a command to an agent, the user requests tracking, or the operator triggers an automatic action toward it (including queue- and linear/slack-driven spawns). Read-only actions do not track. **Spawned agents are always tracked automatically** — the operator MUST NOT ask the user whether to track a spawned agent. This constraint is reinforced in both the §1 principles and the "Spawning an Agent" procedural subsection to ensure proximity-based LLM adherence.

**Window marks ride run-kit, not the window name.** A spawned agent's window is named plain `<wt>` at creation (`rk tab new --name`), then marked `rk tab mark @<window_id> auto` with a note `rk tab note @<window_id> "<id> · <stage>"`. While a pane item is `waiting` on a human the mark flips to `rk tab mark @<window_id> blocked`. On every removal path the operator runs `rk tab mark @<window_id> --off` and `rk tab note @<window_id> "✓ <id> done"`. The mark/note contracts (`@rk_win_marker` / `@rk_win_note`) are tool-owned (`rk skill`); fab is only the producer.

**A pipeline dispatch carries no operator mark.** An interactive-pane stage dispatch (`fab dispatch open`, see [dispatch.md](/runtime/dispatch.md)) takes the identity string `fab-{id}-{stage}` and deliberately carries no operator mark: a pipeline dispatch borrows tmux as a launch surface without joining the tracked set. It usually opens **no window at all** — when the dispatching agent is itself a tmux pane, its stage worker is a **pane split into that agent's own window**, so it never reaches the operator's tab bar; a **new window** named `fab-{id}-{stage}` is the fallback shape (a dispatcher with no pane to split, or a `--server`-named socket), and that window is unmarked for the same reason — pre-marking would make the tab bar claim the operator owns a lifecycle it does not. Such a window is an ordinary unmarked window from the operator's perspective; if the operator genuinely tracks it, the normal spawn/track path applies the marks.

**Removal triggers**: the item's completion fires (a pane item's built-in predicate — applicable only when `scope.change` is non-null: `review-pr` done/skipped when `stop_stage` is null, or at/past its `stop_stage`; a change-less pane item is never done on its own — or a probed item's `done_when`), the pane dies, or the user explicitly stops tracking. `fab operator track rm <id>` is the ack that stops the level-triggered `done`/pane deltas.

#### Multi-Repo Model

**One operator per tmux server.** The isolation unit is the tmux server — a single operator spans every session and every repo on that server. A second operator means a second tmux server (`tmux -L <label>`). "Multiple sessions, same server" share one operator and one state file. There is no `--name` dimension; the server boundary is the only isolation knob. This matches the server-wide singleton already enforced by the `operator` window (`fab operator` switches to the existing window rather than creating a second one).

**Server-keyed state file.** The `tracked` list, `branch_map`, and `clock_override` persist in **one server-keyed file** — `$XDG_STATE_HOME/fab/operator/<server-slug>.yaml` (fallback `~/.local/state/fab/operator/<server-slug>.yaml`), keyed by the tmux socket path so the one operator-per-server owns one file across all the repos it coordinates. The binary derives this path and owns every mutation: the file is read via `fab operator state` (which persists the empty skeleton — `tracked: []`, `branch_map: {}` — when missing; human output opens with an `# `-prefixed OPEN NOTES header — one line per `kind: note` item: id · age · first line, with a display-only staleness flag past 14 days — omitted when no note item exists and absent from `--json`) and `fab operator track list`, and mutated **only** through the `fab operator` verb families — the `track` verbs (`add`/`update`/`observe`/`rm`/`list`/`clock`) for the tracked list and the bounded cadence override, `branch-map rm` for the explicit user-initiated clear, and `tick-start` for the tick bookkeeping, baselines, and probe results. The operator never computes the path and never hand-writes the file — the doctrine is *agents never compute (or hand-write) what the binary can own* (see the Full Mediation design decision below); the binary owns the schema, the timestamps, the list caps (the 200-entry `seen` dedupe list, oldest pruned), and the atomic write. Note-item text is binary-capped at 500 characters. See [kit-architecture.md](/distribution/kit-architecture.md) → "Operator State File" for the derivation mechanism. The file path and its slug rule are a cross-repo contract: run-kit mirrors the exact `slugify` rule to locate the file for display (◉ watched rows, `⚠ operator stale`), pinned in run-kit's operator-cron spec — renaming the file or changing the slug rule requires a coordinated run-kit change. A legacy state file from fab ≤2.24 (carrying the old `monitored`/`watches`/`autopilot`/`notes` sections) is converted by the binary on first touch — see the Legacy State Converts on First Touch design decision and the migration walkthrough in [migrations.md](/distribution/migrations.md). Old repo-rooted `.fab-operator.yaml` files from before the server-keyed model are **not migrated** — they are abandoned in place.

**`(session, repo, pane)` addressing.** Every tracked item and `branch_map` value is repo-qualified. The pane ID is the primary key (server-global, stable); `repo` (absolute main-worktree root) and `session` (tmux session name) are added dimensions, not replacements. The recorded `session` is **context, not identity**: never re-derive which item a pane is from a session name or window index — positional keys are reassigned by `swap-window`/`move-window`/rename, and a tracked agent's session can change mid-lifetime — re-derive per tick from the tick's snapshot keyed on the pane ID (`fab pane map` remains the on-demand form). The per-kind schema:

- A `pane` item's `scope` carries eleven keys, all null until set: `pane` (null until spawned or first tracked) and its `pane_pid` shell-pid fingerprint (recorded when the pane is set; null ⇒ pane-id-only join), `change` (an observed, baseline-maintained field like `stage` — set by `--change` at `track add` or by the tick's baseline writer when a change resolves on the pane; never required to track), `repo`, `session`, `branch`, `stage`/`agent` (the binary-owned diff baselines), `stop_stage`, `spawned_by`, and `merge_mode` (set when the item was queued via a chain).
- The `branch_map` value is `{ branch, repo }`. The `repo` is required to disambiguate a dependency's branch across repos and to choose same-repo (cherry-pick) vs. cross-repo (ordering-only) dependency resolution.
- A `linear`/`slack` item's `scope` carries `repo` — the repo its spawned changes land in — plus `stop_stage` and `query`. An item with no `scope.repo` cannot spawn.

#### Multi-Repo Coordination: Spawning, Dependencies, Queues

**Spawning-rules home.** The **Operator Spawning Rules** — the known-change vs new-change worktree/branch naming strategy (known change: probe-and-route the change-folder branch — the branch usually already exists, created by `/fab-new` in the original checkout, so pass `--checkout <change-folder-name>` when the branch exists and the positional `<change-folder-name>` only when it does not; new change from backlog: `wt create` on the default branch, then `/fab-new` in the agent — fab-new Step 11 renames the worktree's disposable branch inline, so the operator does NOT send a post-intake `/git-branch` (w7dp)) — live in `_cli-external.md`'s `wt` section (only `fab-operator` declares `_cli-external`, so only it pays). This is **fab-owned choreography and stays** even after the `_cli-external` slim (clix): the routing rule necessarily keeps stating *which* wt form to use when (existing branch → `--checkout`; missing → positional) because that decision is fab's — what the slim moved out is the *tool-owned* `wt` contract behind it (the `create`/`delete`/`list` command set, the `wt create` flags/conflict table, the exit-2 new-branch-only semantics), now delegated to `wt skill` at use-time. `fab-operator.md` §6 remains the normative step-by-step spawn procedure. The `fab agent --print --repo <target-repo>` / "never the operator's own config.yaml" repo-targeting rule has a single home — `fab-operator.md` §6; `_cli-external.md`'s `wt` section states only the separate `wt`-side rule (run `wt create` in the target repo's directory) and delegates the session-command targeting there.

**Repo- and session-targeted spawning.** Every spawn flow first establishes **which repo** the work targets (an existing item's `scope.repo`, a linear/slack item's spawn-target `scope.repo`, or the repo the user names — defaulting to the operator's launch repo) and **which tmux session** the new agent window must land in, then runs each step against those, not the operator's own repo or its ambient session:

1. **Derive the target session** (§6 step 2's majority rule): the candidate set is `rk mux sessions --json`'s `role: "user"` rows (run-kit derives the roles from its own reserved constants, and its `reserved` catch-all keeps the exclusion correct when rk adds new infrastructure kinds), minus the operator's own session (never a spawn target); from the same `rk mux panes --json` snapshot, count per candidate session the panes whose `cwd` is under the target repo — the session holding the most wins. A tie the count cannot separate falls to the §8 "Spawn target session" setting; still torn → the one ask. An evidence-backed decision proceeds without asking: the operator announces the chosen session and its deciding evidence in the spawn output and auto-sets the §8 setting. Only a **genuinely torn** spawn — zero candidates, or a tie the setting does not break — asks the user once (attended, answer kept as the §8 setting) or escalates via the §5 notification path (**unattended** queue/linear-slack tick); an evidence-backed inference is a derivation, not a guess (cx52). The session is pinned explicitly at spawn (`rk tab new --session =<session>`) — **the ambient session is never an implicit target** (the operator may run in its own dedicated session, where an untargeted spawn silently misplaces the window; the session analog of the never-rely-on-CWD rule), and an unknown session errors loudly at spawn — never a silent retry against the ambient session.
2. Run `wt create --non-interactive` **with the target repo as the working directory**, so the worktree lands under `$(dirname <target-repo>)/<repo-name>.worktrees/` rather than the operator's repo.
3. Resolve **that repo's** default-role session command per [agent-primitives.md](/runtime/agent-primitives.md) § Spawn composition, in the **role-addressed** form with the target repo named, as one structured query: `fab agent default -o yaml --repo <target-repo>` — its `command` key is the session command (byte-identical to `--print`) and its `skill_prefix` key is the initial skill's prefix (see [kit-architecture.md](/distribution/kit-architecture.md)). The operator-specific rule is **always pass `--repo <target-repo>`** — never the operator's own `config.yaml`, since each repo may configure a different provider/interactive command. The printed command is **profile-resolved** — `fab agent --print` composes `providers.<default.provider>.interactive_command` with the `default` role's `{model}`/`{effort}` substituted (or Claude-style flags appended) — so operator-spawned workers launch **with** a profile (see the "Repo-Targeted Worker Spawns Carry a Profile" Design Decision below). The helper's provider-addressed form (`fab agent --provider <name>`) serves ad-hoc cross-provider sessions. Operator worker spawns carry the target repo's `default`-role profile and take their initial skill's prefix from that same document's `skill_prefix` — one resolution, never a separate `--print` call — per [agent-primitives.md](/runtime/agent-primitives.md) § Skill Prompt Rendering.
4. Open the agent tab per the helper's raw argv form — `rk tab new --session =<session> --cwd <worktree> --name <wt> --ready --json -- <spawn argv…>` (see [agent-primitives.md](/runtime/agent-primitives.md) § Spawn composition): the session command and the initial prompt ride as **argv tokens after `--`**, never a composed shell string — no shell escaping, no `; exec` tail (rk appends the interactive shell fallback itself). The `--json` report carries `window_id` and `pane_id` plus a `ready:` verdict (`parked`/`narrow`/`gone` handled per `_cli-agents.md` § Await — `gone` gets one bounded retry); the marks consume the window id (`rk tab mark @<window_id> auto` + `rk tab note @<window_id> "<id> · <stage>"` right after spawn), and `fab operator track add <id> --kind pane --pane <pane_id> --session <session> --repo … [--change <change-id> --branch <branch>]` consumes the pane id (recording the `pane_pid` fingerprint in the same mutation) and writes the `{ branch, repo }` pair into `branch_map` in the same command. The item id is the change id when known at spawn, else the worktree name — a raw-text spawn is tracked at spawn under the worktree name (its change may not exist yet), and the change appears later as a `changed` delta; the id is never renamed (dependents reference item ids, and `branch_map` is keyed by change). An item already tracked as `pending` (a queued spawn) is instead updated — `fab operator track update <id> --scope '{"pane":"<pane-id>","session":"<session>"}'` — because `track add` refuses a duplicate id.

All four work paths (existing change, raw text, backlog/Linear, non-fab repo) and queue- and linear/slack-driven spawns use the §6 repo- and session-targeted sequence. Existing changes select bare skill `fab-fff` with the change argument; raw text selects `fab-new` with the description; backlog/Linear selects `fab-new` with the ID. Each of those invocations is composed as `<skill_prefix><skill> <args>` with the argument text verbatim, delivered as one trailing argv token. Existing-change targeting uses the transient change-name override. Variant-specific steps include the idea lookup for backlog/Linear, `--reuse` for queue respawns, and linear/slack spawn fields (`stop_stage`/`spawned_by`). The idea lookup is `command -v idea`-gated and skipped silently when unavailable; `fab-new` resolves the backlog ID from `fab/backlog.md`.

**Non-fab repo → plain agent (form 4).** When the target repo has no `fab/` directory (probe `test -d <target-repo>/fab`), the work request still goes to an agent through the same eight-step sequence: `wt create --non-interactive --worktree-name <name>` with no branch argument (there is no change branch), the existence guard trivially skipped, `fab agent default -o yaml --repo <target-repo>` degrading to the project-free config cascade (its `command` is still the session command; `skill_prefix` goes unused), and the tab opened with the **raw task text plus the closing instruction `Commit on this branch, push, and open a draft PR against the default branch.`** — not a skill invocation. It is tracked unconditionally as a change-less `pane` item whose id is the worktree name, passing `--branch <wt>` (the branch wt created) so `branch_map[<wt>] = {branch, repo}` is written and survives the pane item's removal, with no `--stop-stage` (there are no stages). Completion is a chained `github-pr` item the operator adds once the PR URL is known (`fab operator track add <wt>-pr --kind github-pr --scope '{"repo":"<repo>","pr":<n>}' --check-every 2m`, then `track rm <wt>`); the user may `track rm` the pane item at any time. Pipeline-first binds only repos with a `fab/` project; a repo without one is exempt from the pipeline, never from delegation. The operator never runs `fab init` — bootstrapping fab is the user's repo-structure decision, mentioned at most once as an option in a report, never picked, never offered as a menu. A linear/slack-driven spawn whose `scope.repo` has no `fab/` takes this form too (raw prompt, no `--stop-stage`, still `--spawned-by`).

**Existence-guarded pointer activation at spawn (5xnx).** The §6 "Spawning an Agent" sequence is **8 steps** (target repo, target session, worktree, pointer activation, dependencies, session command, open tab, track): the **existence-guarded pointer-activation** sits at **step 4**, between `wt create` (step 3) and opening the agent tab (step 7) (5xnx). The step runs `fab change switch <change>` **in the just-created worktree's directory** — writing *that worktree's own* `.fab-status.yaml` so the worktree is self-describing after the pipeline completes (a bare `fab`/`/fab-*` run later resolves the change without naming it). It is **guarded** on `fab resolve --folder <change>` succeeding (the skill's existing pure-query verb; non-zero exit cleanly signals "no such change"), so the switch fires only when the change folder already exists, and it is **fail-soft** — a `fab change switch` failure logs one line and the spawn continues opening the agent tab (the transient `<change>` override on the embedded pipeline command still resolves the pipeline; activation is an ergonomic enhancement, not a correctness prerequisite). The activation carries **zero cross-tab collision risk**: each operator worktree is a dedicated, single-change checkout that owns its own per-worktree `.fab-status.yaml`, so the switch touches only that worktree's pointer — never the operator's own checkout or any other worktree. The **raw-text and backlog/Linear forms skip the switch** — the change folder doesn't exist yet at spawn time, so the existence guard fails and no switch is attempted; `/fab-new` creates **and** activates the change inside the spawned agent (activation at fab-new Step 10). This makes the spawn path the **second consumer-side activation stance** alongside §3 Pre-Send Validation (which already sends `/fab-switch <change>` first when targeting an existing pane whose active change is wrong) — the spawn path is consistent with that established stance. The `&&`-no-chaining prohibition is unchanged — the fix is a separate spawn-sequence step, not a chained slash command.

**Dependency satisfied.** A `depends_on` entry is satisfied when the dependency **item is `done`** — for a pane item, its built-in predicate fired (`review-pr` done/skipped with a null `stop_stage`, or at/past its `stop_stage` — requiring an observed `scope.change`) — **and**, for a same-repo dependency with a null `stop_stage`, its PR exists (`gh pr view <dep-branch> --json url` succeeds, so the branch is pushed and stable). Tracking, a `branch_map` entry, or a minted branch is not satisfaction — all exist from the moment the dep's agent spawns. An unsatisfied dependency holds the item (`state: held`, re-derived by the binary each tick), re-checked each tick, logging `"{change}: waiting on dependency {dep} ({dep.repo}) to complete."`; when the last dep completes, the item flips to `pending` and the tick's step 2 spawns it.

**Two-tier dependency resolution.** Each `depends_on` entry is classified by comparing the dependency's `repo` (from its item's `scope.repo`, or its `branch_map` `{ branch, repo }` pair after the item is gone) against this change's `repo`:

- **Same-repo dependency** → **cherry-pick**: fetch + resolve the base (step 0 below), then `git cherry-pick --no-commit origin/{default_branch}..<dep-branch>` into the worktree.
- **Cross-repo dependency** → **ordering-only barrier**: wait until the dependency is satisfied (above), then spawn. **No code is merged.**

> **REQUIRED caveat — cross-repo deps give the dependent agent NO code.** A cross-repo `depends_on` is a pure *sequencing* constraint; the dependent worktree receives nothing from the dependency. This is correct only for **logical** dependencies ("don't start the frontend change until the API change merges"), never for **code-level** ones. Cross-repo branches share no common default-branch base to cherry-pick across, so there is no sound way to make the dependency's code available. For code sharing across repos, the dependency must merge and be consumed as a normal upstream artifact (package, vendored copy), outside the operator's scope.

**Step-0 fetch + default-branch resolution (g8st).** Same-repo resolution begins, in the target worktree, by refreshing the remote and resolving the repo's **actual** default branch — never a hardcoded `origin/main`:

```bash
git fetch origin
default_branch=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|^origin/||')
[ -n "$default_branch" ] || default_branch=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name 2>/dev/null)
# Literal fallback when both commands fail: probe the just-fetched refs — main when origin/main exists, else master
[ -n "$default_branch" ] || default_branch=$(git rev-parse --verify -q origin/main >/dev/null && echo main || echo master)
```

`origin/{default_branch}` is the cherry-pick base (and the `merge-auto` rebase target — see Queues below). Fetching first prevents a stale base even on correctly-defaulted repos; resolving the name makes queues usable on repos whose default branch isn't `main`. The resolution chain matches `/git-pr`'s (see [change-lifecycle.md](/pipeline/change-lifecycle.md) § Git Integration); the operator's literal fallback probes the just-fetched refs rather than assuming, because the fetch has already run.

Ancestor-pruning (`git merge-base --is-ancestor`) is scoped to the **same-repo subset** of the dependency set — it is meaningless across repos with no shared history. The `origin/{default_branch}..<dep-branch>` transitive-closure argument (only direct/leaf deps need cherry-picking) holds only within a repo; cross-repo deps carry no such transitive content.

**Repo-spanning queues.** A queue **may span repos** with mixed dependency semantics: implicit chaining and explicit `depends_on` cherry-pick **within** a repo and **degrade to an ordering-only barrier across** repo boundaries. Ordered merge tracks **per-repo PR sequences** — within each repo, base-first in dependency order; across repos, cross-repo barriers are honored (a cross-repo dependent's PR merges only after its barrier dependency reaches its target repo's main). The queue-completion summary annotates each PR with its repo and suggests a per-repo merge order.

**CI-failure = halt-dependents-only.** During ordered merge, a CI failure halts the failing repo's merge sub-sequence AND any repo whose queued items carry a cross-repo `depends_on` into the failed chain — **transitively** over the cross-repo `depends_on` graph (a repo halts if any of its queued items depends, directly or via another already-halted item, on a PR in the failed chain). **Truly independent repos' sub-sequences continue merging.** In an armed sequence, every halt path first disarms the remaining armed PRs (auto-merge choreography rule 5 — halt-dependents-only assumes unstarted merges stay unstarted, which armed auto-merge violates). The operator isolates the blast radius to the failure's dependency cone, reports which sub-sequences halted vs. completed, and escalates the failure to the user.

**The clock — the rk cron operator-tick entry (sole cadence, every provider)**: Cadence is **not owned by the skill** — it is run-kit substrate the skill documents and verifies, exactly like `@rk_pane_agent_state`. `rk operator` idempotently seeds a pinned operator-tick cron entry (one per tmux server); its steady-state shape, in reference summary — `schedule` and `deliver` are the values fab's schedule reconcile converges the live entry to on the first `track` mutation or tick, the remaining fields are rk's own — is `schedule: { kind: backoff, min: 3m, max: 24m }`, `wake_on: { event: agent-state-change, scope: server, debounce: 60s }`, `target: { kind: role, role: operator }`, `payload: "operator tick"`, `deliver: skip-if-busy`, `if_absent: respawn`, `respawn: ["rk","operator","-L","{server}"]` (caller-supplied argv; `{server}` substituted by rk at fire time), `pinned: true` — schema and semantics are owned by run-kit's operator-cron spec, the entry's design authority. `rk operator` seeds the entry idempotently; `rk cron add`/`rm` stay the user's. **Quiescence is an explicit mute the `track` verbs issue** — rk never infers operator intent from fab's private state file: every `fab operator track` mutation and `tick-start --diff` evaluates the **tracked predicate** before and after, and on a flip issues `rk cron mute <id>` (the tracked set emptied) / `rk cron mute <id> --off` (something tracked — clears both a mute and a lease). **Tracked** means: **any item whose state is not `done`** (a list holding only `done` items counts as untracked) — an open merge sequence therefore keeps ticks coming by construction, since its `github-pr` items are not done. The flip is edge-triggered inside the mutation helper (tracked-ness compared before and after; the rk call fires only on a flip, after the save), fail-silent, `exec.LookPath`-gated, argv-only, and 5s-bounded; the entry id is resolved per call from `rk cron list --json` — the rows are read from the bare array or from the `result` array of run-kit's `{"ok":true,"result":…}` envelope (either shape; an `{"ok":false,…}` envelope counts as unparseable), the row whose `target` is `"role:operator"` (`name == "operator tick"` as tiebreak), with zero/ambiguous/unparseable output a silent no-op. **The schedule itself is derived from the tracked set** (the Binary Derives the Cron Schedule design decision below): after any successful save the verb runs the schedule reconcile — only `pane`/`none` items ⇒ `--backoff --min 3m --max 24m`; any `shell`/`agent` item ⇒ `--idle-every <min(check_every)>` (or `--every` when the operator pane's `rk mux panes --json` row reports a null `agent_state` — no idle epoch); the deliver policy is `--deliver skip-if-busy` on every branch and on the bounded override — only the schedule kind varies with the tracked set — compared against the live entry's structured `schedule`/`deliver` fields, issuing exactly one `rk cron edit` only when they differ. A muted or leased entry is still edited (the new schedule takes effect when the lease expires). A bounded user override rides `fab operator track clock --every|--idle-every <dur> --for <dur>` — it writes a top-level `clock_override` with an expiry, applied instead of the derived value until `until` passes, then reverted; an override without `--for` is rejected, and `track clock --off` clears it early. Two lightweight reconciles close the drift window a silently failed flip leaves: `tick-start --diff` mutes the entry when the post-tick state is untracked (skipping an already-muted entry), and §2 Init unmutes (`rk cron mute <id> --off`) when the entry is `muted` while tracked work exists. The lease — `rk cron mute <id> --for <dur>` — is a bounded snooze the skill MAY use for a user-requested quiet window; it auto-expires, nothing renews it, and it is not the quiescence mechanism. **Tick payload**: a tick's text is the **bare text `operator tick`, never `/fab-operator` or any slash command** (a slash command macro-expands its ~21k-token source into every firing, exhausting the context window in ~10 ticks); the rule binds the entry's `payload` and any manually typed tick (4q3l, re-grounded). **Ready line (§2 Init)**: the §2 rk Gate has already proven `rk cron list --json` works, so step 4 reads it for the row whose `target` is `role:operator` — the operator-tick entry — and its `schedule_summary`, `deliver`, `muted`, and `muted_until` fields (`muted` is the effective state — an indefinite mute or a live lease; `muted_until`, unix seconds, is present only while a lease is live), unmuting a `muted` entry while `fab operator track list` shows tracked work. A missing operator-tick entry after the gate passed STOPs: `Error: no operator-tick cron entry on this server — run rk operator to seed it`. Step 5 renders exactly one ready-line template for the agent to copy, never compose — `Operator ready. Clock: rk cron "operator tick" · {schedule_summary} · {deliver}[ · muted[ until HH:MM]]` — copying the JSON values verbatim (` · muted` appended when `muted` is true; ` until HH:MM` in local time appended when `muted_until` is present). **Per-tick clock read (tick step 1)**: each tick re-reads `rk cron list --json` for the operator-tick entry and renders its `schedule_summary` and `deliver` on the frame — cadence is never carried from a previous tick or composed from memory, so a schedule the binary re-derived (or a user `rk cron edit`) shows on the next frame; no lifecycle to manage — the `track` verbs mute/unmute and reconcile, rk evaluates the schedule. A queue has no cadence of its own — a driving chain of items rides the same cron-delivered ticks. **Compaction survival**: the agent cannot `/clear` itself; cron-delivered ticks keep arriving regardless of session health, so when a tick arrives and the Tick Behavior procedure is no longer in context (harness auto-compaction, a session resumed from a summary, or a user `/clear`) — a trigger guaranteed to fire eventually — it runs `/fab-operator` exactly once (reload + §2 Init), treats that tick as consumed (level-triggered deltas re-emit on the next `tick-start --diff`), and resumes bare `operator tick` firings — never by putting `/fab-operator` into a tick payload (§4 Post-Compaction Reload; the matching §1 principle is "Survive compaction").

**Tick snapshot is server-wide.** The tick's snapshot runs inside the binary: `fab operator tick-start --diff` enumerates panes server-wide (the same discovery+resolve row collection behind `fab pane map`), keyed off the current socket, so the operator sees tracked agents in **every** session on its server, not just its own. Each snapshot row carries the `repo` field (the agent's absolute main-worktree root, `null` when the pane is not in a git repo — see [pane-commands.md](/runtime/pane-commands.md)) and the resolved change ID; the emitted `items:` block (or, on a `--quiet` quiet tick, the `fleet_summary:` count block — the quiet-tick design decision below) orders rows first by kind, then by `scope.repo`, then by id, and a pane row's `pr_url` field surfaces the change's PR once it ships (r7ju). The frame's *presentation* (one markdown table + emoji health) is defined by the **Frame rendering** model below.

**One-table status frame.** The status frame is a header line plus **one table over all items** — `| | ID | Kind | State | Checked | Next |` — with no per-repo sections: the repo basename rides the Kind cell (`pane · foo`), the State cell carries the health emoji plus per-kind text (pane items: agent state + stage — a pane item with no observed change suffixes `· no change` (`🟢 active · no change`); with a change, the stage text is prefixed by the change id when it differs from the item id (`🟢 4a8m · apply`); probed items: the declared fields' current values; linear/slack: `{new} new · {seen} seen`; notes: the text's first line), the Checked cell carries `live` for pane items and the age since `checked_at` for probed items (` ⚠` past `check_every`, ` 🔴` past 2×) so staleness is visible, and the Next cell carries the armed action (`▶` marks an item with a `then` or a `pending` pane item; `⏸` a `held` item naming its dep). Example (fenced here only to display the source):

```
🛰️ **Operator** · 16:36 · tick #48 · **7 tracked** · idle-every 2m · skip-if-busy

| | ID | Kind | State | Checked | Next |
|:--:|---|---|---|---|---|
| | `r3m7` | pane · foo | 🟢 apply → review | live | |
| ▶ | `k8ds` | pane · bar | 🟡 waiting · review | live | spawn ef56 |
| ⏸ | `ef56` | pane · bar | held: k8ds | — | spawn after k8ds |
| ▶ | `pr-913` | github-pr · run-kit | ✅ MERGED | 12s | spawn n34 |
| ▶ | `pr-914` | github-pr · run-kit | OPEN · armed | 2m ⚠ | arm next |
| | `linear-bugs` | linear · foo | 0 new · 2 seen | 11m 🔴 | |
| | `n1` | note | Phase 2 of 4 — hexokit after #913 | 3h | |
```

**Frame rendering (markdown-native).** The frame is emitted as an assistant message and rendered by the agent harness as GitHub-flavored markdown — **ANSI escapes do not survive this path** (stripped as literal text *and* as real ESC bytes; empirically verified), and markdown **headings** (`#`/`##`/`###`) render as literal text and are unusable. The only channels that render are tables, **emoji**, **bold**, *italic*, `code spans`, and links. So the frame uses: a header line `🛰️ **Operator** · {HH:MM} · tick #{N} · **{tracked} tracked** · {schedule_summary} · {deliver}` and the single items table — the full frame, rendered when the tick document carries `items:`. On a quiet tick (the document carries `fleet_summary:` instead) the frame is one line — `🛰️ **Operator** · {HH:MM} · tick #{N} · **{tracked} tracked** · {schedule_summary} · {deliver} · no change` (with ` · {W} waiting` appended only when `waiting > 0`; the cadence cells come from the per-tick `rk cron list --json` read). Emoji are the sole color channel — health is 🟢 active/healthy · 🟡 waiting/idle (the `@rk_pane_agent_state` `waiting` state joins plain idle here (ioku)) · 🔴 stuck/errored (or past 2× `check_every` in the Checked cell) · ✅ complete · ⚪ paused (geometric glyphs like `●◌✗` render monochrome and are not used). Rows are ordered kind → repo → id; a removed item renders once with ✅ on the tick it is acked, then vanishes; an `agent_exited` row renders `⏏ shell` in its State cell so it never reads as a live agent. The 🛰️ emoji and **bold** are the prominence/landmark anchors that headings would otherwise provide. Degrades cleanly: strip emoji and the State text still names the state; PR URLs are plain text regardless. The authoritative column spec, frame example, and health-emoji tables live in `fab-operator.md` §4's `### Status Frame Format` subsection (tick step 1 renders the frame from `items:`/`fleet_summary:`), stated as one rule: emit bare markdown — no code fence, no headings, no ANSI; channels are tables, emoji, bold, italic, code spans, plain URLs, plus the distinct agent-critical runtime no-fence rule. Nothing renders between ticks — the frame (plus its italic action footnote) is the only per-tick output. (The "Why emoji + table, not ANSI" design history lives in the Status Frame design decision below.)

**Monitoring tick** (on each cron-delivered `operator tick` or "any updates?"): the tick opens with `fab operator tick-start --diff --quiet` (a user status request drops `--quiet`), whose binary-internal snapshot, probe runs, and predicate evaluations deliver the detections below as `deltas:` (the pane-map + probe + state-read + baseline-diff mechanics live in the binary; `candidates:` carries the sweep population, `needs_check:` the due agent-probed items, and `items:` or `fleet_summary:` the frame data) — the tick then runs four steps: snapshot, act on deltas (before any answers), answer waiting agents, ack:

1. **Stage advance / review failure** — reported from the `stage_advance` and `review_fail` deltas (consumed-on-read against the binary-owned baseline; the baseline write rides the same `--diff` mutation; review→apply is the rework reset and emits `review_fail`).
2. **Completion** — reported from the `done` deltas (level-triggered, re-emitted every tick until `track rm` acks). For a pane item the built-in predicate applies only when `scope.change` is non-null: a display-state check at a stage (`review-pr` done/skipped when `stop_stage` is null — hydrate and ship are mid-pipeline and never complete an item by themselves — or past/at `stop_stage`); a pane item with no observed change is never done on its own (it leaves the list only via `track rm` or a `then`). For a probed item it is its `done_when`. A spawn that deliberately parks earlier (a `/fab-ff` run stops after hydrate) is tracked with `--stop-stage hydrate`, otherwise it never completes. The delta carries the item's `then` verbatim — the operator runs that prose (if any), reports, and removes the item (`track rm` is the ack that stops the re-emission; pane items also get the window done-marks above).
3. **Field changes, staleness, probe errors** — `changed` (consumed-on-read; carries one `{from, to}` entry per differing declared field — including `change` appearing or switching on a pane item, which is how a raw-text spawn's change shows up), `stale` (an agent-probed item past 2× `check_every` — run its `probe.instruction` now and record via `track observe`), `probe_error` (level-triggered; the third consecutive failure sets `paused: true` and the item stops being probed until `track update --resume`; an item paused at the cap renders 🔴 and asks the user).
4. **Pane death / pane mismatch / agent exited** — reported from the `pane_death` (pane absent from the snapshot), `pane_mismatch` (recycled pane only — the recorded `pane_pid` fingerprint is non-null and differs from the pane's current shell pid; tmux recycles `%N` pane IDs across server restarts while the socket-keyed state file survives; a null fingerprint or an unreadable current pid joins on the pane id alone), and `agent_exited` (the item's pane is present and fingerprint-matched but no live agent remains) deltas, all level-triggered and evaluated in that precedence order per item. `agent_exited` is decided by the pane row's `has_agent` tri-state from `rk mux panes --json`: `false` ⇒ exited, `true` ⇒ alive, and **`null`** (an uninstrumented pane — the operator's own pane reports `null`) falls back to the lazy process-tree walk rooted at the pane's `#{pane_pid}` (shell foreground command basename-matched against `sh bash zsh fish dash ksh tcsh csh nu` first; the delta carries `command`). On Linux, a wrapped interactive spawn keeps the non-interactive wrapper shell as the foreground process-group leader for the agent's entire life (verified live 2026-09-02), so `#{pane_current_command}` alone is a universal false-exit signal for wrapped live agents rather than evidence that the agent is gone. Report and remove a dead, mismatched, or exited item; a mismatched or exited pane is never diffed, swept, or framed as the old agent — an exited pane's stale agent state still reads `idle`, so excluding it from `candidates:` keeps the sweep from typing into a bare shell prompt. Its `items:` row falls back to baseline identity fields with null observed fields (`agent_state: null`), counting under `unknown` in `fleet_summary:`, and its frame row renders the baseline identity with the `⏏ shell` marker in place of a live stage. `pane_death` stays load-bearing for unwrapped dispatch pane workers and any pane killed outright; an exited wrapped interactive spawn surfaces as `agent_exited` while its fallback shell keeps the pane alive.
5. **Pending spawns** — a `pending` pane item (deps done, no pane yet) runs the §6 spawn sequence this tick, the confidence gate first.
6. **Auto-nudge** — per-tick population is the `--diff` `candidates:` block: **`waiting` agents first (primary), then `idle` agents as the fallback** (ioku): a `waiting` agent is event-visibly blocked on a human, so it is the primary question-detection candidate; `idle` agents are still swept so a plain-idle agent sitting on a prompt an uninstrumented harness didn't flip to `waiting` is not missed. For each such pane, run `rk mux capture <pane> --lines 40 --classify --json` and feed a non-`none` class through the answer model (see below), delivered via `rk mux send --answer`. `active`/unknown (`—`) panes are **usable, not swept every tick** — classify capture remains applicable to them (uninstrumented, or not yet flipped to `waiting`), but the per-tick sweep is `waiting`+`idle` only (unknown-state and `active` panes are excluded from `candidates:` by construction). (No post-intake `/git-branch` send — fab-new Step 11 creates or renames the branch inline (w7dp). Only a detected branch/change mismatch warrants a `/git-branch` send, per pre-send validation.)
7. **Stuck detection** — for `idle` agents whose classify capture reports `none`, check the `idle_duration` the diff blocks carry (derived from the epoch-based `@rk_pane_agent_state` idle duration). If idle at a non-terminal stage for >15m, report as potentially stuck. Advisory only — a `waiting` agent (blocked on a human) is not stuck.

After processing all items: when the tracked list holds no not-done item, report "All tracked items complete." Quiescence is not the tick's to manage — the `track` verbs mute the entry when the last not-done item leaves and unmute it when the first arrives (the clock block above); a tick that still arrives on an untracked state is the drift signal `tick-start --diff`'s reconcile mutes on.

**Linear and Slack items (`seen` dedupe)**: agent-probed standing queries are never run by the binary — the tick lists due ones under `needs_check:`, the operator runs the item's `probe.instruction` (the named MCP call), and records the result via `fab operator track observe <id> --json …` with `--seen <item-id>` for each handled source id. New-item detection deduplicates spawns against the item's **`seen` list** (binary-capped at 200 entries, oldest pruned): a source item that already spawned a change stays in `seen` after that change completes and MUST NOT be respawned (a respawn loop is the failure this list exists to prevent). A failed check is recorded via `track observe <id> --error "<msg>"`, which increments `failures`; the third consecutive failure auto-pauses the item.

#### Auto-Nudge

The operator acts as a proxy for the user on routine operational questions.

**Question detection** — detection is a per-pane classification over the tick's `candidates:` block from `fab operator tick-start --diff` (the `waiting`-primary + `idle`-fallback population above; a `waiting` state is itself the strongest question signal, and the classify capture confirms *what* the prompt is): for each candidate pane, run `rk mux capture <pane> --lines 40 --classify --json`, which reports a pending-prompt **class** — yes/no, numbered menu, colon prompt, open question, press-key — or `none` with a reason, plus the matched line. The classification contract is tool-owned (`rk skill`); the capture/state-read *mechanics* underneath (including the uninstrumented-pane state-writer caveat that makes capture the universal fallback) belong to [agent-primitives.md](/runtime/agent-primitives.md) § Peek. Claude Code permission/tool-approval prompts are **not** mechanized as their own class — in practice covered by the yes/no and numbered-menu classes; novel prompt shapes remain operator judgment via plain capture. The classify report is **detection input only, never a license to send blind** — the answer model below, the §3 pre-send gate, and the re-capture-before-send guard remain LLM-side and unchanged. On a non-`none` class the operator proceeds to the answer model (bottom-most, most recent prompt); `none` → normal idle behavior (stuck detection applies).

**Answer model** — most detected questions are auto-answered. Rule 4 (numbered menus) classifies the prompt before answering: Routine prompts auto-answer, Strategic prompts escalate. Rule 6 escalates when the operator cannot determine what keystrokes to send. Evaluate in order:

1. Binary yes/no or confirmation prompt → `y`
2. `[Y/n]` or `[y/N]` prompt → `y`
3. Claude Code permission/approval prompt → `y`
4. Numbered menu or multi-choice → classify as **Routine** or **Strategic** using LLM judgment over the terminal capture, weighing four signals: option text length, semantic distinctness of options, surrounding agent context, and reversibility of the choice. No hardcoded keyword list, no agent-side sentinel/marker protocol. **Routine** (tool/permission prompts, binary-framed menus, synonymous-option menus) → `1` (first/default option). **Strategic** (multi-option choices representing materially different directions — scope, PR split, pipeline shape, commit organization, spec/approach) → **non-blocking handling** (see "Non-Blocking Strategic Handling" below) (mmmt). A Strategic classification **never** ends the operator's turn. On classification uncertainty, treat as Strategic (asymmetric cost: false-negative strategic commits the queue to an unchosen direction; false-positive strategic costs at most a notification — and, if auto-picked, a reversal at PR review).
5. Open-ended question where a concrete answer is determinable from visible terminal context → send that answer
6. Question where the operator cannot determine what keystrokes to send → escalate (left open). Rule-6 escalations are **excluded** from auto-pick and from the 30m idle auto-default — sending a guess would emit nonsense into the pane.

**Non-Blocking Strategic Handling (mmmt)**: A Strategic classification MUST NOT block the tick. The operator handles the prompt out-of-band within the current tick and proceeds to the next tracked item in the **same** tick — one strategic question on one change does not freeze the queue. Two branches:

- **Strategic + defensible recommendation → auto-pick-and-notify**: the operator picks its recommended option (LLM judgment over the capture, the same four signals rule 4 lists), sends it (after the Re-Capture-Before-Send guard), fires a notification (Notification Send below), and keeps ticking. The PR review stage is the reversal point (§1 "PR review is the safety net").
- **Strategic + no defensible default → leave open and notify**: the operator leaves the prompt open for the user, fires a notification, and keeps ticking. The 30m Idle Auto-Default remains the backstop for left-open prompts.

In both branches the operator continues ticking; the user answers asynchronously (responding to the notification's guidance or typing into the pane) and the operator picks up the resolution on a later tick via its normal re-capture/re-detection — no new pickup mechanism is added.

**Notification Send (mmmt)**: a single out-of-band shell send run when the operator auto-picks or leaves open a Strategic prompt. The channel is **`rk notify`** — a run-kit external contract (run-kit Web Push) that is **tool-owned**: the `notify` signature and its guarantees live in `rk skill`, read at use-time, not pinned to a version here. The fab-owned usage (message/title template) lives in `_cli-external.md` § rk (HexoKit): `rk notify "{change}: {summary} ({repo})" --title "Operator: strategic question"`. `rk notify` delivers a real background mobile/desktop Web Push and is fail-silent by contract — a notification that cannot be delivered MUST NOT crash or stall the operator; it logs one line and keeps ticking. Mirrors the `_preamble.md` § HexoKit (rk) Reference "fail silently" discipline.

No cooldown or retry limit — each question is evaluated independently. Worktree isolation and human PR merge provide the safety gate for auto-answered prompts.

**Idle Auto-Default on left-open Strategic prompts (scoped to left-open) (mmmt)**: This is the watchdog for a **left-open** Strategic prompt — the no-defensible-default branch of Non-Blocking Strategic Handling above. (Auto-picked Strategic prompts are already resolved, so the watchdog has nothing to act on for them.) When rule 4 leaves a prompt open as Strategic, the auto-default fires on the first tick whose `candidates:` row for that pane shows a `state_duration` of **30 minutes or more** — the LLM runs no timers: run-kit's agent-state epoch already resets on any activity in the pane, so the candidate row's duration is the idle clock and the check rides the normal tick (it never blocks one). The operator then auto-answers and logs using the distinct `auto-defaulted` format (see Logging below).

- **Threshold**: 30 minutes, hardcoded — unchanged (mmmt). No operator-state-file field, no per-change override, no environment variable exposes this value.
- **Idle clock**: `candidates:` rows carry `state_duration` — rk's `agent_state_duration` verbatim for `waiting` and `idle` panes alike (`idle_duration` keeps its idle-only meaning) — and rk's agent-state epoch resets on any activity in the pane (new agent output, user keystrokes, prompt redraw), so the row's duration is the idle clock with no LLM-side timer or polling infrastructure.
- **Answer selection** (priority order): (1) if the prompt visibly states a default (e.g., `(default: 2)`, `Press enter for 2`, `[2]`), send that stated default; (2) otherwise, send `1`. This matches rule 4's existing "first/default" semantics for routine menus.
- **Scope (hard exclusion)**: applies ONLY to **left-open** rule 4 Strategic prompts. It does NOT apply to auto-picked Strategic prompts (already resolved) and MUST NOT apply to rule 6 ("cannot determine keystrokes") escalations — the operator does not know what the correct keystrokes are, so sending `1` or the stated default would emit nonsense into the pane. Rule-6 escalations remain open pending user action regardless of idle duration.

**Re-capture before send**: Before delivering an auto-answer via `rk mux send <pane> "<text>" --answer` (rk's built-in delivery verification replaces the manual probe on that path, and a probe failure surfaces as staged text + stderr warning + exit 1: re-capture and decide, never blind-resend; key-name answers — bare Enter, arrows, `C-c` — ride `rk mux send --key`), the operator runs the pre-send gate ([agent-primitives.md](/runtime/agent-primitives.md) § Pre-send validation) and MUST re-capture the terminal (a fresh 20-line capture via `rk mux capture`, just-in-time — the classify capture that detected the prompt is older, so the guard matters more, not less). The classify report is detection input only — it never replaces the pre-send gate or this re-capture-before-send guard. If output changed since initial capture, abort — the agent is not waiting anymore. Eliminates the race condition between detection and send.

**Logging** (five answer-line shapes + a fail-silent notify line) (mmmt):
- Auto-answer (routine): `"{change}: auto-answered '{summary}' → {answer}"`
- Auto-pick strategic (defensible recommendation): `"{change}: auto-picked strategic '{summary}' → {answer} · notified"`
- Left-open strategic (no defensible default): `"{change}: strategic '{summary}' left open · notified. Please respond."`
- Escalation (rule 6 — cannot determine keystrokes): `"{change}: can't determine answer for '{summary}'. Please respond."`
- Auto-default after 30m idle on a left-open strategic prompt (distinct from `auto-answered` for grep-based after-action review): `"{change}: auto-defaulted after 30m idle: '{summary}' → {answer}"`
- Notification send failure (fail-silent — logged, ticking continues): `"{change}: notify failed ({channel}). Continuing."`

#### Coordination Patterns

The operator understands the full fab pipeline and command vocabulary, and **infers the right action from current state rather than following named playbooks**. There is no playbook catalog: the skill states the pipeline reference (`intake → apply → review → hydrate → ship → review-pr`), the setup/pipeline/maintenance command vocabulary, the spawn sequence, dependency resolution, and queues — and the operator composes those against whatever the tick snapshot shows. A queue is the one named composite, because it is a chain of tracked items with its own merge-mode choreography (below).

#### Queues

> A queue may span repos with mixed dependency semantics, ordered merge tracks per-repo PR sequences, and CI-failure halts dependents only (not the whole sequence) — see "Multi-Repo Coordination" above for the repo-spanning behavior. The mechanics below describe the per-queue loop.

A queue drives N changes through the full pipeline — spawning agents, monitoring progress, and collecting PRs for review — and **is** its tracked items: the user's queue request becomes N `fab operator track add --kind pane` calls, chained by `depends_on` (each change after the first names its nearest same-repo predecessor; a cross-repo entry chains to its immediate predecessor), with `--mode` on the first call. There is no queue state beyond the items themselves — skipping an entry is `track rm <id>`, pausing the unspawned entries is `track update <id> --pause`; a restarted operator re-orients from `fab operator track list` and resumes. Three flat merge modes, resolved by the ladder **explicit user instruction / `--mode` flag > config `autopilot.merge_mode` (the key keeps its historical name) > built-in `cherry-pick-ladder`** — the operator resolves a mode-unnamed queue request silently (no "which merge topology?" round-trip); the binary stamps the resolved mode into each chained item's `scope.merge_mode` and prints `mode: <name> (<source>)` on the first `track add`, which is how the operator learns the resolved mode and its source, stated inside the existing upfront confirmation so the user vetoes in the same breath. Mode is fixed for the queue's lifetime (changing it means removing the chain and re-adding it). The operator pauses and asks ONLY on two misfits (resolved `merge-auto` vs same-repo `depends_on` entries, which that mode's disabled implicit chaining contradicts; the user's own message conflicting with the resolved mode). When it does ask, the question carries the at-a-glance glyphs (`▂▄▆` cherry-pick-ladder · `░▒▓█` merge-auto · `▄▀` stacked-prs), the three compact box diagrams, and a one-line tradeoff per mode; the skill's no-diagrams caveat is **status-frame-only** — a mode question is an ordinary conversational message where the fenced diagrams render fine. In the default **`cherry-pick-ladder`**: all queued changes build on each other via implicit `depends_on` chaining, PRs are created but NOT merged until the user explicitly requests merging. Confirm the queue upfront before starting. Default confirmation: "Confirm upfront (creates PRs — merge after review)."

**Queue ordering**: User-provided (exact order given), confidence-based (descending score), or hybrid (partial user constraints, confidence tiebreaker). User-provided ordering implies implicit chaining — each queued change after the first gets `depends_on: [<nearest-same-repo-predecessor>]`: the closest earlier queue entry in the **same repo** (cherry-picked); when no earlier entry shares the repo, the immediately previous entry as an ordering-only barrier (cross-repo → no code). (w7dp — strict queue-previous would silently break same-repo stacking whenever a cross-repo entry sits in between, since a cross-repo dep contributes no code.)

**Per-change loop (cherry-pick-ladder, default)**: **Gate check confidence BEFORE anything spawns** (below the gate → flag to user; no worktree, no tab, no dispatch) → spawn worktree (`--reuse` for respawns; chaining per the nearest-same-repo rule above) → resolve dependencies (cherry-pick same-repo `depends_on` entries into the worktree; cross-repo = ordering-only barrier) → open the agent tab with the pipeline command **embedded at spawn** (§6 step 7 — `/fab-fff <change>`; the loop has no separate Dispatch item, so the command reaches the pane exactly once (w7dp)) → monitor → when the current change is satisfied (its `done` delta observed and PR URL collected), collect the PR URL — the `{ branch, repo }` pair is already in `branch_map`, recorded by `track add` at spawn → the next chained item flips `held` → `pending` on its own and the tick's step 2 spawns it (its command likewise embedded at spawn) → report `"ab12: PR ready. 1 of 3 complete. Starting cd34."`.

**Queue completion summary**: When all changes in a `cherry-pick-ladder` or `stacked-prs` queue complete, the operator displays a summary with all PR links and suggested merge order (base-first). The user can merge individually, or ask the operator to merge all in dependency order. The CI gate between ordered merges is **mode-split**: in `cherry-pick-ladder` (and for `merge-auto`'s per-PR merges) merge-all runs the **auto-merge choreography** — the operator arms each PR with GitHub auto-merge (`gh pr merge --auto --squash`; the method flag is explicit and REQUIRED — flagless `--auto` may prompt or take the repo default, unsafe unattended; a user-directed method maps to `--merge`/`--rebase`) and verifies the merge on later ticks, a passive tick check instead of a foreground wait; in `stacked-prs`, or when arming is unavailable, the operator merges each PR itself and foreground-waits for CI before proceeding. The choreography's five MUST rules (skill §6 Auto-Merge Choreography): (1) **sequential arming** — at most one armed PR per repo-sequence, arm PR_n only after PR_{n-1}'s merge is verified (its item's `done` delta), never arm a PR whose base is another PR's branch; (2) **arming-failure shapes** — draft PR → `gh pr ready` first (fab's `/git-pr` creates drafts, so this is every queued PR), "already clean" rejection (no required checks) → merge directly, auto-merge disabled on the repo → the foreground CI-wait choreography; (3) **stall rule** — the tick's mechanical probe of a still-unmerged armed PR feeds two inspections: a failed required check (`gh pr checks`) is the CI failure (disarm per rule 5, halt-dependents-only), and `unchanged ≥ 3` on the item (the binary-owned consecutive-no-delta counter) polls `gh pr view --json mergeable` (`mergeable` is the field — `mergeableState` does not exist there), `CONFLICTING` → disarm and escalate; both shapes are event-less, so the tick's probe IS the poll; (4) **the sequence is a chain of `github-pr` items** — starting a merge sequence adds one item per PR (`track add pr-<n> --kind github-pr --scope '{"repo":…,"pr":n}' --then "arm next: gh pr merge --auto --squash <next>" --depends-on pr-<n-1>`), the first armed immediately; per tick a `done` delta on PR_n runs its `then` verbatim (arming PR_{n+1}), and the items ARE the sequence state — an armed PR outlives the operator, and a restarted operator re-orients from `track list` and resumes; (5) **disarm on halt** — a halt/escalation runs `gh pr merge --disable-auto` on the halted sequences' remaining armed PRs (the failing sub-sequence plus its transitive cross-repo dependent cone — independent sub-sequences keep theirs and continue); a user "stop" is global and disarms all. Arming rides the user's single merge-all confirmation (Destructive tier) — no per-PR re-confirmation.

**`merge-auto` mode**: Merge-as-you-go — arm each PR on completion via the auto-merge choreography (a one-PR sequence position; all five rules apply) instead of merging and foreground CI-waiting; the next change's spawn defers to the tick that verifies the merge (spawning earlier would start the next agent from a stale base), and only then `git fetch origin` and rebase the next change onto `origin/{default_branch}` (resolved per the step-0 chain in "Multi-Repo Coordination" above — never a hardcoded `origin/main`) (g8st). Implicit chaining is disabled in this mode — each change rebases onto `origin/{default_branch}` independently. Confirmation text changes to "Confirm upfront (merges PRs on completion)." Natural language equivalents: "merge as you go", "merge on complete", "merge each when done".

**`stacked-prs` mode**: `cherry-pick-ladder` merge timing (PRs created up front, merged only on explicit user request) with true stacked-PR topology for same-repo chains — the dependent's branch is created off its dependency's *branch* at the spawn sequence's worktree/branch step (no cherry-pick commit for same-repo deps), and after `/git-pr` creates the dependent's PR the operator retargets its base to the dependency's branch (`gh pr edit <pr> --base <dep-branch>`), so each PR diff shows only its own delta. Cross-repo dependencies stay ordering-only barriers. Confirmation text: "Confirm upfront (creates stacked PRs — merge after review)." Natural language equivalents: "stacked PRs", "stack the PRs". Merge-all adds two steps per merge: verify the dependent PR's base auto-retargeted onto the default branch after its base PR merged (retarget explicitly via `gh pr edit --base` when the merged branch was not deleted), and rebase the next chain branch onto the default branch after a squash merge to drop the already-merged dependency commits (`git rebase --onto origin/{default_branch} <merged-dep-branch> <next-branch>` + force-push) — a conflict in that rebase escalates, never skips.

**Failure matrix**:

| Failure | Action | Resume? |
|---------|--------|---------|
| Confidence below gate | Flag to user: run `/fab-fff` or skip | Wait for user input |
| Review fails (rework exhausted) | Flag, skip to next (`track rm`) | Yes |
| Cherry-pick conflict (cherry-pick-ladder) | Escalate, do not spawn | No — queue halts, wait for user input |
| Rebase conflict mid-queue (merge-auto) | Flag, skip to next | Yes |
| Rebase conflict during stacked-prs merge-all | Escalate — never skip | No — halt, wait for user input |
| Agent pane dies | 1 respawn attempt, then flag and skip | Yes |
| Stage timeout (>30 min same stage) | Flag regardless of retry state | Yes |
| Total timeout (>2 hr per change) | Flag for review | Yes |

**Interruptibility**: `"stop after current"` (finish active, halt queue), `"skip <change>"`, `"pause"` (stop new commands, running agents continue), `"resume"`. Interrupts acknowledged immediately and persisted through the `track` verbs — `track rm` on the not-yet-spawned items once the current change lands (or immediately to abandon the queue), `track rm <id>` to skip an entry, `track update <id> --pause` / `--resume` on the unspawned items.

**Resumability**: If the operator session restarts, state is reconstructable from `fab pane map --all-sessions` plus `fab operator track list`. Resume from the first not-done item.

#### Configuration

| Setting | Default | Override |
|---------|---------|----------|
| Stuck threshold | 15m | "flag agents stuck for more than {N} minutes" |
| Spawn target session | inferred (§6 step 2 majority rule; auto-set on each announced inference) | "spawn into session {name}" |

All settings are session-scoped — they reset when the operator session restarts. Cadence is not a session setting — the binary derives it from the tracked set and applies it via `rk cron edit` (the clock block above); a bounded user override is `fab operator track clock --for`. The strategic auto-default threshold stays hardcoded at 30m — there is deliberately **no** setting for it, and it is not an operator-state-file field.

#### Design Constraints

- **Binary-internal tick snapshot**: The per-tick observation primitive is the snapshot inside `fab operator tick-start --diff` (deltas + candidates + needs_check + items/fleet_summary blocks); under `--quiet` (the tick's default) a no-delta tick whose last full document (`last_full_at`) is less than 10 minutes old replaces `items:` with a five-count `fleet_summary:` (tracked/waiting/idle/active/unknown — `tracked` counts all not-done items, the four state counts cover pane items, invariant `tracked ≥ sum`), a non-empty `deltas:` or `needs_check:` and any tick whose `last_full_at` is at least 10 minutes old emit the full document (a missing or unparseable stamp counts as due), and `candidates:` is always emitted. `fab pane map --all-sessions` remains the on-demand/manual/startup-orientation surface
- **No persistent audit trail**: Per-answer logging is inline only — no file-backed log
- **Question classification is run-kit's**: Pending-prompt classification (the class taxonomy and guards) lives in run-kit's `rk mux capture --classify` and is tool-owned (`rk skill`); the operator keeps only the judgment steps (the answer model, the delivery guards). Claude Code permission/tool-approval detection is not its own class and stays covered by the yes/no and numbered-menu classes

#### Launcher

The operator is launched via `fab operator` — a `fab-go` subcommand (source: `src/go/fab/cmd/fab/operator.go`).

**rk delegation (checked first)** (rkop): when a **capable** run-kit is on PATH, bare `fab operator` hands the ENTIRE launch to `rk operator`, exec'ing it as a process replacement (`syscall.Exec` behind the injectable `execOperator` seam) with `--workers <v>` appended to argv iff the flag was supplied — the value rides **argv, not the `FAB_AGENT_WORKERS=` env prefix**, because rk composes the env for the agent it launches, and rk validates it (letters/digits/`_`/`-`, usage error exit 2; a behavior delta from the fallback's verbatim pass-through). Capability is probed side-effect-free by the injectable `rkOperatorPath` seam: `exec.LookPath("rk")` + `rk operator --help` exiting 0 with `--workers` in its output (the passed-through flag is the discriminant — the binary is probed, never the version string). rk then owns the whole launch: its own preconditions (`$TMUX`, fab on PATH — fab's own `$TMUX` check is skipped on this path), the role-marked singleton (`@rk_win_role=operator` wins over a merely-named window), launcher resolution via `fab agent operator --print`, and the provider-agnostic **typed** kickoff. A failed probe falls through **silently** to the built-in launcher below (cli-layering delegation rule 2 — absence degrades, never errors); a failure AFTER a passing probe (the exec syscall) is surfaced, never fallen back on. The operator **subcommand family is never delegated** — choreography stays in fab.

**Built-in launcher (the rk-absent fallback).** It creates a singleton tmux window named "operator" running the resolved **operator-role** session command (via `internal/agent` + `internal/spawn`) with the shell-quoted, receiver-rendered `fab-operator` prompt (see [agent-primitives.md](/runtime/agent-primitives.md) § Skill Prompt Rendering), wrapped in the interactive shell fallback (`spawn.WithShellFallback` applied after the `FAB_AGENT_WORKERS=` env prefix — see [agent-primitives.md](/runtime/agent-primitives.md) § Spawn composition), so the operator's tab survives its own agent's exit as a shell in the same cwd. The singleton check is an **exact, server-wide window-name match** (pw3k): it enumerates `tmux list-windows -a -F '#{window_id}\t#{window_name}'` and compares names exactly — never tmux target resolution, whose prefix/glob fallback would let a window like `operator-logs` falsely satisfy the check (and was session-scoped, missing an operator in another session on the same server). On exact match it selects the window by its server-global window ID (grammar-exempt) with a best-effort `switch-client` so a cross-session match moves the user's client; absence launches; a tmux enumeration error is surfaced distinctly (with the child's stderr), never conflated with "absent". Requires an active tmux session (`ERROR: not inside a tmux session` via the central RunE error path, exit 1).

**Launch preconditions (fallback path): neither a git repo nor a `fab/` project is required** (2sdj). The launcher matches the per-tmux-server, cross-repo singleton model — its natural launch point is a neutral parent directory (e.g. `~/code`) with no git and no `fab/` project. `runOperator` resolves two things gracefully:

- **Window cwd** (`tmux new-window -c <dir>`): try `gitRepoRoot()` (`git rev-parse --show-toplevel`) first, fall back to `os.Getwd()` on failure. Inside a repo the window opens in the repo root (today's behavior, unchanged); outside any repo it opens in the current directory. The old hard `cannot determine repo root` error is gone — it errors only when BOTH `gitRepoRoot()` and `os.Getwd()` fail (`cannot determine working directory`, a genuinely broken environment). The git repo root was only ever the `-c` argument — it is NOT part of the operator state-file path (still socket-keyed under `XDG_STATE_HOME`, unchanged — no migration).
- **Session command**: when a `fab/` project resolves (`resolve.FabRoot()` succeeds), read the **operator role's provider `interactive_command`** from that project's `fab/project/config.yaml` via the in-process `internal/agent` resolution (see the next paragraph). When `resolve.FabRoot()` fails — launched with no `fab/` project up the tree — fall back to the PROJECT-FREE cascade (`config.LoadNoProject()` — `env > system > built-in defaults`, so a machine-wide `~/.fab-kit/config.yaml` still governs an operator launched from a neutral directory) and then to `spawn.DefaultSpawnCommand` (the `{model}`/`{effort}` template `claude --permission-mode bypassPermissions -n "$(basename "$(pwd)")" --model {model} --effort {effort}`, profile-substituted by `spawn.WithProfile`) rather than erroring. A `fab/`-less launch reads the **upper tiers** — `FAB_*` env vars and the system `~/.fab-kit/config.yaml` — and only the project tier is absent, so a machine-wide `agent.session` DOES reach an operator launched from a neutral directory. The resolution chain itself — role → provider → `interactive_command` with the role's `{model, effort}` substituted — is the SHARED `roleSessionCommand` helper that `fab agent <role>` also walks, so the operator tab and `fab agent operator` can never compose different commands; only the missing-`interactive_command` POLICY differs (the operator falls back so it always launches, `fab agent` errors). A regression test asserts the two paths agree.

**Coordinating agent runs on the operator role.** The operator launches its agent on a deliberately-chosen profile rather than whatever the session command happened to specify. `runOperator` resolves the **operator** role **in-process** (`operatorProfile`/`operatorSpawnCommand`); `operator` is a first-class role in the fixed roster (`internal/agent`) and a **Tier-1 (session)** one, so which provider it lands on is the `agent.session` knob's call, and the launcher composes that provider's `interactive_command` with the resolved `{model, effort}` via `spawn.WithProfile(sessionCmd, model, effort)`. **`WithProfile` operates in one of two modes selected by placeholder presence** (see [_shared/configuration.md](/_shared/configuration.md) § `providers`): for a **templated** `interactive_command` (one carrying `{model}`/`{effort}` — the built-in claude default is templated, as is a non-Claude command) it **substitutes** the resolved profile into the placeholders (all-or-nothing, empty-value token-drop) — letting the operator launch a non-Claude coordinating agent whose flag grammar lives in the provider config; for a **non-templated** `interactive_command` (a plain-form user config) it instead **appends** ` --model`/` --effort` to the END (last-wins; duplicate `--effort` accepted by the claude CLI; each flag omitted when empty). Placing the default's placeholders last makes substitution byte-identical to that append. On **any** failure — an unresolvable fab project or empty resolution — it falls back to the in-process built-in operator default `agent.DefaultProfile(agent.RoleOperator)`. This keeps the operator a **non-orchestrator (non-pipeline) consumer** of the agent-role system. A `fab/`-less launch therefore composes a fully-defaulted command: `spawn.DefaultSpawnCommand` + the operator default `{model, effort}`.

`fab operator` is a parent command whose subcommand surface is:

- **`fab operator tick-start`** — Called at the start of each operator tick (step 1 of tick behavior). Derives the server-keyed operator state file path via `StatePath()` (no repo-root resolution), reads the file (absent file treated as empty), increments `tick_count` by 1, writes `last_tick_at` as an RFC3339 UTC timestamp, and writes back atomically preserving all other fields (the tracked list, branch_map, clock_override). Outputs `tick: N\nnow: HH:MM` to stdout using local time. Write failure → stderr error + exit 1. The flagless form is exactly this bookkeeping and nothing more. With **`--diff`** (the tick's normal form), the binary additionally probes the tracked items: it snapshots the fleet internally (the same discovery+resolve row collection `fab pane map` uses, server-wide, keyed off the current socket — skipped entirely when the tracked list is empty), joins every pane item on `scope.pane`, fingerprinted by `scope.pane_pid` (per-tick pids come from ONE batched `tmux list-panes -a -F '#{pane_id} #{pane_pid}'` call, made only when at least one pane item has a non-null `scope.pane`; a failed batch call yields an empty map and is not an error, and a null recorded pid or an unreadable current pid joins on the pane id alone), runs every **due shell probe** (argv executed directly — never a shell string — with a 10 s per-probe timeout, stderr discarded, stdout parsed as a JSON object; probes run sequentially under a 60 s per-tick wall-clock budget, and items the budget cuts off emit `probe_error` with `error: "skipped (tick budget)"` and `failures` untouched; only the declared `probe.fields` — top-level keys or dotted paths — are extracted, compared against `last`, and stored back, an absent declared field storing null), evaluates `done_when` (the equality-only predicate grammar — see the `done_when` Is Equality-Only design decision), `depends_on`, and staleness, and appends the YAML blocks to stdout in a pinned order: `deltas:` (event kinds `changed` / `done` / `stale` / `probe_error` / `pane_death` / `pane_mismatch` / `agent_exited` / `stage_advance` / `review_fail`, every delta keyed by `id`, in two delivery classes — see the Level-Triggered vs Consumed-on-Read Delta Classes design decision), `candidates:` (pane items whose snapshot `agent_state` is `waiting` or `idle`, waiting first, each with `pane`/`id`/`agent_state`/`idle_duration`/`state_duration` — `state_duration` is rk's `agent_state_duration` verbatim for `waiting` and `idle` rows (null when rk reports none) while `idle_duration` keeps its idle-only meaning; the auto-nudge sweep population, and `state_duration` is the §5 30m auto-default's input), `needs_check:` (due agent-probed items — `id`, `kind`, `age`, `instruction` — listed for the LLM, never run by the binary), and `items:` (one row per item — the per-kind fields (pane rows carry a present-keyed `change` field after `pane`, null when no change is observed, with `stage`/`display_state`/`pr_url` likewise null then) plus the derived `state` (`held`/`pending`/`live`/`watching`/`stale`/`paused`/`done`) and `next` (the item's `then`, `spawn` for pending, `held: <dep-id>` for held) — the status frame's data source). **`--quiet`** (valid only with `--diff`; alone it errors `--quiet requires --diff` before any state read/write, consuming no tick) replaces the `items:` block with a five-count `fleet_summary:` mapping (tracked/waiting/idle/active/unknown, pinned key order; never both keys) on a no-delta, no-needs_check tick whose last full document (`last_full_at`, RFC3339 UTC) is less than 10 minutes old (a built-in constant — no flag/config knob; a missing or unparseable stamp counts as due); a delta or needs_check tick and any tick whose `last_full_at` is at least 10 minutes old emit the full document, `candidates:` is always emitted, and the empty-tracked-list short-circuit emits the all-zero summary (or `items: []` on a due full tick). Every full document also writes `last_full_at` — alongside `tick_count`/`last_tick_at` and the baseline writes (pane baselines `scope.stage`/`scope.agent`/`scope.change` — the change is set only when the snapshot resolves one and is sticky: an unresolved snapshot fabricates no delta and leaves the baseline alone, while a change appearing or switching emits a consumed-on-read `changed` delta consumed by the same-write baseline update; a first-observed change also writes `branch_map[<change>] = {branch, repo}` in the same mutation, `repo` from `scope.repo` and the branch resolved once from the pane's cwd, skipped on detached HEAD or git failure and retried on a later tick while the entry stays absent; probe results `last`/`checked_at`/`unchanged`/`failures`/`paused`) — in the same atomic mutation: the full/quiet decision is computed inside the mutation (it reads the prior stamp), and `--diff` is the authoritative baseline writer. `--diff` ends with the level-wise clock reconciles: after the baseline write it issues one `rk cron mute <id>` when the post-tick state is untracked (skipping an already-muted entry), then the schedule reconcile — the same fail-silent, gated, 5s-bounded rk calls the `track` verbs make (the clock block above). `agent_exited` detection is decided by the snapshot row's `has_agent` tri-state (`false` ⇒ exited, `true` ⇒ alive, `null` ⇒ the process-tree walk); the walk first basename-matches the snapshot row's `command` field (rk rows' `command`, or the ninth `#{pane_current_command}` field of the fallback `list-panes -F` format — see [pane-commands.md](/runtime/pane-commands.md)) against `sh bash zsh fish dash ksh tcsh csh nu`, and only that shell branch resolves the pane's root PID and walks its process tree. A live agent process at the root or among its descendants suppresses the delta and gives the item a clean join; a PID-resolution or discovery error supplies no positive evidence and silently emits `agent_exited`. The agent classifier uses the provider-aware name set documented under `fab pane process`. Per-item evaluation order is `pane_death` → `pane_mismatch` → `agent_exited` → clean join, and a dead/mismatched/exited item gets no baseline write, no stage diffs, and no `candidates:` row (its items row falls back to baseline identity with null observed fields). A legacy-shaped state file converts on this verb too, and a `tracked`-present file holding an item under the retired change-keyed kind converts in the same atomic write (kind becomes `pane`, `scope.change` seeded from the item's id, `scope.pane_pid` null — idempotent; the rename's vocabulary lives in [migrations.md](/distribution/migrations.md)); the converted pane items are diffed in the same run (see the Legacy State Converts on First Touch design decision).

- **`fab operator state [--all] [--json]`** — prints the server-keyed state file (YAML verbatim; JSON with `--json`), persisting the empty skeleton (`tracked: []`, `branch_map: {}`) first when missing; a pure read of an existing file never rewrites it (a legacy-shaped file converts first). Human mode opens with the `# `-prefixed OPEN NOTES header — one line per `kind: note` item (id · age-from-`updated_at` · first line of text; a note older than 14 days carries a display-only `⚠ <age>` flag) — omitted when there are no note items and never in `--json`. `--all` is a deprecated no-op (note items always print).

- **`fab operator track add|update|observe|rm|list|clock`** — the one verb family over the `tracked` list (the full contracts live in `_cli-fab-operator.md` § fab operator track): `add` creates an item with the kind's binary-filled defaults (for `pane`: eleven pinned scope keys; `--pane` records `scope.pane_pid` in the same mutation, null on lookup failure; `--change` pre-declares the expected change; branch+repo write `branch_map` in the same mutation, keyed by `--change` when given, else the item id); `update` mutates passed fields (`--scope` merges per key — a `--scope` carrying `pane` re-records `pane_pid`, and clearing the pane nulls it) and `--pause`/`--resume` toggles `paused` (`--resume` zeroes `failures`); `observe` records an agent-probe result (`--json` stores the declared fields or the whole object into `last`, sets `checked_at`, resets `failures`, appends `--seen` ids with the 200-entry oldest-pruned cap; `--error` increments `failures` instead, 3 ⇒ `paused: true`); `rm` deletes the item (the ack for `done` and the pane deltas; a pane item's `branch_map` entry is retained); `list` prints one line per item (`id · kind · state · checked-age · next`) or the items array with `--json`; `clock (--every|--idle-every) <dur> --for <dur>` writes the bounded `clock_override` (`--for` required; `--off` clears). Every validation failure — duplicate id, unknown id, malformed `--done-when`, `--check-every` below the 1m floor, a `shell` probe without `--fields`, `--depends-on` naming an unknown id, `clock` without `--for` — exits non-zero with a one-line error and writes nothing. All six verbs carry the operator-clock side effect (the mute/unmute flip plus the schedule reconcile).

- **`fab operator branch-map rm <change-id> | --all`** — the explicit user-initiated clear for `branch_map` entries (written by `track add` when branch+repo are given, or by the tick at first change observation; retained by `track rm`). Unknown change-id → exit non-zero.

- **`fab operator time`** — Pure clock query with no file I/O or side effects. Always outputs `now: HH:MM` (local 24-hour time). With `--interval <duration>` (Go duration string, e.g. `3m`), also outputs `next: HH:MM` = now + interval. Invalid duration string → stderr error + exit 1.

**Usage in tick lifecycle**: The agent invokes `fab operator tick-start --diff --quiet` at step 1 of each tick (a user status request drops `--quiet`; the binary's time-based full document — full whenever `last_full_at` is at least 10 minutes old — is the periodic full refresh, no skill-side counter or timer) and parses its single stdout document: the tick count (`tick: N`) and current time (`now: HH:MM`), the `deltas:` it acts on, the `candidates:` block that feeds the auto-nudge sweep, the `needs_check:` block whose items it checks and observes, and the frame block — `items:` (rendered as the full status frame) or, on a quiet tick, `fleet_summary:` (rendered as the one-line compact frame) — the diff tick makes no per-tick `fab pane map`, `fab operator state`, or baseline-write calls (the binary owns all of them). The frame (plus its italic action footnote) is the only per-tick output — no restated tick document, no echoed `candidates:`, no per-candidate "no question detected" lines, and nothing between ticks. Separation of concerns: `tick-start` has side effects (writes YAML state, runs probes), `time` is a pure query (no writes).

## Design Decisions

### Auto-Answer Model with Strategic Escalation (rule 4 classification)
**Decision**: Detected questions are auto-answered by default via a numbered decision list (items 1-6, evaluated in priority order). Rule 4 (numbered menus) further classifies the prompt as Routine or Strategic before answering. Routine prompts (tool/permission, binary-framed, synonymous-option menus) auto-answer `1`. Strategic prompts (multi-option choices representing materially different directions — scope, PR split, pipeline shape, commit organization, spec/approach) escalate to the user. Classification is LLM-judged over four signals in the terminal capture (option text length, semantic distinctness, surrounding agent context, reversibility); no hardcoded keyword list, no agent-side sentinel protocol. Classification uncertainty MUST escalate (asymmetric cost structure: silently committing the queue to an unchosen branch of work is more expensive than an extra user nudge).
**Why**: Worktree isolation and human PR merge are sufficient safety gates for routine operational prompts, but not for prompts that commit the queue to a direction the user never inspected (scope, PR split, spec/approach). A pure all-auto-answer model traded correctness for throughput in the exact scenarios where correctness matters most. Principle-based LLM classification adapts to novel prompt text without maintaining a keyword list or coupling the operator to every skill's surface area.
**Rejected**: Pure all-auto-answer (original model) — loses correctness on strategic prompts. Hardcoded keyword list — brittle, fails on novel prompts, high-maintenance. Agent-side `[STRATEGIC]` sentinel protocol — couples the operator to every skill and fails on Claude Code native + third-party prompts the operator cannot modify.
*Introduced by*: 260314-007n-redesign-operator-auto-nudge (original model); 260422-hin2-operator-strategic-menu-escalation (Strategic classification + escalate-on-uncertainty)

### 30-Minute Idle Auto-Default on Strategic Escalations
**Decision**: A left-open rule-4 Strategic prompt gets the auto-default on the first tick whose `candidates:` row for that pane shows a `state_duration` of 30 minutes or more (hardcoded — no operator-state-file field, no per-change override, no environment variable exposes the threshold). The LLM runs no timers: `candidates:` rows carry `state_duration` (rk's `agent_state_duration` verbatim for `waiting` and `idle` panes; `idle_duration` keeps its idle-only meaning), and run-kit's agent-state epoch resets on any activity in the pane (new agent output, user keystrokes, prompt redraw), so the row's duration is the idle clock. The operator auto-answers — sending the prompt's stated default if visible (e.g., `(default: 2)`, `Press enter for 2`, `[2]`), otherwise option `1` — and logs with a distinct format, `"{change}: auto-defaulted after 30m idle: '{summary}' → {answer}"`, so after-action review tooling can distinguish confidently-auto-answered decisions from decisions taken because the user never returned.
**Why**: Strategic escalations stall forward progress if the user is asleep, in meetings, or otherwise away from the terminal. Unattended queue runs (overnight, multi-hour) become unreliable when every strategic escalation halts the pipeline. A 30-minute idle watchdog trades oversight for throughput in exactly the scenario where the alternative is zero throughput. The grep-distinct log format preserves auditability — `auto-defaulted` entries are recoverable separately from `auto-answered` entries.
**Rejected**: Configurable threshold (state-file field, per-change override, environment variable) — added surface area for marginal benefit; one threshold serves the single motivating "user is asleep / in a meeting" scenario well. Shorter threshold — risks auto-defaulting while the user is mid-reply. Longer threshold — defeats the feature. Uniform auto-default across all escalation types — conflates rule 4 Strategic (known-good default `1`) with rule 6 "cannot determine keystrokes" (auto-defaulting `1` would emit nonsense into the pane). Reusing the `auto-answered` log line — muddies audit trails by conflating confidently-answered and fell-back decisions. An LLM-side per-prompt real-time timer — conversation-only state, lost on compaction and re-payable every tick, when the candidate row's rk-owned duration already is the idle clock.
*Introduced by*: 260422-hin2-operator-strategic-menu-escalation; *Updated by*: 260911-1159-operator-pane-kind-pid-fingerprint (the idle clock is the candidate row's `state_duration`, not an LLM-side timer)

### Re-Capture Before Send
**Decision**: The operator re-captures terminal output immediately before sending an auto-answer. If the output changed, the send is aborted.
**Why**: Eliminates the race condition between idle check and send. Single-tick grace period was rejected — it adds latency without fully solving the race.
**Rejected**: Single-tick grace period — delays answers by one full monitoring cycle and doesn't guarantee safety.
*Introduced by*: 260314-007n-redesign-operator-auto-nudge

### Operator Uses /fab-fff for Queue Spawns
**Decision**: The operator uses `/fab-fff` instead of `/fab-ff` for queue gate checks and pipeline invocations.
**Why**: `/fab-fff` is the more autonomous pipeline variant, fitting for operator-driven queues where human interaction is minimized.
**Rejected**: Keeping `/fab-ff` — its interactive fallback on review failure conflicts with the operator's autonomous mode.
*Introduced by*: 260314-007n-redesign-operator-auto-nudge

### Standing Concerns Are User-Created Tracked Items, Not a Fixed Registry
**Decision**: Standing monitoring concerns are **tracked items the user creates conversationally** ("watch Linear project DEV for new issues, spawn agents, stop at intake" → a `linear` item via `track add`; "tell me when #913 merges" → a `github-pr` item; "poll the deploy until green" → a `shell` item), persisted in the operator state file and probed on each tick (a `shell`/`github-pr` item by the binary, a `linear`/`slack` item by the operator from the tick's `needs_check:` block). There is no fixed, built-in set of concerns: the item's structured fields (`probe`, `check_every`, `done_when`, `scope`, `seen`) carry the machine-readable part, and the free-form `then` prose carries everything the operator executes as an LLM (trigger conditions, label filters, spawn/notify actions, concurrency limits). Users manage items conversationally — create, pause/resume, retarget, re-scope, or remove; every utterance maps to one `track` verb (the skill's §7 Conversational Map). Ticks are the operator's heartbeat and the `track` verbs' mute keeps them coming while **any** not-done item exists (see "Tracked Means Any Item Not Done" below).
**Why**: Real workflows have multiple concurrent monitoring concerns, but which concerns matter is per-user and per-repo, so a fixed enumeration built into the skill would be wrong for almost everyone. One generic item schema — every item declaring *how* it is probed, *when* it is done, *what happens* then, and *how often* to look — covers concerns no typed section could anticipate, without new Go per concern; splitting structured fields from `then` prose keeps dedupe and scheduling mechanical (and testable) while leaving judgment to the LLM.
**Rejected**: A fixed set of built-in, toggleable concerns (wrong granularity — users' concerns are not enumerable in advance, and adding one would require a skill release). Per-concern typed sections with their own verbs and lifecycles (every new long-running thing needs new Go, and anything without a section is invisible to the mechanical tick). An all-structured item schema with no prose field (cannot express the trigger conditions users actually state). CLI-level branch resolution (`fab resolve --search-branches`) — fab operates on change folders, not git branches; branch awareness belongs in the operator skill.
*Introduced by*: 260317-yrgo-operator5-branch-fallback; *Updated by*: 260911-4a8m-operator-generic-tracked-items (generalized to the single tracked-item model)

### Note Items vs Probed Items vs Not-Operator-State
**Decision**: Cross-cutting narrative state routes by content class. A passive narrative read on restart/orientation — phase progress and holds, peer scoping agreements, report-back promises, merge-gate waits — is a **`kind: note` item** (500-char-capped free prose, never probed, rendered in the frame and the `state` OPEN NOTES header). A standing concern over an external source is a **probed item** — `linear`/`slack` (agent-probed) or `shell`/`github-pr` (binary-probed) — so the mechanical tick sees it. Anything still true for a different operator next month — process lessons — is **not operator state**: it routes via an `idea` backlog entry → a fab change into docs/memory.
**Why**: Items re-enter operator context on every tick and state read, so the surface must carry only what re-orientation needs; and the operator has no memory write path (a three-file context load, and it may run with no `fab/` project at all), so durable process lessons cannot route through the operator — they need the `idea` → fab change path into docs/memory.
**Rejected**: A dedicated `lesson` item kind (durable lessons belong in docs/memory, not in a per-server state file; the kind would invite a reflexive scratchpad). Teaching `depends_on` to survive item removal (fixes one case by complicating two schemas — a surviving wait is a note item). Auto-expiry for note items (notes are decisions, not a dedupe cache).
*Introduced by*: 260823-s2gw-operator-note-narrative-state; *Updated by*: 260911-4a8m-operator-generic-tracked-items (notes and watches folded into the one tracked-item model)

### Branch Fallback in Operator, Not CLI
**Decision**: Branch fallback resolution lives in the operator skill (user-initiated only), not in the `fab` CLI. When `fab resolve` fails, the operator scans branch names as a fallback before reporting failure.
**Why**: `fab` is orthogonal to git — it operates on change folders (filesystem/YAML). Branch name scanning is a coordination concern (finding where a change lives), not a CLI concern. The operator already has the context to decide between read-only (`git show`) and action (worktree creation) responses.
**Rejected**: `fab resolve --search-branches`, `--branch` output mode, automatic fallback in CLI — all rejected because they couple the CLI to git branch semantics.
*Introduced by*: 260317-yrgo-operator5-branch-fallback

### Dependency-Aware Agent Spawning (operator7)
**Decision**: `/fab-operator` (v7) adds pre-spawn dependency resolution to the operator. When spawning an agent for a change with `depends_on` entries, the operator cherry-picks dependency content into the worktree before opening the agent tab. Uses `git cherry-pick --no-commit origin/{default_branch}..<dep-branch> && git commit -m "operator: cherry-pick <dep> dependency"` (the base is fetched and resolved, never hardcoded (g8st)). On conflict: abort, escalate, do not spawn.
**Why**: Without dependency awareness, agents working on dependent changes start from a baseline missing the dependency code, causing build failures, spec divergence, and manual intervention. This defeats the operator's "automate the routine" principle.
**Rejected**: `git merge --squash` — rejected for unattended sessions where merge machinery introduces risk. Transitive dependency resolution — rejected because leaf dependency branches already carry transitive content via the operator's own cherry-picking when those deps were spawned; `origin/{default_branch}..<dep-branch>` gives the complete transitive closure.
*Introduced by*: 260324-prtv-operator7-dep-aware-spawning; *Updated by*: 260612-g8st-git-state-hardening (base = fetched, resolved default branch — see "Operator Git Ops Fetch First and Resolve the Default Branch")

### Operator7 Direct fab-new for Raw Text Spawns
**Decision**: When spawning agents from raw text descriptions, the operator passes the description directly to `/fab-new` instead of creating an intermediate backlog entry via `idea add`. The "From raw text" spawn path follows the same structure as "From backlog ID": worktree → resolve deps → spawn with `/fab-new <description>` → track → completion.
**Why**: The `idea add` step created orphaned backlog entries in `fab/backlog.md` that served no further purpose — the intake's Origin section already captures the raw input for traceability. `/fab-new` natively accepts natural language descriptions, making the backlog indirection redundant overhead.
**Rejected**: Keeping `idea add` for backlog traceability — the intake artifact is the real record of a change's origin, not the backlog entry.
*Introduced by*: 260326-13ro-operator7-direct-fab-new-spawn

### Pipeline-First Routing Principle (operator7)
**Decision**: The operator routes all new work **in a fab project** (the target repo has a `fab/` directory) through `/fab-new` then a pipeline command (`/fab-fff`, `/fab-ff`, `/fab-continue`). The operator MUST NOT dispatch raw inline implementation instructions to a fab-project agent pane and MUST NOT use `/fab-continue` to skip intake for new work. Operational maintenance commands (merge PR, archive, delete worktree, rebase, `/git-branch`, `/fab-switch`) are exempt. A repo with no `fab/` is exempt only from the pipeline, not from delegation — its work goes to a plain agent in a fresh worktree (Working a Change form 4). The principle lives with the pane kind's spawn rules in the skill, binding **spawns** (tracking an existing pane the user points at, a GitHub PR, or a Linear query needs neither it nor a worktree).
**Why**: Without an explicit prohibition, an operator (especially after `/clear` or under time pressure) could shortcut by sending freeform implementation instructions directly to an agent pane — bypassing intake generation, confidence scoring, and the full pipeline. This violates the fab workflow's core value: specification-driven development with traceability (Constitution §II).
*Introduced by*: 260326-u3un-operator-enforce-pipeline-routing; *Updated by*: 260911-4a8m-operator-generic-tracked-items (scoped to the tracked-item model); *Updated by*: 260911-1159-operator-pane-kind-pid-fingerprint (binds spawns, not tracking); *Updated by*: 260911-pudv-operator-non-fab-repo-plain-agent (binds fab projects only)

### Cherry-Pick-Ladder Is the Default Merge Mode
**Decision**: Queue chaining defaults to **cherry-pick-ladder** mode. All queued changes after the first implicitly get `depends_on:` — naming the **nearest same-repo predecessor** (w7dp) (the closest earlier same-repo queue entry, cherry-picked; no same-repo predecessor → the immediately previous entry as an ordering-only barrier), not blindly the previous queue entry. PRs are created but not merged until the user reviews and explicitly requests merging. Two opt-in modes share the queue model: merge-as-you-go behavior is available as the `merge-auto` mode, and the default's merge timing with a true stacked-PR topology (each same-repo dependent branches off its dependency's branch and PRs against it) is available as `stacked-prs`. Queue completion produces a summary with all PR links and suggested merge order (base-first). Ordered merge gates each PR per mode — auto-merge arming with tick verification for `cherry-pick-ladder`/`merge-auto`, foreground CI wait for `stacked-prs` and when arming is unavailable. The mode is resolved by the ladder `--mode` flag > config `autopilot.merge_mode` (the key keeps its historical name) > built-in default, and the binary stamps it into each chained item's `scope.merge_mode` at `track add`.
**Why**: Merge-as-you-go as default caused two problems: (1) rebase conflicts when rebasing dependent changes onto freshly-merged `origin/main` re-linearized commits that cherry-pick resolution had already handled, and (2) no opportunity for holistic review of the full change set before any code merged to `main`. Stack-then-review gives the user full review control over the entire queue.
**Rejected**: Merge-as-you-go as default — too many rebase conflicts and no review control. Available as opt-in for users who want it.
*Introduced by*: 260327-gwg9-operator-base-chaining-default; *Updated by*: 260612-w7dp-orchestrator-dispatch-review-pr-recovery (chaining reconciled to nearest-same-repo-predecessor — the strict queue-previous rule contradicted the worked example and silently broke same-repo stacking across an intervening cross-repo entry); *Updated by*: 260820-t6rq-autopilot-merge-modes-stacked-prs (the three-mode model — each name conveys its mechanism and merge agency); *Updated by*: 260823-2c92-operator-auto-merge-choreography (the ordered-merge CI gate is mode-split); *Updated by*: 260911-4a8m-operator-generic-tracked-items (the queue is a chain of tracked items; mode stamped per item)

### Agent Tabs Are Named for the Worktree and Marked via `rk tab`
**Decision**: A spawned agent's window is named plain `<wt>` (the worktree name — always available at spawn time and unique across panes, so it is a consistent identifier for all three spawn paths), and operator ownership is marked through run-kit's window options instead of name prefixes: `rk tab mark @<window_id> auto` plus `rk tab note @<window_id> "<id> · <stage>"` at spawn/track, the mark flipped to `blocked` while the pane item is `waiting` on a human, and `rk tab mark --off` + `rk tab note "✓ <id> done"` at removal. rk owns the mark/note option contract (`@rk_win_marker` / `@rk_win_note`); fab is only the producer.
**Why**: Window identity and ownership marking are tmux substrate, which run-kit owns (cli-layering rule 1) — the mark options give the tab bar the same at-a-glance map (tracked now / waiting on a human / done) without fab reimplementing guarded name rewrites, and without name prefixes competing with the user's naming sovereignty. The worktree name is always available at spawn time and unique across panes, making it a consistent identifier for all spawn paths.
**Rejected**: Name-prefix markers (`»`/`›`) maintained by fab-side rename primitives — a second, fab-owned marking mechanism duplicating rk's window options, and prefix rewrites clobber-or-guard against user retitles by construction. `⚡`-style emoji prefixes — double-width rendering breaks tmux tab alignment (260328-iqt8). Folding the mark into the `track` state verbs — couples a state write to a tmux side-effect with different failure semantics (the m7kq separation rule, unchanged).
*Introduced by*: 260911-4a8m-operator-generic-tracked-items (carries forward 260328-iqt8-standardize-tmux-tab-naming's worktree-name choice)

### Multi-Repo / Multi-Session Isolation = Tmux Server (one operator per server)
**Decision**: The operator's isolation unit is the **tmux server** — exactly one operator per server, spanning every session and repo on it, owning one **server-keyed** state file at `$XDG_STATE_HOME/fab/operator/<server-slug>.yaml` (fallback `~/.local/state/...`), keyed by the tmux socket path (the binary derives it via `StatePath()` — see [kit-architecture.md](/distribution/kit-architecture.md)). The file path and its `slugify` rule are a cross-repo contract: run-kit mirrors the exact slug rule to locate the file for display (◉ watched rows, `⚠ operator stale`), pinned in run-kit's operator-cron spec — renaming the file or changing the slug rule requires a coordinated run-kit change. A second operator means a second tmux server (`tmux -L <label>`). There is **no `--name` dimension** — the server boundary is the only isolation knob, matching the server-wide singleton already enforced by the `operator` window. Old repo-rooted `.fab-operator.yaml` files are **not migrated** — abandoned in place (the tracked set is re-derivable from live panes). Every tracked item (`scope.repo`), `branch_map` value (`{ branch, repo }`), and linear/slack spawn target is repo-qualified under the `(session, repo, pane)` addressing tuple, with pane ID as the server-global primary key.
**Why**: A single operator coordinating multiple repos/sessions is the central value of the operator (one pane of glass). A repo-rooted state file is single-repo-only; a fixed global path would force a machine-wide singleton. Keying the file by the tmux socket scopes one owner across all repos on a server while still allowing a second server to host an independent operator. No migration is acceptable because operators don't survive a binary upgrade anyway.
**Rejected**: Per-repo operators (loses the single pane of glass). A `--name` operator dimension (redundant with the server boundary). Repo-rooted `.fab-operator.yaml` (single-repo only). A fixed global state path (machine-wide singleton). Migrating old state files (unnecessary — the tracked set is re-derivable).
*Introduced by*: 260607-oy0k-operator-multi-repo-skill; *Updated by*: 260911-4a8m-operator-generic-tracked-items (repo qualification rides the tracked item schema)

### Cross-Repo Dependencies = Ordering-Only (no code merge)
**Decision**: `depends_on` resolution is two-tier, split by repo. A **same-repo** dependency cherry-picks (`git cherry-pick --no-commit origin/{default_branch}..<dep-branch>` — base fetched and resolved (g8st)). A **cross-repo** dependency is an **ordering-only barrier**: the operator waits until the dependency is satisfied (its item done), then spawns — **no code is merged**. The skill states the REQUIRED caveat that a cross-repo dependency gives the dependent agent no code (pure logical sequencing), correct only for logical deps ("don't start the frontend until the API merges"), never code-level ones. Ancestor-pruning (`git merge-base --is-ancestor`) is scoped to the same-repo subset only.
**Why**: Cross-repo branches share no common default-branch base, so there is no sound cross-repo cherry-pick; logical sequencing is the only sound cross-repo semantic. Forbidding cross-repo deps would be too restrictive for real multi-repo workflows.
**Rejected**: Forbid cross-repo deps (too restrictive). Full cross-repo code merge (unsound — no shared base). Cross-repo ancestor-pruning (meaningless across repos with no shared history).
*Introduced by*: 260607-oy0k-operator-multi-repo-skill

### Repo-Spanning Queue CI-Failure = Halt-Dependents-Only
**Decision**: A queue may span repos with mixed dependency semantics (within-repo cherry-pick chaining degrades to cross-repo ordering-only barriers); ordered merge tracks per-repo PR sequences. On a CI failure during ordered merge, the operator halts the failing repo's merge sub-sequence AND any repo whose queued items carry a cross-repo `depends_on` into the failed chain — **transitively** over the cross-repo `depends_on` graph. Truly independent repos' sub-sequences **continue merging**. The completion summary reports halted vs. completed sub-sequences and escalates to the user.
**Why**: Maximizes independent-repo throughput while still respecting cross-repo ordering barriers — the failure's blast radius is isolated to its dependency cone rather than throttling the whole queue.
**Rejected**: Halt-all (conservative, throttles independent repos — the earlier lean, overturned during clarify). Halt-only-failing-repo (ignores cross-repo ordering barriers, would merge a dependent ahead of its failed barrier).
*Introduced by*: 260607-oy0k-operator-multi-repo-skill

### Operator Context Loading Trimmed to Three Files (zc9m)
**Decision**: `fab-operator.md` §2 Context Loading loads only `config.yaml`, `constitution.md`, and `context.md` (optional), and `fab-operator` is named in the `_preamble.md` §1 exception list with its 3-file load. ### Status Frame = One Markdown Table + Emoji (ANSI does not render)
**Decision**: The operator status frame is rendered as **markdown** — a header line and one table over all tracked items (`| | ID | Kind | State | Checked | Next |`). Health is shown with **emoji** (🟢🟡🔴✅⚪); IDs are `code spans`; the header uses emoji + **bold**; the Kind cell carries the repo basename (`pane · foo`); the Checked cell carries the probe freshness (`live` / age / `⚠` / `🔴`); PR URLs surface as **plain text** on the pane item's row. Earlier specs colored an ANSI-wrapped glyph (`\e[32m●\e[0m`) and a later iteration broadened ANSI to many fields ("structural color"). **Both were non-functional**: the frame is an assistant message rendered as markdown by the agent harness, and ANSI escapes are stripped on that path — verified empirically that neither literal `\e[` text nor real ESC bytes render, and that markdown headings also render as literal text. Emoji (glyphs, not escapes) are the only surviving color channel; markdown tables give real column alignment and absorb the wide PR URL.
**Why**: The operator never writes to a TTY directly — it emits text that the harness markdown-renders. Color/visual hierarchy therefore must come from channels that survive that render (emoji, tables, bold, italic, code spans), not ANSI or headings. One table over all items with a Checked age column makes a stale item *visible* — freshness is a column, not a separate surface — and the repo basename riding the Kind cell keeps rows narrow without per-repo anchor sections. PR URLs are surfaced as plain text (not `[#N](url)` links) so they are selectable/copyable in a plain xterm.
**Rejected**: ANSI SGR codes (stripped by the markdown renderer — the bug this fixes). Markdown headings for the header/sections (render as literal `##` text). `[#N](url)` markdown links for PRs (xterm shows only `#N`, not a copyable URL). Per-repo `📂` anchor sections plus a separate watches table (the one-table form subsumes them; a stale non-pane item had no row at all under the sectioned frame). Geometric glyphs `●◌✗` for health (render monochrome — no color).

### Operator Git Ops Fetch First and Resolve the Default Branch (g8st)
**Decision**: Every operator git sequence that uses the default branch as a base — the same-repo dependency cherry-pick, the `merge-auto` rebase, and the `stacked-prs` merge-all rebase — runs `git fetch origin` first and resolves the repo's **actual** default branch instead of hardcoding `origin/main`: `git symbolic-ref --short refs/remotes/origin/HEAD` (strip `origin/`) → `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` → probe the just-fetched refs (`main` when `origin/main` exists, else `master`). The resolved `origin/{default_branch}` is the cherry-pick range base and the `merge-auto` rebase target.
**Why**: Hardcoding `origin/main` with **no fetch step** made queues unusable on any repo whose default branch isn't `main`, and even on main-defaulted repos the base could be stale. Fetch-first fixes the staleness; name resolution fixes the portability. The chain matches `/git-pr`'s default-branch resolution (one convention across autonomous git paths — see [change-lifecycle.md](/pipeline/change-lifecycle.md) § Git Integration); the operator's literal fallback probes refs rather than assuming, because the fetch has already run.
**Rejected**: A shared `_` helper file for the chain (two consuming skills, three lines each — a helper would add loading cost for every other skill; the chain is inlined per consumer). Keeping hardcoded `origin/main` with a config override (the resolution is mechanical; no config knob needed).
*Introduced by*: 260612-g8st-git-state-hardening

### Queue Spawns Have a Single Dispatch Point: Gate Before Spawn, Command Embedded at Spawn (w7dp)
**Decision**: A spawned change's initial pipeline command has exactly **one** dispatch point — the §6 spawn-sequence open-agent-tab step (**step 7**) embeds it as the trailing argv token of the `rk tab new … -- <argv…> "<skill-prompt>"` invocation. The queue per-change loop carries no separate "Dispatch" item, and the confidence **Gate runs before the tab opens** — a below-threshold change gets no worktree, no tab, and no dispatch. The initial command is the single parseable `/fab-fff <change>` (the change-name override) — `&&`-chained slash commands have no chaining semantics and MUST NOT be sent.
**Why**: A double dispatch (the spawn-embedded command plus a separate post-spawn dispatch) fires the command twice into the same pane. All spawn forms already send the initial command via the spawn tab, so keeping spawn-embedding required no new machinery, while gating after spawn would open tabs for work the gate then rejects. `/fab-fff <change>` targets the change directly (no switch pre-step) and picks up from its current stage.
**Rejected**: Bare tab + post-spawn keyed dispatch (adds an idle-detection/ready-state dependency to every spawn). Keeping a loop Dispatch item with a "skip if already sent" note (preserves the double-dispatch hazard). An `&&` chain (no chaining semantics — the trailing command lands as literal text).
*Introduced by*: 260612-w7dp-orchestrator-dispatch-review-pr-recovery; *Updated by*: 260911-4a8m-operator-generic-tracked-items (the open-tab step is `rk tab new` argv form)

### Operator Launch Is Git-Optional, `fab/`-Optional, and Operator-Role-Resolved
**Decision**: `fab operator` requires neither a git repo nor a resolvable `fab/` project, and it launches its coordinating agent on the **operator role**. (1) Window cwd: try `gitRepoRoot()`, fall back to `os.Getwd()`, error only if both fail. (2) Session command: the operator provider's `interactive_command` from the project config when `resolve.FabRoot()` succeeds, else `spawn.DefaultSpawnCommand` (non-fatal `FabRoot()` failure). (3) Profile: **resolve the `operator` role in-process** (tykw) (`operatorProfile`) and consume its full model/effort directly rather than the `fab agent -o yaml` native `model_alias` seam; substitute/append `{model}`/`{effort}` via `spawn.WithProfile`; on ANY failure fall back to the in-process `agent.DefaultProfile(agent.RoleOperator)`. `spawn.WithProfile` is the shared composition helper in `internal/spawn`. No state-file path change — state stays socket-keyed; no migration for the launcher itself (config-schema restructures ship as their own migrations).
**Why**: The git root was incidental — used ONLY as the tmux window `-c <dir>`, never in the socket-keyed state path — and forcing one repo root (and one owning `fab/` project) contradicted the operator's per-tmux-server, cross-repo singleton design, whose natural home is a neutral parent dir. On the profile: the coordinator deserves its own named role rather than a borrowed one, so the launcher resolves `operator` directly instead of probing the `apply` stage to borrow `doing`. The role's fill is the coordinator's highest-volume, pattern-matching, escalation-disciplined workload, and the built-in fallback keeps the operator working when no project is resolvable. This keeps the operator a non-orchestrator (non-pipeline) consumer of the agent-role system. `fab operator` is **NOT** an alias of `fab agent operator` — it keeps its distinct responsibilities (tmux singleton window management, launching with `/fab-operator` as the initial prompt, the state/tick/track subcommands); only the session-command *composition* is shared. Conceptually: `fab operator` ≈ singleton tmux window running `$(fab agent --print operator) '/fab-operator'`.
**Rejected**: Keeping the hard git-repo (and `fab/`-project) precondition (contradicts the cross-repo singleton model; the git root was never essential). Keeping the `doing` borrow / the `apply`-stage probe (mis-names the coordinator's role — a real `operator` role exists (tykw)). Reducing `fab operator` to an alias of `fab agent operator` (loses its tmux-singleton / initial-prompt / subcommand responsibilities — only the session-command composition is shared). Inline `--model`/`--effort` concatenation in `runOperator` (not reusable, not unit-testable) — hence the shared `spawn.WithProfile` helper.
*Introduced by*: 260613-2sdj-operator-doing-tier-no-git-dep; *Updated by*: 260702-tykw-agent-providers-role-tiers (operator role resolved in-process; session command from the operator provider), 260806-j9nh-agent-profiles-session-workers (the operator's provider is the `agent.session` knob's call)

### Non-Blocking Strategic Escalation + Adaptive Heartbeat (mmmt)
**Decision**: A Strategic menu (rule 4) does not park the operator's turn. Strategic handling is **non-blocking**, split by whether a defensible recommendation exists: (1) **defensible recommendation → auto-pick-and-notify** — the operator picks its recommended option (LLM judgment over the capture using rule 4's four signals), sends it after the re-capture-before-send guard, fires a notification, and keeps ticking; the PR review stage is the reversal point (§1). (2) **no defensible default → leave open and notify** — the operator leaves the prompt open, fires a notification, and keeps ticking; the 30m idle auto-default remains the backstop for these left-open prompts (its scope is narrowed to left-open prompts only — auto-picked ones are already resolved — and its timer runs in the background, not blocking the tick). In both branches the operator picks up the user's async answer on a later tick via the existing §5 re-capture/re-detection path — **no new pickup mechanism is added**. The notification **send** is abstracted behind one fail-silent out-of-band shell command, **`rk notify`** (run-kit Web Push; the contract is tool-owned, read at use-time via `rk skill`); all sends fail silently. The 30m strategic auto-default threshold stays **hardcoded** (no setting), and no operator-state-file field exposes it. Cadence is the rk cron operator-tick entry — see "Cron Entry as the Sole Cadence, Provider-Neutral" below.
**Why**: At introduction the operator's coordination loop was a single-threaded in-session heartbeat serving every tracked change across every repo and session on one server, and the old "escalate to user" behavior parked the loop waiting for a human, so a single strategic question on one change **froze the entire queue** (observed live on the FKF queue (bmzo)). Non-blocking escalation is the minimal structural fix — it removes the single-question-freezes-everything failure mode without changing the single-clock architecture. Auto-pick-and-notify keeps the queue moving and defers human judgment to PR review (the existing safety net). Abstracting the send behind one shell command lets the channel evolve (ntfy.sh → `rk notify`) without touching the escalation logic; `rk notify` is the default because it delivers a real background push, is fail-silent by contract, routes through infra the user already runs, and avoids a world-readable topic secret.
**Rejected**: Parking every strategic menu (the freeze this change removes). A second concurrent loop or a separate watcher thread for the watchdog (violates the one-clock design, adds infrastructure). Hardcoding ntfy.sh as the default channel (world-readable topic). Shortening or making configurable the 30m auto-default threshold (stays hardcoded). Building run-kit Web Push here (it shipped as a separate run-kit change, backlog `[xd9r]`); the operator only consumes it as the default channel (mmmt).
*Introduced by*: 260615-mmmt-non-blocking-operator-escalation

### Operator Keys Off the Richer `@rk_pane_agent_state` Agent Column (ioku)
**Decision**: The operator's monitoring keys off the three-state-plus-unknown Agent column read from the `@rk_pane_agent_state` tmux pane option (`active`/`waiting`/`idle`/`—`; see [runtime-agents.md](/runtime/runtime-agents.md) and [pane-commands.md](/runtime/pane-commands.md)) — the operator's interface keys off the snapshot rows that carry the column (per tick via `fab operator tick-start --diff`, on demand via `fab pane map --all-sessions --json`). Three concrete keyings: (1) the per-tick auto-nudge population is **`waiting` primary + `idle` fallback** (`active`/unknown panes are usable but not swept every tick); (2) `waiting` is the **primary pickup trigger for human-blocked agents** (capture-classify stays the fallback for `active`/unknown panes) — the signal also feeds the cron entry's `wake_on: agent-state-change` (6t88); (3) the pre-send gate uses the mode-aware semantics the gated sender enforces (plain send refuses `active`/`waiting`; `--answer` permits `waiting` for detected-prompt answers; unknown warns-and-sends in both non-force modes — enforced by `rk mux send`). **Rejected**: Sweeping only `waiting` (would miss idle-but-prompted panes on uninstrumented harnesses). Sweeping every non-idle pane every tick (churns capture on `active`/unknown panes for marginal gain — they stay capture-applicable, not per-tick swept). A new operator signal beyond the Agent column (the column carries the signal directly — no second channel needed).

### Operator Activates the Change Pointer at Spawn for Existing Changes (5xnx)
**Decision**: The §6 spawn sequence carries an **existence-guarded pointer-activation step** at **position 4** (between `wt create` at step 3 and opening the agent tab at step 7, in the 8-step sequence). The step runs `fab change switch <change>` in the **just-created worktree's CWD**, writing that worktree's own `.fab-status.yaml`, **guarded** on `fab resolve --folder <change>` succeeding (the existing pure-query verb; non-zero exit = "no such change") so it fires only when the change folder already exists, and **fail-soft** (log one line and continue opening the tab on a switch failure). The raw-text and backlog/Linear forms **skip** the switch — the folder doesn't exist yet at spawn time, so the guard fails — and defer activation to `/fab-new`, which creates and activates the change inside the spawned agent (activation at fab-new Step 10). This is the **second consumer-side activation stance** alongside §3 Pre-Send Validation (switch first when sending to an existing pane whose active change is wrong); the spawn path is consistent with it. The `&&`-no-chaining prohibition is unchanged — the fix is a separate spawn step, not a chained slash command.
**Why**: After an operator-driven pipeline completed on an existing change, the spawned worktree had **no active-change pointer** (`.fab-status.yaml` is gitignored and per-checkout, so a fresh worktree starts pointer-less; the `/fab-fff <change>` entry form relies on a transient `<change>` override that never writes the pointer). Any human who later `cd`s in and runs a bare `fab`/`/fab-*` got `No active change (multiple changes exist — use /fab-switch)` and had to name the change on every follow-up (the highest-friction case being `/fab-archive <change>`). Setting the pointer at spawn carries **zero cross-tab collision risk** — each operator worktree is a dedicated, single-change checkout that owns its own `.fab-status.yaml`, so the parallel-tabs-share-one-pointer concern the transient override protects against does not arise within a single worktree. The override remains correct for pipeline resolution; the activation merely *also* makes the worktree self-describing.
**Rejected**: Leave-as-is / rely on the `<change>` arg (zero new writes, but pushes friction onto every human follow-up). **Sequentialized slash commands** — `/fab-switch <change>` before `/fab-fff`, in either form: (a) a `&&`-joined string sent as one prompt does not work at all — the spawn embeds a single prompt, where `&&` is not a shell operator and the harness reads one leading `/command`, so the `&& …` tail is absorbed into the first command's argument; (b) two separate Enter-terminated sends *would* work, but a slash-command switch is a full agent round-trip for a one-line symlink write and a post-spawn send regresses the single-dispatch-at-spawn property (w7dp). The synchronous `fab change switch` **CLI verb** does the identical write directly — no agent turn, no pane-timing fragility — and setting the pointer is operator *coordination* state the operator already owns directly (like `wt create`/window marks), not pipeline work to delegate. Aborting the spawn on switch failure (over-couples ergonomics to correctness — the transient override still resolves the pipeline). A bespoke `test -d` folder check instead of `fab resolve --folder` (duplicates resolution logic and ignores archived state).
*Introduced by*: 260617-5xnx-operator-spawn-activate-pointer

### Spawn Target Session Is Inferred Live Per Spawn by Majority Rule, Never Persisted-and-Trusted
**Decision**: §6 spawn-sequence step 2 infers the tmux session every new agent window lands in, live at spawn time: the candidate set is `rk mux sessions --json`'s `role: "user"` rows minus the operator's own session, and the decision is the **majority rule** over the same `rk mux panes --json` snapshot — the candidate session holding the most panes whose `cwd` is under the target repo wins; a tie the count cannot separate falls to the §8 setting, and still torn → the one ask (attended) or §5 escalation (unattended). Default-and-announce on an evidence-backed inference (announce session + deciding evidence, auto-set the §8 setting). The operator pins the session explicitly at spawn (`rk tab new --session =<session>`): **the ambient session is never an implicit target**, the session analog of the never-rely-on-CWD rule.
**Why**: The operator may run in its own dedicated tmux session, distinct from the work session(s); an untargeted spawn resolves against the ambient session, so every spawn path silently misplaced its window there, an observed real failure (z597). `session` is context-not-identity (reassigned by `move-window`/rename, changeable mid-lifetime) and §1 Re-derive-state forbids trusting stale values, so the session must be derived live at spawn time; repo-scoped evidence handles multi-repo naturally because each repo's work clusters where it already lives. An ask-first cold start fires exactly when the answer is obvious from the pane map the operator already fetches (live reproduction: the ask's own prompt computed "fabKit — 13 target-repo worktree panes" as its recommendation, then asked anyway), and a wrong landing is cheap to correct (`move-window`; the spawn's `--json` report confirms where the window landed), so evidence-backed default-and-announce replaced ask-first (cx52).
**Rejected**: Deriving from a persisted `session` field (stale-prone — context, not identity); a config-only default work session, incl. a persistent `operator.spawn_session` key (a single durable value fights the multi-repo model and goes stale — session names are per-tmux-server and ephemeral; the operator may also run with no resolvable `fab/` project); ambient-as-implicit-default (the bug itself); keeping an ask-first cold-start rung (asks exactly when the answer is obvious, and recurs every session because the §8 setting is session-lifetime-scoped); evidence tiers beyond the majority rule (the pane-count majority over `role: user` rows decides every observed case; tiers were speculative generality).

### Full Mediation of State Writes
**Decision**: Every operator-state-file mutation — item CRUD, probe bookkeeping (`track observe`), the bounded cadence override (`track clock`), and the tick mechanics — goes through a `fab operator` verb; the operator never writes the YAML itself. The doctrine extends to tick mechanics: `fab operator tick-start --diff` computes the per-tick diff and runs the due probes inside the binary and is the authoritative writer of each item's baselines (pane items: `scope.stage`/`scope.agent`; probed items: `last`/`checked_at`/`unchanged`/`failures`/`paused`) in the same atomic mutation as the tick bookkeeping. The schema block in `fab-operator.md` §4 is reference documentation of what the binary maintains, not a format the agent composes. The doctrine's scope extends beyond writes to computation and detection policy: probe execution, the `done_when` evaluation, and item-state derivation already compute binary-side, and pending-prompt classification is tool-owned by run-kit (`rk mux capture --classify`); the genuinely judgment-requiring steps (the answer model, the delivery guards) stay LLM-side.
**Why**: "Schema cannot drift" holds only if no hand-write path remains; the motivating incident (2026-08-13: a gpt-5.6-luna session hand-edited the YAML with an invented free-form field instead of a tracked entry) was a tick-time state write. "Run a command with flags" is the instruction class weak models follow reliably; whole-file YAML regeneration is the class they fail — and prose-enforced schema fails exactly where the operator is meant to become provider-agnostic.
**Rejected**: Mediating only structural ops (leaves the highest-frequency writes hand-edited); a post-hoc schema validator (detects drift instead of preventing it, and still leaves timestamp/pruning computation on the agent); schema-validated whole-file `write` on stdin (still makes weak models compose YAML; rejection loops stall the tick loop); leaving probe/detection policy in skill prose (guard and comparison logic redone in natural-language reasoning every tick, untested, and free to drift from the documented list as the skill file is edited).
*Introduced by*: 260819-m7kq-operator-state-binary-subcommands; *Updated by*: 260911-4a8m-operator-generic-tracked-items (probe execution and predicate evaluation moved binary-side; prompt classification rides run-kit)

### Mode Is Stamped Per Chained Item at `track add`
**Decision**: A chained pane item's merge mode is resolved once at `fab operator track add` by the ladder `--mode` flag > config `autopilot.merge_mode` > built-in `cherry-pick-ladder`, stamped into the item's `scope.merge_mode`, and printed as `mode: <name> (<source>)` on the first chain add. There is no mode-mutation verb; changing a queue's mode means removing the chain and re-adding it. An invalid config value is the binary's own actionable error, never a misfit question.
**Why**: A queue's dependency topology is built per-mode at spawn time (branch-off-dep vs cherry-pick) — switching mid-queue would leave half the queue in the wrong topology. ### Auto-Merge Choreography: Sequential Arming with Verified-Merge Gating
**Decision**: Merge-all for the modes whose PRs target main (`cherry-pick-ladder`, and `merge-auto`'s per-PR merges) rides GitHub auto-merge under a five-MUST-rule choreography: at most one armed PR per repo-sequence, armed only after the predecessor's merge is verified (its item's `done` delta), never an assumption, never a PR whose base is another PR's branch; the three arming-failure shapes are handled (draft → `gh pr ready`, already-clean → merge directly, repo-disabled → foreground CI-wait fallback); the per-tick stall check treats a failed required check as the CI failure and, at `unchanged ≥ 3` on the armed item (the binary-owned no-delta counter), polls `gh pr view --json mergeable` with `CONFLICTING` → disarm and escalate; the sequence IS a chain of `github-pr` items (one per PR, chained by `depends_on`, each carrying `then: "arm next: …"`) — an armed PR outlives the operator, and the items are what a restarted operator re-orients from (`fab operator track list`); and a halt disarms the halted sequences' armed PRs (dependent cone — independent sub-sequences continue; a user stop disarms all). An open merge sequence keeps the clock live like any other not-done tracked item. **`stacked-prs` keeps the manual foreground merge-all.**
**Why**: Foreground CI-watching between ordered merges was the longest operator-busy stretch in the coordination lifecycle, at exactly the moment the fleet is otherwise idle. Arming converts it into a passive tick check — but a bare "just use auto-merge" is dangerous: an armed PR outlives the operator and fires without an event, so sequencing must be operator-verified, the sequence must survive `/clear`/crash, conflicts must be polled for (auto-merge fails silently), and halting must disarm what GitHub would otherwise still merge. Carrying the sequence as `github-pr` items makes it mechanical: the binary probes each armed PR on cadence, the `done` delta fires the next arm, and the `unchanged` counter replaces a conversation-counted stall window with binary state.
**Rejected**: Arm-all-upfront (unordered merges; wrong-base hazard). Including `stacked-prs` (the win was always marginal there — its inter-merge choreography is operator-sequenced anyway — and its failure modes are the worst: an armed stacked PR can merge into its dependency's *branch*, destroying the stack silently, or fire on stale-green checks after GitHub's no-re-CI base retarget). Persisting the sequence as prose (a note the tick never probes — prose state is invisible to the mechanical loop).
*Introduced by*: 260823-2c92-operator-auto-merge-choreography; *Updated by*: 260911-4a8m-operator-generic-tracked-items (the sequence is a chain of `github-pr` items; the stall rule reads the binary's `unchanged` counter)

### Level-Triggered vs Consumed-on-Read Delta Classes
**Decision**: `fab operator tick-start --diff` emits deltas in two delivery classes. **Level-triggered, re-emitted every tick until acked** — `done` (acked by `track rm`), `stale` (acked by `track observe`), `probe_error` (acked by `track update --resume` or `track rm`), `pane_death`, `pane_mismatch`, `agent_exited` (acked by `track rm`): stateless predicates over the current snapshot and `last` that need no baseline read. `done` is the item's `done_when` evaluating true against `last`, or the pane built-in — a display-state predicate at a stage (`review-pr` done/skipped, or at/past `stop_stage`) that applies only when `scope.change` is non-null (a change-less pane item is never done on its own); `pane_death` is the pane's absence from the snapshot; `pane_mismatch` is the recycled-pane case only — a non-null recorded `pane_pid` differing from the pane's current shell pid (a null recorded pid or an unreadable current pid joins on the pane id alone); `agent_exited` is the item's pane present and fingerprint-matched but no live agent remaining, decided by the row's `has_agent` tri-state (`false` ⇒ exited, `true` ⇒ alive, `null` ⇒ the process-tree walk decides). The walk runs only in the shell-foreground branch, positive live-agent evidence produces a clean join, and PID/tree errors fail toward emitting. `agent_exited` is evaluated after `pane_death` and `pane_mismatch`, so a mismatched shell-fronted pane emits only `pane_mismatch`. **Consumed-on-read, baseline-diffed** — `changed` (per-field from/to against `last`), `stage_advance`, and `review_fail` (review→apply): computed against the stored baselines and consumed by the same-write baseline update; a lost one costs a missed report only. `pane_mismatch` excludes a recycled pane from diffing, baseline writes, `candidates:`, and the `items:` join. `agent_exited` mirrors those exclusions because a wrapped interactive spawn leaves the pane alive as a shell and its stale `@rk_pane_agent_state` can still read as a nudge candidate. (260902-ssyf-operator-liveness-process-tree)
**Why**: Action-demanding deltas re-emit until the operator reports and removes them, so a crash between diff and action loses nothing; report-only deltas need no durable per-event acknowledgement. Positive process-tree confirmation is necessary because on Linux the wrapped interactive spawn's shell remains the foreground process-group leader for the live agent's entire lifetime, while failing toward emitting prevents an unconfirmed bare shell from entering the nudge population. The `has_agent` tri-state short-circuits the walk on instrumented panes — `false`/`true` decide without a process read — and only an uninstrumented pane (`null`) pays the walk.
**Rejected**: One uniform consumed-on-read class for every delta (a crash between diff and action loses action-demanding events permanently). One uniform level-triggered class (requires durable per-event ack state for events whose loss is harmless). Stage-diffing completion (the stage string does not change at the final stage). Agent state as exit evidence (fab ignores its PID segment and the pane option can retain the agent's last value). `pane_pid` childlessness or `#{pane_current_command}` as a primary liveness signal: an unwrapped single-command spawn can make `pane_pid` the agent with zero children, while a wrapped Linux spawn keeps the shell as process-group leader for the live agent's entire lifetime.
*Introduced by*: 260823-dbwg-operator-tick-diff-offload; *Updated by*: 260911-4a8m-operator-generic-tracked-items (deltas keyed by item id; `done`/`stale`/`probe_error`/`changed` join the classes; `has_agent` tri-state gates the walk)

### Completion Is the Pipeline Terminus, Dependency Satisfaction Is Completion Plus PR
**Decision**: With `stop_stage: null`, the pane built-in completion predicate is `stage == review-pr && display_state ∈ {done, skipped}` — a display-state check at the terminus, never bare stage membership — and it applies only when `scope.change` is non-null; a change-less pane item is never done on its own. Early parking is expressed through `stop_stage` (`--stop-stage hydrate` for `/fab-ff` spawns). Separately, the skill defines **dependency satisfied** once (the dep item done **and**, for same-repo null-`stop_stage` deps, PR exists) and every consumer — both resolution tiers, the queue spawn-next step, linear/slack spawns — points at it.
**Why**: A hard-coded `{hydrate, ship, review-pr}` completion set fired on stage *entry* under `/fab-fff` — every hydrate/ship transition emitted completion each tick and drove premature removal (100% reproducible, 2026-08-28). Same-repo dependencies were once gated only on the branch resolving in `branch_map`, which is written at spawn, so a running dep looked satisfied; only the completion signal protected the queue. PR-exists is the cheapest observable proof a dep branch is pushed and stable for cherry-pick or a stacked retarget.
**Rejected**: Keeping `{hydrate, ship}` in the set with an added `display_state` check — `hydrate/done` is a transient window in `/fab-fff` (finish auto-activates ship), so it still races. Branch-resolvable ⇒ satisfied. A parked-`/fab-ff` heuristic without `stop_stage`.
*Introduced by*: 260828-nr3a-tick-completion-review-pr-only; *Updated by*: 260911-4a8m-operator-generic-tracked-items (the built-in predicate emits the item's `done` delta)

### Quiet Tick Replaces `items:` With Counts; Compact One-Line Frame on No-Change Ticks

**Why**: Every tick appending a full items document plus a full frame grew context linearly with wall-clock time on a quiet fleet and buried real events in identical frames. **Rejected**: A flag or config knob for the interval (hardcoded 10 mirrors the §5 30m precedent); emitting `fleet_summary:` alongside `items:` (no byte saving); a small table for the compact frame (one line is the point); making `--quiet` the default of `--diff` (breaks byte-identity); a Go daemon heartbeat (`[2ne8]`, separate).

### Binary Derives the Cron Schedule From the Tracked Set
**Decision**: the schedule is a pure function of the items' `check_every` values, applied through `rk cron edit` only on change; user overrides are bounded by `--for`. The deliver policy is `skip-if-busy` on every derived branch (backoff, every, idle-every) and on the bounded `clock_override`; the backoff branch — a pane/none-only set — is a fallback poll behind `wake_on: agent-state-change` and runs `3m → 24m`.
**Why**: a per-tick LLM cadence judgment is conversation-only state, the same failure class as the #913 incident. One deliver policy: `immediate` injects a tick mid-turn (queued as a mid-turn message on Claude, less predictable on other providers), and a per-branch table changed the operator's delivery semantics silently whenever a shell/agent item joined or left the tracked set. Ladder bounds: a 1-minute floor buys almost no latency over the wake event and mostly buys token spend; a 30-minute ceiling exceeds the operator's own 10-minute full-frame window. Accepted cost: under `skip-if-busy` a tick landing mid-turn is dropped, so on the backoff branch a drop at a long rung delays the fallback poll by up to that rung (≤ 24m) — `wake_on` fires independently, so a real fleet event never waits for the rung.
**Rejected**: LLM-issued `rk cron edit` per tick; unbounded overrides. `when-idle` on the backoff branch (holds the fire until idle — no tick lost, no rung paid twice — rejected for policy uniformity: a third policy on one branch rebuilds the per-branch table under another name). `immediate` on the backoff branch (mid-turn injection; the per-branch table).
*Introduced by*: 260911-4a8m-operator-generic-tracked-items; *Updated by*: 260911-tnmm-operator-clock-skip-if-busy-ladder

### Operator Reads Plans, Never Executes (kp3d)
**Decision**: The §1 "Keep context lean" row (never read intake/spec/plan artifacts) is deleted outright — the operator reads any plan, roadmap, intake, or task document it needs to drive tracked work to completion, with no replacement condition. The §1 "Coordinate, don't execute" row is the single work rule: every user task, bug report, or idea is a work request entering via §6 Working a Change (`/fab-new` spawn in a fresh worktree; a send for a live tracked item); reading code to diagnose or editing files in the operator pane counts as executing; direct actions are a closed maintenance allowlist (merge PR, archive, worktree deletion, rebase/cherry-pick for dependency resolution, `fab operator track` verbs, pane sends/answers/nudges); the only question about a work request is which repo.
**Why**: Two 2026-09-11 incidents. (1) Handed a bug, the operator reproduced and fixed it inline — the old row had no trigger clause, and "ask when ambiguous" + "maintenance-level actions such as…" read as outs; diagnosis was treated as not-execution. (2) Asked to "check the rk-mcp plan" (W0/W1 merged, W2–W4 unspawned), the operator refused to read the roadmap, citing the read-prohibition, and asked the user what the next phase should cover. The read rule existed for context budget (PR #550 era); the server-keyed state file + §4 Post-Compaction Reload already make the operator survive context loss, so the rule's cost (cannot sequence a roadmap) exceeded its benefit. User direction: remove conditions rather than add them; the one condition that stays is "never execute in the operator pane".
**Rejected**: Adding a "bug report = work request" clause beside the existing rows (adds conditions). Relaxing the read rule to "on demand only" or an allowlist of document kinds (new conditions; the rk-mcp roadmap was not a fab artifact). Keeping "ask when ambiguous" (the stall hatch the incident exercised).
*Introduced by*: 260911-kp3d-operator-read-plans-never-execute

### Periodic Full Refresh Is Time-Based (`last_full_at` ≥ 10m), Not a Tick Count
**Decision**: `fab operator tick-start --diff --quiet` emits the full `items:` document whenever the state file's `last_full_at` is at least 10 minutes old (built-in constant `tickQuietFullAfter`, no flag or config knob), and every full document — quiet-mode-or-not, delta- or needs_check-forced or age-forced — rewrites `last_full_at` (RFC3339 UTC) inside the same atomic tick mutation as `tick_count`/`last_tick_at`. A missing, unparseable, or future stamp counts as due. The every-10th-tick count constant is deleted.
**Why**: The operator's clock is run-kit's cron entry with backoff `3m → 24m`, so "every 10th tick" is a count over a variable interval — roughly every 30 minutes at the floor but about 4 hours at full backoff, which is the "frequency is too low" the user observed on 2026-09-11. A wall-clock age is cadence-agnostic: every tick is full once the cadence reaches 10 minutes, which is the right answer for a tick that rare. The binary already owns the tick bookkeeping and the full/quiet decision, so one more scalar in the same mutation is the smallest correct change.
**Rejected**: A flag or config knob (the "Quiet Tick Replaces `items:` With Counts" rejection stands — the §5 hardcoded-30m idle default is the same posture). A skill-side timer (the skill keeps no counter or timer by design). Deriving the interval from the cron schedule (couples fab to run-kit's schedule shape for nothing a duration does not already give). An HTML fleet table written by fab beside the state file — run-kit already consumes the operator state YAML at the pinned cross-repo path, so any fleet UI is run-kit's to render; fab writes no HTML.
*Introduced by*: 260911-5ubz-operator-time-based-full-refresh

### Pane Is the Identity; Change Is Observed
**Decision**: The operator's core tracked kind is `pane` — **any agent session in a tmux pane** — joined on `scope.pane` plus a `scope.pane_pid` shell-pid fingerprint (recorded whenever a verb sets the pane; null ⇒ pane-id-only join). A fab change, when present, is an **observed**, baseline-maintained field (`scope.change`, maintained by the tick's baseline writer exactly like `scope.stage`): a change appearing or switching emits a consumed-on-read `changed` delta (`fields: {change: {from, to}}`), never a pane-level delta; an unresolved snapshot change is sticky-silent (no delta, baseline untouched); a first-observed change writes `branch_map[<change>] = {branch, repo}` (the branch resolved once from the pane's cwd, retried on later ticks while the entry stays absent). The built-in completion predicate splits on `scope.change` — non-null ⇒ `review-pr` done/skipped or at/past `stop_stage`; null ⇒ never done on its own. The item id is the change id when known at spawn, else the worktree name, and is never renamed when a change later appears (dependents reference item ids; `branch_map` is keyed by change). Raw-text spawns are tracked at spawn under the worktree name, closing the gap where a raw spawn ran `/fab-new` before any change id existed (backlog `lm49`). Pipeline-first and spawn-in-a-worktree bind **spawns**, not tracking — tracking an existing pane the user points at needs no gate and no kind question.
**Why**: The old change-keyed kind made the join key and the watched object disagree: the binary emitted a pane-level mismatch every tick for any pane whose resolved change differed from the item id (a raw-text spawn before its change existed, a fresh change, a change switch), and the kind's name itself told the operator a change-less pane "does not fit", so it refused to track a live agent the user pointed at. The pane is what the operator actually watches; making the join honest — pane id plus a fingerprint only a recycled pane can fail — lets the change be what it is: an observed attribute, diffed and reported like the stage. `pane_pid` was already dispatch's recycle discriminator (`PaneWorkerAlive`), so the operator adopts a proven fingerprint rather than inventing one, and one batched `tmux list-panes -a` keeps the per-tick cost at one subprocess on any fleet size, rk-less servers included.
**Rejected**: Keeping the old change-keyed kind name and only relaxing the join (the name itself drove the tracking refusal — the rename is the skill-side half of the fix; the migration catalog names the retired spelling); naming the kind `agent` (collides with the existing `agent` probe mode for linear/slack items); `pane_start_time` as the fingerprint (empty on tmux 3.7c); one `tmux display-message` pid lookup per tracked item per tick (N subprocesses vs. one batched `list-panes -a`); renaming the item id when a change appears (breaks dependents for no benefit — `branch_map` keys by change).
*Introduced by*: 260911-1159-operator-pane-kind-pid-fingerprint

### `pane_mismatch` Means Recycled Pane Only
**Decision**: `pane_mismatch` fires only when the recorded `scope.pane_pid` is non-null AND the pane's current shell pid (from the tick's one batched `tmux list-panes -a -F '#{pane_id} #{pane_pid}'` fetch) differs — tmux recycles `%N` pane ids across server restarts while the socket-keyed state file survives, and a differing fingerprint proves the pane is not the one tracked. A null recorded fingerprint or an unreadable current pid joins on the pane id alone (an unreadable pid is never a mismatch — the posture dispatch's `PaneWorkerAlive` already applies). The delta's `found:` field carries the observed change id or null; the observed change never participates in the mismatch decision. Per-item evaluation order stays `pane_death` → `pane_mismatch` → `agent_exited` → clean join, and a mismatched pane gets no baseline write, no stage/change diff, and no `candidates:` row.
**Why**: The delta previously conflated two events — a genuinely recycled pane (the case it was designed for) and a change legitimately appearing or switching in a watched pane — so the level-triggered delta re-emitted every tick until `track rm`, telling the operator to remove an item it should keep watching. One delta, one meaning: the recycled pane.
**Rejected**: The old change-id comparison (misfires for raw-text spawns, fresh changes, and change switches); treating an unreadable pid as a mismatch (violates the unreadable-is-not-a-mismatch posture); reporting a change appear/switch as `pane_mismatch` (that is the consumed-on-read `changed` delta's job).
*Introduced by*: 260911-1159-operator-pane-kind-pid-fingerprint

### Five-Bucket Classification Governs Which `run-kit` Tokens Flip
**Decision**: Every `run-kit` occurrence in kit content is classified before editing into A (present-tense product noun → HexoKit), B (`rk`-prefixed substrate → untouched), C (repo / formula / PR identifier → untouched until the deferred renames), D (past-tense narrative → untouched), or E (frozen migration → untouched). Section headings that name the product are bucket A and rename with a same-change pointer sweep.
**Why**: The rebrand renames the product, not the substrate (plan D2) and not history (D11); GitHub, Homebrew, and PR identifiers are external objects that keep their names until R1/R2. A search-and-replace would corrupt all three classes, and leaving the headings would keep "Run-Kit" in the always-loaded preamble after the product stopped being called that.
**Rejected**: (a) flip every `run-kit` token — breaks formula install lines and repo-scoped PR references, and rewrites history; (b) flip nothing but the README — leaves deployed skills naming a product that no longer exists under that name, propagating into customer repos via `fab sync`; (c) rename headings without sweeping pointers — leaves dead `§` anchors, a review must-fix.
*Introduced by*: 260911-y50t-hexokit-banner-sweep

### Non-Fab Repos Get a Plain Agent, Never the Operator's Hands, Never an Unprompted fab init
**Decision**: When a work request targets a repo with no `fab/` directory, the operator still spawns an agent in a fresh worktree through the same §6 spawn sequence, sends the raw task text plus a commit/push/draft-PR instruction (no skill prefix), tracks it as a change-less `pane` item keyed by worktree name with no `--stop-stage`, and completes it through a chained `github-pr` item. Pipeline-first binds only repos with a `fab/` project. The operator never runs `fab init` and never offers it as a menu; it may mention it once as an option in a report.
**Why**: The skill prohibited executing in the operator pane but offered only `/fab-new`-based delegation forms, so a non-fab repo was a dead end the operator improvised out of — a three-way menu whose "direct edit" option was the one prohibited action and whose very existence broke the which-repo-only ask. The spawn sequence already works without `fab/` (`wt` is repo-agnostic, `fab agent --repo` degrades to the project-free cascade, the `pane` kind tracks change-less panes), so the fix is a named form, not a mechanism.
**Rejected**: Letting the operator edit directly in non-fab repos (contradicts the single never-execute constraint). Making `fab init` the default (a repo-structure decision that is the user's). Go-side non-fab detection or `fab init` automation (a one-line existence check the skill makes itself).
*Introduced by*: 260911-pudv-operator-non-fab-repo-plain-agent
