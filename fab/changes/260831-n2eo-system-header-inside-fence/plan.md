# Plan: System Scaffold Header Inside the Fence

**Change**: 260831-n2eo-system-header-inside-fence
**Intake**: `intake.md`

## Requirements

### Rendering: Fence-Owned Header

#### R1: The System Header Renders Inside the Managed Fence
`SystemScaffoldHeader`'s content SHALL be emitted inside the system target's managed fence
(between the BEGIN and END anchors), above the existing `fenceHeaderComment` prose. It SHALL
NOT be emitted above the fence. A `~/.fab-kit/config.yaml` SHALL therefore open with its first
live YAML key, or — when nothing is overridden — with the fence BEGIN anchor.

- **GIVEN** a system config with live `dispatch:` and `agent:` blocks
- **WHEN** `fab config upgrade --system` runs
- **THEN** line 1 of the file is `dispatch:` (a live key), not a comment
- **AND** the header text appears exactly once, inside the fence anchors

- **GIVEN** a system config with no overrides at all
- **WHEN** `fab config upgrade --system` runs
- **THEN** the file opens with the fence BEGIN anchor and the header sits inside it

#### R2: No Binary-Owned Text Is Written Above the Fence (the ownership invariant)
For the system target there SHALL be no code path that writes fab-generated text above the
fence. The region above the fence SHALL contain only user content: live keys and the user's own
comments. This makes the v2.23.8 two-copy outcome structurally impossible rather than merely
unlikely.

- **GIVEN** a v2.23.8-shaped file whose header a user has EDITED
- **WHEN** `fab config upgrade --system` runs
- **THEN** the binary writes NO header copy above the fence
- **AND** the above-fence copy that remains is the user's own edited text, preserved by R10a
- **AND** the inside-fence copy is the pristine canonical text
- **NOTE** two copies is the CORRECT outcome here and does not violate this requirement: the
  only way to reach one copy would be to delete the user's edited text, which R10a forbids.
  The invariant is about who WRITES above the fence, not about total copy count.

- **GIVEN** a user comment above the fence (e.g. `# work laptop only`)
- **WHEN** `fab config upgrade --system` runs
- **THEN** that comment survives above the fence

#### R3: The Redundant Generator Sentence Is Folded, Not Duplicated
The header's "This scaffold is generated by `fab config init --system` and refreshed by
`fab config upgrade --system` …" sentence states the same fact the fence prose already states.
It SHALL be folded into the fence prose so the claim exists once (owner-or-pointer,
`fab/project/code-quality.md`).

- **GIVEN** the regenerated system config
- **WHEN** a reader looks for "this content is regenerated"
- **THEN** that claim appears exactly once inside the fence

### Engine: Decoupling

#### R4: The Legacy-Paragraph Discard Is Independent of Header Presence
`normalizeTargetPreamble`'s early return on `target.Header == ""` currently gates BOTH header
installation AND the R10a line-complete legacy-paragraph discard. These SHALL be separated: the
discard SHALL be gated by its own predicate (e.g. `adoptLegacyFile`), so removing the preamble
header does not disable legacy adoption.

- **GIVEN** a legacy unfenced system scaffold from a released version
- **WHEN** `fab config upgrade --system` runs after this change
- **THEN** its generated paragraphs are still discarded and replaced by the fence
- **AND** exactly one advert per field appears (no duplication)

- **GIVEN** the m4ai R10a regression suite
  (`TestSystemUpgrade_AdoptsReleasedHistoricalScaffoldsAfterRegistryDrift`,
  `TestSystemUpgrade_LineCompleteAccounting*`, `TestSystemMutation_LineCompleteAccounting*`)
- **WHEN** the suite runs against this change
- **THEN** every test passes, and any test-body edit is mechanically forced by R1 (not a weakening) and is individually justified as conformed-to-changed-spec

### Parity

#### R5: `init --system` and `upgrade --system` Render the Same Shape
Both doors SHALL produce byte-identical structure for equivalent input. `RenderSystemScaffold`
and the upgrade render path already share `assemble` and `SystemTarget`, so the relocation
SHALL be made at that shared seam rather than in either caller.

- **GIVEN** a machine with no system config
- **WHEN** `fab config init --system` writes one, then `fab config upgrade --system --check` runs
- **THEN** `--check` reports the file already up to date and exits 0

#### R6: Already-Shipped v2.23.8 Files Relocate Without Duplication
A file previously written by v2.23.8 carries the header above the fence. The first
`--system` run after this change SHALL relocate it — recognizing the v2.23.8 header rendering
as generated content and discarding it — leaving exactly one copy inside the fence.

- **GIVEN** a `~/.fab-kit/config.yaml` produced by v2.23.8's `upgrade --system`
- **WHEN** `fab config upgrade --system` runs after this change
- **THEN** the header appears exactly once, inside the fence
- **AND** all live keys and their values are byte-identical to before
- **AND** `fab config show` output is unchanged

#### R7: Project Target Unchanged
`fab/project/config.yaml`'s rendered shape SHALL be unchanged — its reference header already
lives inside its fence region and `initHeader` is a separate project-only constant.

- **GIVEN** an existing `fab/project/config.yaml`
- **WHEN** `fab config upgrade` runs
- **THEN** the output is byte-identical to what the pre-change binary produced

### Documentation

#### R8: Memory and Spec Reflect the Fence-Owned Header
`docs/memory/_shared/configuration.md` and `docs/specs/config.md` SHALL describe the system
file's shape as fence-owned header + user-owned region above, and record the ownership
rationale as a Design Decision.

- **GIVEN** the change is complete
- **WHEN** a reader consults the memory's managed-fence section
- **THEN** it states the header is inside the system fence and the above-fence region is the user's

### Non-Goals

- Deleting the header outright — its precedence rule is the file's least obvious fact.
- Changing the project config's shape or `initHeader`.
- Changing R10a's preserve-on-doubt semantics — this change removes a region from doubt, it does not relax the rule.
- A `src/kit/migrations/` file — machine-level config is outside the per-project migration vehicle (same rationale m4ai recorded).
- Any CLI flag or signature change.

### Design Decisions

#### Relocate the Header, Do Not Delete It
**Decision**: Move `SystemScaffoldHeader`'s content inside the managed fence rather than removing it.
**Why**: The header carries the one non-obvious fact about the file — it outranks every repo's committed config for preference-class fields. Deleting it would make the file cleaner and less discoverable simultaneously. Inside the fence it is equally readable, honestly labelled as regenerated, and adjacent to the field adverts it belongs with.
**Rejected**: Dropping `Target.Header` for the system target entirely (loses the precedence explanation); leaving it above the fence and documenting "don't bother deleting it" (the duplication defect in R2 stays).
*Introduced by*: 260831-n2eo-system-header-inside-fence

#### Ownership, Not Layout, Is the Justification
**Decision**: Treat the change as fixing an ownership defect: inside-fence is binary-owned, above-fence is user-owned, with no overlap.
**Why**: Verified on v2.23.8 that an EDITED header yields two copies — R10a preserves the user's paragraph as unaccounted content while the binary installs a fresh pristine header. The region was therefore neither customizable (your text is buried) nor cleanable (deletion does not stick). Removing the competing writer resolves it; the tidier top-of-file is the visible consequence.
**Rejected**: Making R10a smarter about headers — R10a was behaving correctly (preserve on doubt); the defect is having two writers for the same lines, not the arbitration between them.
*Introduced by*: 260831-n2eo-system-header-inside-fence

#### Relocate at the Shared `assemble` Seam
**Decision**: Make the change where `RenderSystemScaffold` and the upgrade path already converge (`assemble` + `SystemTarget`), not in either caller.
**Why**: Both doors call `assemble(target.Header, fence, …)` with the same `SystemTarget`, so a single change at that seam gives `init`/`upgrade` parity for free and makes divergence impossible by construction rather than by matching test.
**Rejected**: Patching `RenderSystemScaffold` and the upgrade render path separately (two places to keep in sync — the drift class `--check` exists to catch).
*Introduced by*: 260831-n2eo-system-header-inside-fence

#### Separate the Discard Gate from Header Presence
**Decision**: Gate the R10a legacy-paragraph discard on its own predicate, independent of whether `Target.Header` is non-empty.
**Why**: `normalizeTargetPreamble` returns early on `Header == ""`, and that same function performs the discard. Blanking the header to relocate it would silently disable legacy adoption, reintroducing the duplicated-advert bug that two m4ai review cycles were spent eliminating. The coupling is invisible at the call site, so it must be broken explicitly and documented.
**Rejected**: Keeping a sentinel non-empty header purely to keep the discard alive (preserves the bug's cause while hiding it better).
*Introduced by*: 260831-n2eo-system-header-inside-fence
