# Plan: Auto Pane Dispatch Inside tmux

**Change**: 260805-l9ng-auto-pane-dispatch-in-tmux
**Intake**: `intake.md`

## Requirements

### Runtime: `fab dispatch start` mode selection

**R1** — `fab dispatch start` SHALL resolve its launch mode from an explicit-signal-first ladder rather than defaulting unconditionally to headless. The ladder, evaluated in order, is:

1. Explicit `--pane` → **pane** mode (existing semantics unchanged: `ServerReachable` probe, hard error and nothing persisted when unreachable).
2. Explicit `--headless` → **headless** mode.
3. Explicit `--timeout` (`Flags().Changed("timeout")`) → **headless** mode.
4. Explicit `--server` (`Flags().Changed("server")`) → **pane** mode (the flag's only purpose is pane targeting).
5. No explicit signal → **auto**: `$TMUX` non-empty in the process environment → **pane**; otherwise → **headless**.

The mode selection SHALL be a pure, table-testable function in `internal/dispatch` taking the four explicit signals plus the `$TMUX` value and returning the resolved mode plus whether auto fired.

- **GIVEN** no mode-related flag and `$TMUX` unset
- **WHEN** `fab dispatch start <change> <stage>` runs
- **THEN** the mode resolves to headless (today's behavior, byte-preserved)

- **GIVEN** no mode-related flag and `$TMUX` set to a tmux socket string
- **WHEN** `fab dispatch start <change> <stage>` runs
- **THEN** the mode resolves to pane, targeting the current server (no `-L` passed unless `--server` was given)

- **GIVEN** `--timeout 600` and `$TMUX` set
- **WHEN** `fab dispatch start <change> <stage> --timeout 600` runs
- **THEN** the mode resolves to headless (a timeout is only meaningful there) and the timeout is honored in the wrapper

- **GIVEN** `--server work` with `$TMUX` unset and no `--pane`/`--headless`
- **WHEN** `fab dispatch start <change> <stage> --server work` runs
- **THEN** the mode resolves to pane against socket `work`

**R2** — A new `--headless` boolean flag SHALL exist on `fab dispatch start` as the explicit opt-out from auto pane selection, and `--pane` + `--headless` SHALL be a usage error (exit 2, enforced by cobra's `MarkFlagsMutuallyExclusive` before any `RunE` work — the repo's mutual-exclusion precedent in `resolve.go` / `pane_capture.go` / `panemap.go`), launching nothing and persisting nothing. `--headless` + `--timeout` SHALL compose (both select headless). The existing `--pane` + `--timeout` usage error SHALL remain unchanged.

- **GIVEN** `--pane --headless`
- **WHEN** `fab dispatch start` runs
- **THEN** it exits non-zero naming both flags, launches nothing, and writes no dispatch record

- **GIVEN** `--headless --timeout 600` inside tmux
- **WHEN** `fab dispatch start` runs
- **THEN** the dispatch is headless with `timeout: 600` recorded

**R3** *(revised in rework cycle 1)* — When pane mode was selected by **auto** (not by an explicit flag), `start` SHALL **soft-fall-back to headless** whenever the pane path cannot proceed — for **both** failure shapes: **(a)** `ServerReachable` fails (unreachable/stale tmux), and **(b)** the resolved provider carries **no `session_command`**. In both shapes it prints a one-line notice to stderr (shape (a): `pane auto-selection: tmux unreachable, falling back to headless`; shape (b) names the missing `session_command` analogously) and proceeds with the headless launch (re-composed from `dispatch_command`, honoring the no-cross-fallback rule — a provider lacking *both* commands still errors with the `dispatch_command` hint), producing a headless-shaped dispatch record. To make shape (b) reachable, `runDispatchStart` SHALL NOT hard-fail on pane-command composition before the auto-fallback decision point — composition of the pane command is deferred until auto-selected pane mode is validated (probe passed AND `session_command` present). A `dispatch_command`-only provider that worked headless before this change MUST keep working under auto inside live tmux. When pane mode was selected **explicitly** (`--pane`, or `--server` acting as the pane signal), the existing **hard errors** SHALL apply to both shapes — non-zero exit, nothing launched, nothing persisted.

- **GIVEN** `$TMUX` set to a stale/dead socket and no mode flag
- **WHEN** `fab dispatch start <change> <stage>` runs
- **THEN** stderr carries the one-line fallback notice, the launch is headless, and `{stage}.yaml` records `pid`/`pgid` with no `pane`/`window`/`server`

- **GIVEN** a provider carrying `dispatch_command` but no `session_command`, `$TMUX` pointing at a **live** tmux server, and no mode flag
- **WHEN** `fab dispatch start <change> <stage>` runs
- **THEN** stderr carries a one-line notice naming the missing `session_command`, the launch is headless, and the record is headless-shaped — the pre-change headless behavior is preserved, not regressed into an error

- **GIVEN** an unreachable tmux server and an explicit `--pane`
- **WHEN** `fab dispatch start <change> <stage> --pane` runs
- **THEN** it exits non-zero and persists no record (unchanged)

- **GIVEN** a provider with no `session_command` and an explicit `--pane` (or pane-signaling `--server`)
- **WHEN** `fab dispatch start` runs
- **THEN** it exits non-zero with the `providers.<name>.session_command` hint and persists no record (unchanged)

**R4** *(extended in rework cycle 1)* — The `dispatched <id>/<stage> (<report>)` output line SHALL name the selection source when auto fired, so a surprising mode is explainable from output (the compliance-visibility principle). Auto-selected pane reports `pane %N, window fab-<id>-<stage>, auto: tmux`; auto-selected headless reports `pid N, pgid N, auto: no tmux`; an explicitly-selected mode's report is **byte-identical to today** (no suffix). A soft fallback reports the headless identity plus its trigger — `auto: tmux unreachable` for shape (a), an analogous named-constant reason for shape (b) (missing `session_command`).

- **GIVEN** auto-selected pane mode
- **WHEN** the dispatch starts
- **THEN** stdout reads `dispatched <id>/<stage> (pane %N, window fab-<id>-<stage>, auto: tmux)`

- **GIVEN** an explicit `--pane` or `--headless`
- **WHEN** the dispatch starts
- **THEN** stdout carries no `auto:` suffix

### Non-Goals

- No `dispatch.default_mode` config knob in v1 — the env default plus two explicit flags cover the matrix; a knob is additive later.
- No change to native Agent-tool dispatch, the skills' `dispatch=` branch, adapter selection, the five-state / three-state machines, the result-file contract, or the prompt-delivery mechanism.
- No run-kit-specific detection beyond `$TMUX`.
- `ServerReachable` remains the *validation* step (a real tmux query); `$TMUX` is only the *defaulting* signal. Neither replaces the other.

### Design Decisions

**Decision**: Mode selection is a pure function `dispatch.SelectMode(paneFlag, headlessFlag, timeoutSet, serverSet bool, tmuxEnv string) (Mode, AutoReason)` in `internal/dispatch`, called from `runDispatchStart`'s prologue.
**Why**: The ladder is the whole behavioral surface of this change and has seven interacting inputs; a pure function is table-testable without launching a process or a tmux server, matching the `DeriveState`/`DerivePaneState` precedent in the same package.
**Rejected**: Inline `if` chain in `runDispatchStart` (untestable without real launches, and the existing file already delegates every derivable rule to `internal/dispatch`).
*Introduced by*: 260805-l9ng-auto-pane-dispatch-in-tmux

**Decision**: `--pane`/`--headless` exclusion uses cobra's `MarkFlagsMutuallyExclusive`, not a hand-rolled `Flags().Changed` check in `RunE`.
**Why**: It fires during `ValidateFlagGroups` before any `RunE` work, so it is a genuine exit-2 usage error per the binary's exit-code convention and structurally cannot leave partial state — matching `resolve.go`, `pane_capture.go`, and `panemap.go`. (The pre-existing `--pane`+`--timeout` guard stays in `RunE` because it is unchanged behavior with a pinned message.)
**Rejected**: A `RunE` `Flags().Changed` pair-check (exit 1, duplicates machinery cobra already owns).
*Introduced by*: 260805-l9ng-auto-pane-dispatch-in-tmux

**Decision**: The soft fallback is asymmetric — auto-selected pane degrades to headless with a stderr notice; explicitly-selected pane keeps its hard error. The fallback covers **both** pane-path failure shapes: an unreachable tmux server **and** a provider with no `session_command` (pane-command composition is deferred until auto-selected pane mode is validated, so shape (b) is reachable).
**Why**: A stale `$TMUX` (inherited from a killed server) must never break an unattended dispatch that never asked for a pane; a `dispatch_command`-only provider that worked headless before the auto default must not start failing merely because the user is inside tmux; conversely, a caller who typed `--pane` asked for watchability and a silent downgrade would defeat it.
**Rejected**: Hard error under auto (a stale env var breaks unattended runs — and, for shape (b), every CLI-dispatched stage of a `dispatch_command`-only provider inside run-kit would regress outright). Soft fallback under explicit `--pane` (silently discards the caller's stated intent). Composing the pane command before mode validation (makes shape (b) unreachable — the original review must-fix).
*Introduced by*: 260805-l9ng-auto-pane-dispatch-in-tmux
