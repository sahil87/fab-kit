## Requirements

### Kit: the user-level operator skill (`src/kit/templates/user-skill-fab-operator.md`)

#### R1: A pointer template, not a copy
The kit MUST ship `src/kit/templates/user-skill-fab-operator.md`: frontmatter `name: fab-operator` and `description: {DESCRIPTION}` only; a "Generated by `fab sync` — do not edit" note; and exactly two normative rules — (1) inside a fab project (`fab/project/config.yaml` at or above the cwd) read that project's `.agents/skills/fab-operator/SKILL.md` and follow it, falling through to (2) if it is missing; (2) otherwise run `fab kit-path`, read `<kit-path>/skills/fab-operator.md` and follow it, reading `<kit-path>/skills/{x}.md` wherever that skill or `_preamble` says `.agents/skills/{x}/SKILL.md`. It MUST NOT carry operator logic, a `helpers:` list, or any fab-kit-only path (Constitution V; the portability guard walks `src/kit/**`).

- **GIVEN** the template rendered with the operator's `description:`
- **WHEN** a harness discovers it at `~/.claude/skills/fab-operator/SKILL.md` and the user is in `$HOME`
- **THEN** rule 2 sends the agent to the installed kit's `fab-operator.md` and helpers

- **GIVEN** the same file and a cwd inside a synced fab project
- **WHEN** `/fab-operator` runs
- **THEN** rule 1 sends the agent to the project's deployed copy, so project semantics are unchanged

### fab-kit module: the writer (`src/go/fab-kit/internal/skills.go`, `sync.go`)

#### R2: `deployUserOperatorSkill` writes two tiers under the shared Claude gate
`deployUserOperatorSkill(kitDir string, claudeAvailable bool) error` MUST render the template with `{DESCRIPTION}` taken from the `description:` frontmatter line of `<kitDir>/skills/fab-operator.md` and write it to `$HOME/.agents/skills/fab-operator/SKILL.md` unconditionally and to `$HOME/.claude/skills/fab-operator/SKILL.md` only when `claudeAvailable`. It MUST be rewrite-if-differs (byte compare before write), MUST create no `.gitignore`/manifest, MUST never list, read, or touch sibling skill directories, and MUST preserve an existing Claude-tier file when the gate is closed. `$HOME` comes from `os.UserHomeDir()`.

- **GIVEN** a kit with the template and `claude` on PATH
- **WHEN** the helper runs twice
- **THEN** both files exist after the first run with `name: fab-operator`, the description verbatim, and the literal `fab kit-path`; the second run writes nothing

- **GIVEN** `claude` absent and a pre-existing `~/.claude/skills/fab-operator/SKILL.md`
- **WHEN** the helper runs
- **THEN** only the `.agents` tier is written and the Claude file is byte-identical afterwards

#### R3: Pre-feature kits are a silent no-op; failures fail the sync
When `<kitDir>/templates/user-skill-fab-operator.md` does not exist the helper MUST return `nil` and write nothing (a project pinned to an older kit must keep syncing). A missing `description:` line, an unresolvable `$HOME`, or a write failure MUST return an error. `Sync` MUST call the helper inside `if !projectOnly`, immediately after `deploySkills`, joining its error into `deployErr` (`errors.Join`) so the run exits non-zero after the remaining repair steps. Output is one tally-style line per run (`written` / `up to date` / a Claude-tier skip line).

- **GIVEN** a fixture kit without the template
- **WHEN** `deployUserOperatorSkill` runs
- **THEN** it returns `nil` and `$HOME` is untouched

Never Fail; the package writes nothing; the header comment's "read at most one file" sentence is updated to name the additional read-only reads.

- **GIVEN** both tiers present with the current description and `claude` on PATH
- **WHEN** `fab setup check` runs
- **THEN** two OK findings under `user-skills` and exit 0

- **GIVEN** the `.agents` tier missing

### Design Decisions

#### The User-Level Operator Skill Is a Pointer Written Only by `fab sync`
**Decision**: `fab sync` (fab-kit module) renders `templates/user-skill-fab-operator.md` into `~/.agents/skills/fab-operator/SKILL.md` (always) and `~/.claude/skills/fab-operator/SKILL.md` (Claude gate), rewrite-if-differs, no manifest. The file defers to a project's deployed copy when inside a fab project and otherwise points at `$(fab kit-path)/skills/`. `fab setup check` reports presence and staleness; nothing else writes it.
**Why**: The operator is a cross-repo singleton launched from a neutral cwd (2sdj), and the cron respawn `rk operator -L` opens in `$HOME`, where no project skill resolves. A copy of the operator prose would drift every release; a pointer drifts nothing. Claude Code lets a personal skill win over a same-named project skill, so the pointer must itself hand back to the project copy. `fab setup` lives in the other Go module and cannot share the writer; `Sync` already runs on every `init`, `upgrade-repo`, and `sync`, so it is sufficient coverage.
**Rejected**: A full user-level copy of skill plus helpers (drift); changing rk's `-L` cwd (contradicts 2sdj); a `fab operator` launcher writer (misses the cron path; wrong module); a `fab setup` writer (module boundary → duplicated writer); a Go string template (prose belongs in markdown, Constitution I); a `.agents/skills/`-exists predicate for rule 1 (self-reference from `$HOME`).
