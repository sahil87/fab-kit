# Intake: Config Upgrade — System Scaffold Regeneration

**Change**: 260830-m4ai-config-upgrade-system-scaffold
**Created**: 2026-08-30

## Origin

Surfaced during a `/fab-discuss` session on 2026-08-30 while inspecting the user's own
`~/.fab-kit/config.yaml`. The user asked for two commented examples to be added to the
system scaffold — `agent.profiles.operator.provider` (override one role's provider) and a
per-provider/per-role model fill (`providers.claude.profiles.default`). Investigation showed
**both already ship in 2.23.7**; the user's on-disk file simply predated them, because the
system layer has no regeneration path at all.

> **User input**: "both. And lets stay consistent - if project configs are updated using
> `fab config upgrade` - then then system config should use that door too"

The two examples the user asked for are therefore **already implemented** and are NOT in scope.
The real defect is the missing door. Key decisions from the conversation:

1. The regeneration verb is **`fab config upgrade --system`** — explicitly *not* a new
   `init --refresh` flag. The user's stated reason is surface consistency: one upgrade door
   for both config layers.
2. The managed region is delimited by a **managed fence**, reusing the project layer's
   existing BEGIN/END anchor machinery (chosen over a header-anchored comment region and over
   a whole-file rebuild).
3. Adoption **reorders live keys above the fence**, matching `fab/project/config.yaml`
   convention, accepting a one-time visible reshuffle of the user's file.

## Why

**The problem.** `~/.fab-kit/config.yaml` is frozen at whatever kit version first created it.
`fab config upgrade` targets `fab/project/config.yaml` only ("Requires a fab repo (walks up
for `fab/`)"), and `fab config init --system` refuses to touch an existing file — it errors
with *"refusing to overwrite existing system config … (it is user-owned once created; edit it
directly or remove it first)"* (`src/go/fab/cmd/fab/config.go:1135`). There is no third path.

**The consequence.** Every knob added after a machine's system config was born is invisible on
that machine. The user's file was a live demonstration: it was missing the
`agent.profiles.operator` example line, the entire `providers.claude.profiles` fill map (six
roles), and the whole `autopilot.merge_mode` block. A user reading their own system config to
find out what they can set machine-wide gets a silently stale answer, and the deeper the kit
evolves the worse the drift. The scaffold's own header claims it "cannot drift from the
schema" — true at birth, false forever after.

**Why this approach.** The reconciliation engine already exists and is already correct:
`configupgrade.computeUpgrade` preserves live fields verbatim, regenerates the commented
fence, parks removed keys rather than deleting them, carries `renamed_from` renames, writes
atomically, and is byte-stable/idempotent. The system layer needs that same engine pointed at
a different path with a different field filter — not a second mechanism. Building a separate
`init --refresh` would fork the reconciliation logic in two, which is exactly the drift class
`fab config upgrade --check` exists to catch.

## What Changes

### 1. New `--system` mode on `fab config upgrade`

`fab config upgrade --system` reconciles `~/.fab-kit/config.yaml` instead of
`fab/project/config.yaml`. Bare `fab config upgrade` keeps its current project-only meaning —
the flag mirrors `fab config init --system` exactly, and `--project` remains the explicit
opposite spelling.

```
fab config upgrade                    # project config (unchanged behavior)
fab config upgrade --system           # ~/.fab-kit/config.yaml
fab config upgrade --system --check   # drift probe, writes nothing, non-zero exit on drift
```

Three behaviors differ from the project path:

- **No fab repo required.** The system config is machine-level and repo-independent. `--system`
  MUST NOT walk up for `fab/` and MUST NOT fail outside a fab project. This is the same posture
  `fab config init --system` already takes.
- **Scope filter.** Only fields with `scope: system` or `scope: both` are rendered into the
  fence, matching `renderSystemScaffold` (`src/go/fab/cmd/fab/config.go:1168`). A `scope: project`
  field (e.g. `stage_hooks`, `project.name`) MUST NOT appear.
- **Header.** The regenerated file keeps `configupgrade.SystemScaffoldHeader`
  (`mutation.go:26`) as its preamble, not the project `referenceHeader`. The header's current
  sentence "This scaffold is generated by `fab config init --system`" becomes inaccurate once
  upgrade also writes it and MUST be reworded to name both doors.

### 2. A managed fence for the system layer

Today the system scaffold is **unfenced** — verified: `grep '>>>\|<<<' ~/.fab-kit/config.yaml`
returns nothing, while the project config has anchors at lines 14 and 75. `SetSystem` is
explicitly documented as writing *"without introducing a project reference fence"*
(`mutation.go:113`), so this is a deliberate existing design being revised, not an oversight.

The fence is what gives upgrade a boundary between fab-owned comment lines and the user's own.
Reuse the project machinery — `fenceWidth`, the BEGIN/END anchor renderer, and `beginLineRe`,
which already matches "regardless of the stamped version or the dash-pad width"
(`configupgrade.go:76`) — rather than inventing a second anchor format.

Target shape after upgrade:

```yaml
# ~/.fab-kit/config.yaml — system-level fab config (all repos on this machine).
# ... (SystemScaffoldHeader, reworded)

dispatch:
  mode: pane

agent:
  session: claude
  workers: codex
  profiles:
    operator:
      provider: claude

# >>> fab reference (kit 2.24.0) >>> ---------------------------------------
# Overridable fields you have NOT overridden, with current defaults.
# REGENERATED by `fab config upgrade --system` on every upgrade — edits inside
# this fence are overwritten. To override a field: move it ABOVE the fence and
# uncomment it.
#
# agent.session / agent.workers — providers for the two agent DEPTHS: ...
# agent:
#   session: claude
#   ...
# <<< end fab reference <<< ------------------------------------------------
```

Note the fence body's explanatory preamble (`fenceHeaderComment`, `configupgrade.go:92`)
currently reads "REGENERATED by `fab config upgrade`" — under `--system` it must name the
`--system` form. Parameterize it rather than duplicating the constant.

### 3. Adoption of existing unfenced files

Every system config in the wild is unfenced, so the first `--system` run is an adoption, not a
reconciliation. The project side already has this exact case handled — *"A legacy file with no
fence gets one appended"* (`configupgrade.go:23`) — but the naive append is wrong here: the
legacy system file is **entirely comments plus live keys**, so appending a fresh fence would
leave the whole stale commented scaffold sitting above it as orphaned prose, duplicating every
block.

Adoption MUST therefore:

1. Recognize the legacy generated scaffold region (the commented blocks emitted by
   `renderSystemScaffold`: header + `CommentOutSegment(f.ShortSegment)` per system-scoped field)
   and **discard** it — it is fab-generated content being replaced, not user prose.
2. Preserve every **live** key verbatim, including any user comments attached to them.
3. **Hoist live keys above the fence**, matching project convention. The user's current file
   has them below the comment scaffold (a `set --system` artifact — `SetSystem` appends), so
   this is a one-time visible reordering.
4. Emit an advisory `Report` line naming the adoption, since the reshuffle is surprising.

A user comment that is *not* part of the generated scaffold must survive. If the
discard-the-scaffold recognition cannot be made safe, the fallback is to preserve unrecognized
comment lines above the fence rather than delete them — losing a user's note is worse than
leaving a stale duplicate.

### 4. Removed-key parking

Mirror the project behavior: a live key no longer in the registry is **parked** in a comment
block below the fence with its value serialized, never silently deleted
(`configupgrade.go:36`). This matters more for the system layer than the project one, because a
machine-wide setting is typically set once and never revisited.

### 5. `set --system` / `unset --system` fence awareness

`SetSystem` and `UnsetSystem` (`mutation.go:114`, `mutation.go:~95`) currently render without a
fence. Once a fence exists they must not corrupt or duplicate it: a `set --system` on a fenced
file MUST write the live key above the fence and leave the fence intact. The project-side
`Set`/`Unset` already do exactly this via `renderMutation`, so the fix is to route the system
variants through the same path with the system field filter and header.

**Verified regression risk**: `fab config set --system providers.claude.profiles.default.model`
currently emits mis-indented YAML — `model`/`effort` land at 10 spaces under a `default:` key at
6. It parses, but it is inconsistent with every other block. Worth correcting while this code is
being touched; flag if it turns out to be a deeper `setLivePath` issue than a local fix.

### 6. Migration vehicle — deliberately none

`fab/project/code-quality.md` requires that "restructuring existing user data" ship as a
`src/kit/migrations/` file. That rule does **not** apply here: migrations are applied per
project by `/fab-setup migrations`, and `~/.fab-kit/config.yaml` is machine-level, outside any
project — a per-project migration would run N times against one shared file. The adoption path
built into `upgrade --system` (item 3) is the correct vehicle. This exemption is deliberate and
should be recorded as a Design Decision so review does not flag it as a missing migration.

### 7. Docs and CLI reference

Per the constitution's Additional Constraints, a change to the `fab` binary's command
signatures MUST update `src/kit/skills/_cli-fab.md` and ship tests. `docs/specs/config.md`
documents the six-verb surface and must gain the `--system` upgrade mode.

### 8. `fab setup` self-heals the system scaffold

The interactive wizard (`fab setup`, shipped via `[stpw]`) is the natural place for the
scaffold to refresh itself without the user ever learning the verb. On entry — before the
scope banner and the first question — the wizard SHALL run the `upgrade --system`
reconciliation against `~/.fab-kit/config.yaml`.

Constraints, so this stays invisible when there is nothing to do:

- **Silent when clean.** If the reconciliation reports `Changed: false`, print nothing. The
  wizard's existing "all-Enter run = zero writes, idempotent" invariant (`[stpw]`) MUST hold.
- **One advisory line when it fires.** On a real change, print a single line naming what
  happened (e.g. `Refreshed ~/.fab-kit/config.yaml reference block (kit 2.24.0)`), then
  continue into the interview normally. Do not prompt.
- **Non-fatal.** A reconciliation error MUST warn and continue into the wizard, never abort
  it — the user came to set a value, not to maintain comments.
- **Entry point**: `runSetupWizard` (`src/go/fab/cmd/fab/setup_wizard.go:93`).

This closes the discovery gap end to end: a user who never runs `fab config upgrade --system`
by hand still gets a current scaffold the next time they touch `fab setup`.

### 9. `--all` checks both layers in one invocation

CI wants one command that answers "is this machine's fab config clean?" across both layers.
`fab config upgrade --check --all` computes the project and system reconciliations and reports
both.

```
fab config upgrade --check           # project only (UNCHANGED — existing CI keeps working)
fab config upgrade --check --system  # system only
fab config upgrade --check --all     # both layers, one invocation
```

- **Spelling rationale.** Bare `--check` deliberately keeps its current project-only meaning
  (assumption 4); repurposing it would silently change the verdict of every existing CI
  invocation. `--all` is the additive, non-breaking spelling.
- **Exit code**: non-zero when **either** layer has drifted; zero only when both are clean.
- **Output**: report each layer on its own labelled line so a CI log names which one drifted,
  rather than collapsing to a single verdict.
- **`--all` without `--check`**: MUST be accepted and upgrade both layers, for symmetry —
  a check mode with no applying counterpart is a trap.
- **Outside a fab repo**: `--all` includes the project layer, so it requires a fab repo and
  fails with the existing `resolve.FabRoot()` error. Only `--system` is repo-free.
- **Flag conflict**: `--system --all` and `--project --all` are contradictory; reject with a
  usage error rather than silently picking one.

## Impact

**Code:**
- `src/go/fab/cmd/fab/config.go` — `configUpgradeCmd` gains `--system`/`--project` flags and
  the no-repo-required path (~lines 60–115); `runConfigInitSystem`/`renderSystemScaffold`
  (~1120–1188) get factored so upgrade and init share one scaffold renderer.
- `src/go/fab/internal/configupgrade/configupgrade.go` — `Upgrade`/`Check`/`computeUpgrade`
  parameterized by field filter + header + fence-comment text; `render`/`renderFence` reused.
- `src/go/fab/internal/configupgrade/mutation.go` — `SystemScaffoldHeader` reworded;
  `SetSystem`/`UnsetSystem` routed through the fence-aware `renderMutation`.
- `src/go/fab/internal/configref/configref.go` — likely unchanged; the scope filter already
  exists as a predicate in `renderSystemScaffold` and should move somewhere shared.

- `src/go/fab/cmd/fab/setup_wizard.go` — `runSetupWizard` (line 93) gains the silent,
  non-fatal `upgrade --system` warm-up (item 8).

**Tests:** `config_upgrade_test.go`, `config_show_init_test.go`, `noproject_config_test.go`,
`setup_test.go` (wizard warm-up: silent-when-clean, advisory-when-changed, non-fatal-on-error)
(the no-repo path is directly relevant). Needed: adoption of an unfenced legacy file,
idempotence (two runs byte-identical), `--check` drift exit codes, scope filtering (no
`stage_hooks` in the system fence), parking, live-key preservation with attached comments, and
running outside a fab repo.

**Docs:** `src/kit/skills/_cli-fab.md`, `docs/specs/config.md`.

**Blast radius:** every existing `~/.fab-kit/config.yaml` on every machine is rewritten on
first `--system` run. Mitigated by: the reconciliation is non-destructive by construction
(live keys verbatim, removed keys parked), `--check` previews it, and the existing
`validateYAML` guard refuses to write unparseable output.
