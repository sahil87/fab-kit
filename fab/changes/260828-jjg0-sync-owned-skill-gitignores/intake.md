# Intake: Sync-Owned Skill Gitignores

**Change**: 260828-jjg0-sync-owned-skill-gitignores
**Created**: 2026-08-29

## Origin

Conversational — raised during a `/fab-discuss` session, then drafted via `/fab-draft`.

> The blanket git-ignore added by fab-kit in the .agent/skills and the .claude/skills folder is preventing other skills from being added to the skills folder. I am thinking maybe we should namespace all of the skills generated by fabKit … and then git ignore all of these four or five categories. Is there any other way to solve this?

Key decisions reached in the discussion:

- **Namespacing by prefix was rejected.** The prefixes fab would need (`fab-`, `_`, `docs-`, `code-`, `git-`, `internal-`) include four generic ones that would collide with user-authored skills — a user `git-*` or `docs-*` skill would be both ignored *and* deleted by sync. A naming convention baked into an ignore rule also drifts the moment a fifth prefix appears.
- **A generated manifest replaces the convention.** `fab sync` knows exactly what it deployed; it writes that list as a per-target `.gitignore`, and the same list scopes stale pruning. Exact ownership, no naming rule.
- **The gitignore is only half the blocker.** `cleanStaleSkills` (`src/go/fab-kit/internal/skills.go:237`) deletes *every* entry in a target dir that is not in fab's current kit list — so a user-added skill is destroyed on the next `fab sync` regardless of git. Fixing the ignore rules without fixing pruning would be worse than today (the user would commit a skill and sync would delete it).
- **All three deploy targets stay.** The user verified in a live OpenCode session that OpenCode does **not** surface skills from `.agents/skills/` as `/commands`, so the `.opencode/commands/` flat-file target cannot be retired. `.claude/skills/` stays as the documented Claude Code target (collapsing to `.agents/skills/` alone is a possible follow-up, not this change).
- **The other agent-dir ignores were never fab's business.** `/.cursor`, `/.codex`, `/.kimi` (and historically `/.gemini`) are directories fab never writes to; ignoring them was collateral from the blanket approach and is dropped along with the rest.

## Why

**Problem.** `fab sync` line-ensures six directory-level ignores into the project root `.gitignore` via `src/kit/scaffold/fragment-.gitignore`:

```
/.agents
/.claude
/.cursor
/.opencode
/.codex
/.kimi
```

These were meant to hide fab's deployed skill copies, but they ignore the **entire** agent directories. In a project using fab-kit, nothing under `.claude/` or `.agents/` can be committed: not a team's own `.claude/skills/*`, not `.claude/agents/*`, not `.claude/settings.json`, not project-level skills for Codex/agy/kimi under `.agents/skills/`. The user hit this trying to add a non-fab skill to a fab-managed project — it silently never reached git.

**Compounding problem.** Even with git fixed, `cleanStaleSkills` treats "not in fab's kit list" as "stale" and `os.RemoveAll`s it. Any user skill placed in a fab target directory is deleted on the next sync. Today this is masked because nobody can commit those skills anyway; the moment the ignore is narrowed, this becomes data loss.

**Consequence of not fixing.** fab-kit is unusable alongside any other skill-distribution mechanism (hand-written project skills, other kits, Claude Code plugins that write into `.claude/`) — a hard adoption ceiling for a tool whose constitution (Principle V, Portability) promises "no assumptions about the host project's structure".

**Why this approach.** The information needed to ignore exactly the right files already exists at the only moment it is authoritative: inside `fab sync`, right after it deploys. Writing that list as a nested `.gitignore` inside each target directory (git honours nested ignore files) gives exact coverage with zero naming convention, and reusing the same file as the record of what fab owns makes pruning safe by construction. Alternatives considered and rejected are in § Assumptions.

## What Changes

### 1. Scaffold fragment — drop the blanket agent-dir ignores

`src/kit/scaffold/fragment-.gitignore` loses the six directory lines and the `# Optional - ignore agent specific folders` header. Resulting fragment:

```
# Fab Specific
.fab-*
!fab/.fab-version
.status.yaml.lock
/.claude/settings.local.json
```

The `/.claude/settings.local.json` line is **new**: once `/.claude` is no longer ignored, this per-developer Claude Code file (which Claude Code documents as intended-to-be-gitignored, and which this repo carries) would surface in `git status` of every fab-managed project. It is a non-directory token, so it takes `lineEnsureMerge`'s strict-literal dedup path (same class as `.fab-*` / `.status.yaml.lock` — see `docs/memory/distribution/setup.md` § gitignore-aware dedup). No other line changes.

`lineEnsureMerge` is additive and never removes lines, so existing projects keep the six lines until the migration (§ 5) strips them.

### 2. `fab sync` writes a generated `.gitignore` inside each fired target

After `syncAgentSkills` succeeds for a target, sync writes `{BaseDir}/.gitignore` as a **whole-file-owned** artifact (overwrite, byte-stable, same "fab owns this file" model as the `config.yaml` reference fence). Content:

For a `directory`-format target (`.claude/skills/`, `.agents/skills/`):

```
# Generated by `fab sync` — lists the skills fab-kit deployed here. Do not edit.
# Everything else in this directory is yours and is NOT ignored.
/.gitignore
/_cli-agents/
/_cli-external/
/_cli-fab/
…
/fab-new/
…
```

For the `flat`-format target (`.opencode/commands/`):

```
# Generated by `fab sync` — lists the commands fab-kit deployed here. Do not edit.
# Everything else in this directory is yours and is NOT ignored.
/.gitignore
/_cli-agents.md
…
/fab-new.md
…
```

Rules:

- One entry per skill **actually deployed** in this run (skipped `WARN: kit/skills/X.md missing in cache` skills are not listed). Entries are anchored with a leading `/` and sorted (the kit list from `listSkills` is already sorted).
- The file lists itself so the generated ignore never shows as untracked.
- Written only for targets that **fired** (agent CLI detected / `FAB_AGENTS` named it). A skipped target's directory is left untouched, consistent with today's "existing dot folders are preserved".
- Write failures propagate like every other scaffold write (jznd fail-loud contract): a failed `.gitignore` write is a non-zero sync.
- Targets are written with `0644`; content ends with a trailing newline.

### 3. `cleanStaleSkills` prunes only what fab previously deployed

Current behaviour: any entry not in the **current kit list** is removed. New behaviour:

1. Before deploying, read the target's existing generated `.gitignore` (if present) and parse the anchored entries back into a set of **previously fab-owned names** (strip leading `/`, trailing `/` or `.md`; skip comment lines and the `/.gitignore` self-entry).
2. Prune an entry **only if** it is in the previously-owned set **and** absent from the current kit list. Entries fab never recorded are never touched.
3. If no generated `.gitignore` exists (first sync after upgrading to this version, or a fresh target), prune **nothing** and, when the directory already contains entries, print one line: `Note: {rel} has no fab manifest yet — stale fab skills (if any) were not pruned this run; they will be from the next sync.` The § 5 migration handles the one-time cleanup of pre-existing stale fab entries.
4. Both formats (`directory` and `flat`) follow the same rule; `cleanLegacyAgents` (`.claude/agents/*.md` matching kit skill names) is unchanged — it already prunes by kit-name match only.

The generated `.gitignore` is therefore the manifest — no separate `.fab-manifest` file. Ordering inside `deploySkills` per target becomes: read previous manifest → deploy → prune (previous − current) → write new manifest.

### 4. Repo-local cleanup (fab-kit's own checkout)

fab-kit's own root `.gitignore` carries the six lines plus a `/.gemini` line with a comment explaining it hides an untracked legacy `.gemini/skills/` tree. In this change: remove all seven lines and the comment block, delete the untracked `.gemini/` tree from the developer checkout if present (it is untracked, not a tracked deletion), and run `fab sync` so the three nested ignores exist. `.claude/settings.local.json` becomes ignored via the fragment line (§ 1).

### 5. Migration `2.22.0-to-2.23.0`

A markdown migration in `src/kit/migrations/`, applied by `/fab-setup migrations`, sentinel-guarded and idempotent:

**Pre-check**: skip entirely if not a git repo or no root `.gitignore`.

**Changes**:

1. **Strip the historical blanket lines** from the root `.gitignore`. The removal set is the exact set of tokens the fragment ever shipped — `/.agents`, `/.claude`, `/.cursor`, `/.opencode`, `/.codex`, `/.kimi`, `/.gemini` — matched under the same directory-token equivalence the dedup uses (leading slash optional, trailing `/` or `/*` tolerated), plus the `# Optional - ignore agent specific folders` header comment when it is the immediately preceding line. Lines the fragment never shipped are untouched. Any `!` negation lines are untouched. Print each removed line.
2. **Run `fab sync`** so the three generated `.gitignore` manifests exist in this checkout.
3. **One-time stale sweep**: for each fired target, compare its entries against the current kit list and list any entry that is a *former fab skill name* — detected as `directory` entries whose `SKILL.md` (or flat `.md`) is byte-identical to a kit skill of a different name, or whose name appears in the removed-skill history noted in the migration body. Present them to the user and remove only on confirmation (this is the only non-mechanical step; it exists because § 3 rule 3 deliberately refuses to guess on the first run).
4. **Verify**: `git status --porcelain .claude .agents .opencode` shows no fab-deployed skill paths as untracked. If it does, the migration reports which target lacks its manifest and stops.
5. **Worktree note**: the root `.gitignore` edit is tracked and lands once, but the nested manifests are per-checkout sync output. Print: `Other worktrees of this repo will show fab skills as untracked until each runs 'fab sync'.` (wt's worktree init already runs `fab sync`, so new worktrees are covered; only pre-existing ones need a manual run.) Per the "migrations touching per-checkout state must sweep worktrees" lesson, the migration offers to run `fab sync` in each sibling listed by `git worktree list --porcelain`.

`src/kit/VERSION` bumps `2.22.0 → 2.23.0` (minor: behaviour change to sync + a migration; no `.status.yaml` schema change).
