# Migration: 2.18.1 to 2.19.0

## Summary

Rename the provider command fields to the **interaction-mode** spellings:

1. `providers.<name>.session_command` → `providers.<name>.interactive_command`
2. `providers.<name>.dispatch_command` → `providers.<name>.headless_command`

Pure key renames — every value, comment, and the file's indentation style is
carried verbatim. Both scopes are swept: the project's `fab/project/config.yaml`
**and** the system config `~/.fab-kit/config.yaml` (the `providers:` table is
`scope: both`, so either file can carry provider blocks — and the
worktree/system-sweep lesson from `2.15.7-to-2.15.8` says a migration that
touches only one location strands the other).

**Why a migration and not just the read-time alias.** The 2.19.0 binary reads
*both* spellings — for each field independently, a non-empty new spelling wins
and the deprecated spelling is the fallback, silently — so nothing breaks
before this migration runs. But the registry's `renamed_from` carry-forward in
`fab config upgrade` is a **top-level-key** operation, and this rename lives
*inside* `providers.<name>:` blocks. It therefore skips it by design (the
`providers` row's `renamed_from` is informational for `--json` consumers only).
This migration is what actually rewrites the file, and this is a user-data
restructure, so per the constitution it ships as a migration rather than an
ad-hoc script.

**Out of scope — names that stay.** Only the two *field* names move. The
`dispatch.mode` **value** `headless`, the `dispatch.*` config block, and the
`fab dispatch` command family all keep their names — the rename disambiguates
the fields from them, it does not touch them.

No `.status.yaml` schema change, no binary capability pre-check (pure YAML
editing), no `fab/` data change beyond `config.yaml`, and no commit (the
project config is committed by the user in their own change; the system config
is not in git).

`src/kit/VERSION` is bumped `2.18.1` → `2.19.0` (minor — a config-schema
rename; migration name FROM=released, TO=next, per the `2.16.19-to-2.17.0`
precedent).

## Pre-check

1. **Nothing to do.** If neither `fab/project/config.yaml` nor
   `~/.fab-kit/config.yaml` exists, skip this migration entirely. Print:
   `Skipped: no config.yaml in either scope.`
2. **Sentinel (idempotency).** Skip when **neither** file carries a target key —
   no `session_command:` or `dispatch_command:` nested under a
   `providers.<name>:` entry in either file. Print:
   `Skipped: provider config already on the interaction-mode spellings.`
   (Re-running is a complete no-op.)
3. **Live keys only.** A target key must be a **live** YAML key — commented
   lines (`#   session_command: …`) are reference scaffold, never rewritten.
   The managed fence between the `# >>> fab reference` / `# <<< end fab
   reference` anchors is entirely commented and is regenerated by
   `fab config upgrade`; leave it untouched.

## Changes

Apply to **each** of `fab/project/config.yaml` and `~/.fab-kit/config.yaml`
that exists and carries a target key. Preserve every other key, value, comment,
and the file's indentation style verbatim. Use an **atomic write** (temp file
in the same directory, then `rename`).

### 1. `session_command:` → `interactive_command:`

For every `providers.<name>:` entry, rename a live `session_command:` key
directly beneath it to `interactive_command:`. Keep its indentation, its
value, and any comment above or beside it, byte-for-byte.

```yaml
# before
providers:
    codex:
        session_command: codex -m {model}
        dispatch_command: codex exec -m {model}

# after
providers:
    codex:
        interactive_command: codex -m {model}
        headless_command: codex exec -m {model}
```

- If the entry **already** has an `interactive_command:` key as well as
  `session_command:` (a hand-half-migrated file), drop the deprecated duplicate
  and print
  `Warning: <path> providers.<name> carried both interactive_command and session_command — kept interactive_command, dropped the deprecated session_command.`
  (The binary prefers the new spelling, so resolution is unchanged.)

### 2. `dispatch_command:` → `headless_command:`

Same rename, same rules, for `dispatch_command:` → `headless_command:`. The
two renames are independent **per field**: a provider carrying
`interactive_command` (new) alongside `dispatch_command` (old) has exactly one
key rewritten.

- If the entry already has `headless_command:` as well, drop the deprecated
  duplicate and print
  `Warning: <path> providers.<name> carried both headless_command and dispatch_command — kept headless_command, dropped the deprecated dispatch_command.`

### 3. Report

Print one line per rewritten file:
`Rewrote <path> to the interaction-mode provider command spellings.`

Files that exist but carry no target key are skipped silently (this is what
makes the per-file step idempotent and re-run-safe).

## Verification

1. Neither file carries a live target key under any provider:
   `yq '.providers | to_entries | map(select(.value.session_command or .value.dispatch_command)) | length'`
   prints `0` for `fab/project/config.yaml` (same for `~/.fab-kit/config.yaml`
   when present).
2. Values survived: every renamed key's value is byte-identical to what the old
   key carried, and no other key moved.
3. YAML still parses: `yq '.' fab/project/config.yaml` succeeds (exit 0).
4. Resolution across the rewrite is unchanged: 2.19.0 reads both spellings with
   new-spelling-wins, so the rewrite is a no-op to the resolver.
   `fab resolve-agent <stage>` prints the same `model=`/`effort=`/`provider=`/
   `dispatch=` lines as before the rewrite — spot-check `apply` (a Tier-2 role)
   and, when a renamed `interactive_command` is in play, `fab operator`'s
   launcher path.
5. `fab config set providers.<name>.interactive_command …` /
   `.headless_command …` are accepted, and the old spellings refuse as
   unknown-key with the `fab config explain` pointer (the write surface takes
   the new names only — this migration is the fix for old keys on disk).
6. Re-running this migration is a complete no-op: the Pre-check sentinel trips
   (`Skipped: provider config already on the interaction-mode spellings.`) and
   nothing is changed.
