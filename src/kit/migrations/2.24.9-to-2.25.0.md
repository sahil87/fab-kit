# Migration: 2.24.9 to 2.25.0

## Summary

The operator state file (`$XDG_STATE_HOME/fab/operator/<server-slug>.yaml`,
path unchanged) moves from the four legacy owned sections (`monitored`,
`watches`, `autopilot`, `notes`) to one `tracked:` list of generic items, and
the `fab operator` verb set is replaced accordingly: `enroll` / `update` /
`remove`, `watch *`, `autopilot *`, and `note *` are gone;
`track add|update|observe|rm|list|clock` replace them.

**This migration performs no file edits.** The state file is binary-owned, and
the operator may run with no `fab/` project at all — so the conversion is
applied by the binary itself: the first read-modify-write by any
`fab operator` verb (including `tick-start` and `state`) detects a
legacy-shaped file (any of the legacy sections present, `tracked` absent) and
converts it in the same atomic write:

- `monitored.<id>` → `fab-change` items (scope from the entry's fields;
  `checked_at` carries over from `last_transition`)
- `watches.<name>` → `linear`/`slack` items with `probe.mode: agent`,
  `probe.instruction` composed from `source` + `query`,
  `scope.{repo, stop_stage, query}`, `seen` = `known ∪ completed`,
  `then` = the watch's `instructions`, `check_every: 5m`
- `autopilot.queue` entries not yet in `completed` → pane-less `fab-change`
  items chained by `depends_on` (nearest same-repo predecessor; cross-repo →
  immediate predecessor), with `scope.merge_mode` = `autopilot.mode`
- open `notes` → `kind: note` items with `id: n<N>`; resolved notes are
  dropped
- the legacy keys (`monitored`, `watches`, `autopilot`, `notes`, `notes_seq`)
  are deleted in the same write; `branch_map`, `tick_count`, and
  `last_tick_at` are untouched

**Refusal while a queue is running.** When `autopilot.state == running`, every
`fab operator` verb refuses the conversion: it exits non-zero, writes nothing
(the file stays byte-identical), and prints:

```
operator state file has a running autopilot queue — finish or stop it (fab operator autopilot stop on fab ≤2.24) before upgrading
```

User action: on the old (≤2.24) binary, let the queue finish or stop it with
`fab operator autopilot stop`, **then** upgrade. An exhausted queue converts
normally — completed entries are dropped and the remainder become the chained
items above.

## Pre-check

1. Run `fab operator state`. Exit 0 means the state file is already in the
   tracked-items shape (fresh file, or conversion already applied) — nothing
   further to do; this migration is a no-op.
2. Exit non-zero with the running-queue message above means the file is
   legacy-shaped **and** its autopilot queue is still running: stop here. On
   the ≤2.24 binary, finish or stop the queue (`fab operator autopilot
   stop`), then re-run the pre-check.

## Changes

None. This migration intentionally performs no file edits — the binary owns
the state file and converts it on first touch (see Summary). Do not hand-edit
`$XDG_STATE_HOME/fab/operator/<server-slug>.yaml`.

## Verification

1. `fab operator state` exits 0 and prints the tracked items; open notes
   appear under the `OPEN NOTES` header as `kind: note` items.
2. The state file carries a `tracked:` list and none of the legacy keys
   `monitored` / `watches` / `autopilot` / `notes` / `notes_seq`;
   `branch_map`, `tick_count`, and `last_tick_at` are preserved.
3. The conversion is idempotent: a second `fab operator state` run changes
   nothing.
4. The running-queue refusal holds: with `autopilot.state: running` in a
   legacy file, any `fab operator` verb exits non-zero with the exact message
   quoted in the Summary and leaves the file byte-identical. The remedy is the
   user action above — finish or stop the queue with `fab operator autopilot
   stop` on fab ≤2.24 before upgrading.
