# Migration: 2.25.1 to 2.26.0

## Summary

The operator's tracked-item kind `fab-change` is renamed to `pane`: the
operator's core kind is now **any agent session in a tmux pane**, joined on
`scope.pane` plus a `scope.pane_pid` shell-pid fingerprint, with the fab
change carried as an observed field `scope.change` rather than as the item's
identity.

- `fab-change` is **removed outright** at `fab operator track add` — there is
  no alias and no deprecation message. `--kind fab-change` (and
  `track list --kind fab-change`) now exits non-zero through the existing
  unknown-kind path: `unknown --kind "fab-change" (valid: pane, github-pr,
  linear, slack, shell, task, note)`.
- `track add` gains a `--change <id>` sugar flag (writes `scope.change`;
  non-empty, existence not validated), and the `pane` kind's scope pins two
  new keys — `pane_pid` (the pane's shell pid, recorded whenever `scope.pane`
  is set, null on lookup failure) and `change` (the observed change id, null
  until a change appears) — both additive inside the owned `scope` mapping.

**This migration performs no file edits.** The state file
(`$XDG_STATE_HOME/fab/operator/<server-slug>.yaml`, path unchanged) is
binary-owned, and the operator may run with no `fab/` project at all — so the
conversion is applied by the binary itself: the first read-modify-write by
any `fab operator` verb (including `tick-start` and the read verbs `state`
and `track list`, which convert-and-save then read) detects a
`tracked`-present file holding an item with `kind: fab-change` and rewrites
it in the same atomic write:

- `kind: fab-change` → `kind: pane`
- `scope.change` is seeded from the item's id (a `fab-change` item's id was
  the change id by construction — without it, converted items would never
  complete)
- `scope.pane_pid` is seeded `null` (no live fingerprint ⇒ pane-id-only join,
  exactly the pre-upgrade behavior)

The conversion is idempotent: a file with no `kind: fab-change` items is
untouched.

## Pre-check

1. Run `fab operator track list`. Exit 0 means the state file is readable and
   already converted (or never held a `fab-change` item) — nothing further to
   do; this migration is a no-op.

## Changes

None. This migration intentionally performs no file edits — the binary owns
the state file and converts it on first touch (see Summary). Do not hand-edit
`$XDG_STATE_HOME/fab/operator/<server-slug>.yaml`.

## Verification

1. `fab operator state` exits 0 and shows every former `fab-change` item as
   `kind: pane` with `scope.change` set to the item's id and
   `scope.pane_pid: null`; no `kind: fab-change` remains anywhere in the
   file.
2. The conversion is idempotent: a second `fab operator state` run changes
   nothing.
