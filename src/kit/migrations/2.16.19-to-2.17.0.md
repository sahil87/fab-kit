# Migration: 2.16.19 to 2.17.0

## Summary

Rewrite the agent config to the **roles / profiles / depth-knobs** schema:

1. `agent.tiers:` → `agent.profiles:` (a key rename; values verbatim).
2. `providers.<name>.model` / `.effort` → `providers.<name>.profiles.default.{model,effort}`
   (the flat per-provider fill folds into the provider's `default`-role fill).

Both scopes are swept: the project's `fab/project/config.yaml` **and** the system
config `~/.fab-kit/config.yaml` (both keys are `scope: both`, so either file can
carry them — and the worktree/system-sweep lesson from `2.15.7-to-2.15.8` says a
migration that touches only one location strands the other).

**Why a migration and not just a read-time alias.** The binary reads *both* old
spellings — `agent.tiers` per role, and the flat fill as an alias for
`profiles.default` — so nothing breaks before this migration runs. But the registry's
`renamed_from` carry-forward in `fab config upgrade` is a **top-level-key** operation
(it rewrites a column-0 `key:` token and preserves the block below it verbatim), and
`agent.tiers` → `agent.profiles` is a rename *inside* the `agent:` block. It therefore
skips it by design. This migration is what actually rewrites the file, and this is a
user-data restructure, so per the constitution it ships as a migration rather than an
ad-hoc script.

**One semantic the rewrite does NOT preserve** (and cannot): the old `agent.tiers`
re-based every unset field from its `default` tier, so `agent.tiers.default.model: X`
set the model for every tier that did not name its own. `agent.profiles` has **no
cross-role inheritance** — `agent.profiles.default` is the `default` *role's* own
override. The Changes step below surfaces a warning when it detects that shape, with
the two replacements (`agent.session`/`agent.workers` for a provider intent,
`providers.<name>.profiles.default` for a model/effort intent). The values are still
carried verbatim — the migration never guesses which intent was meant.

**And one value whose REACH the upgrade changes.** 2.17.0 reads a flat
`providers.<name>.model`/`.effort` as an alias for `providers.<name>.profiles.default`,
so step 2's rewrite is semantically a no-op on disk — it spells out what the binary
already reads. What moves is the set of roles the value reaches, and it moved when the
**binary** was upgraded: 2.17.0 ships built-in per-role fills for all three providers,
so a flat fill now reaches the `default` role plus every role/field its provider ships
no `profiles.<role>` fill for — and nothing else. For **claude** (an exhaustive
six-role map) that is a gain of exactly one role: the flat fill was inert under
2.16.19, where every built-in tier set its own model and effort, and it now fills the
`default` role. For the **sparse codex/gemini** maps it is a loss: those providers
shipped *no* fills under 2.16.19, so a flat fill was the only fill and reached every
role — under 2.17.0 it stops reaching the roles/fields they now fill themselves.
Changes step 2 warns on exactly this shape; Verification step 5 states what to expect.

No `.status.yaml` schema change, no binary capability pre-check (pure YAML editing),
no `fab/` data change beyond `config.yaml`, and no commit (the project config is
committed by the user in their own change; the system config is not in git).

`src/kit/VERSION` is bumped `2.16.19` → `2.17.0` (minor — a config-schema change plus
new `agent.session`/`agent.workers` keys; migration name FROM=released, TO=next).

## Pre-check

1. **Nothing to do.** If neither `fab/project/config.yaml` nor `~/.fab-kit/config.yaml`
   exists, skip this migration entirely. Print:
   `Skipped: no config.yaml in either scope.`
2. **Sentinel (idempotency).** Skip when **neither** file carries a target key — no
   `tiers:` nested under a top-level `agent:` block, and no `model:`/`effort:` nested
   **directly** under a `providers.<name>:` entry (a `model:`/`effort:` under
   `providers.<name>.profiles.<role>:` is the NEW shape and is not a target). Print:
   `Skipped: agent config already on the profiles schema.`
   (Re-running is a complete no-op.)
3. **Live keys only.** A target key must be a **live** YAML key — commented lines
   (`# tiers:`, `#   model: …`) are reference scaffold, never rewritten. The managed
   fence between the `# >>> fab reference` / `# <<< end fab reference` anchors is
   entirely commented and is regenerated by `fab config upgrade`; leave it untouched.

## Changes

Apply to **each** of `fab/project/config.yaml` and `~/.fab-kit/config.yaml` that
exists and carries a target key. Preserve every other key, value, comment, and the
file's indentation style verbatim. Use an **atomic write** (temp file in the same
directory, then `rename`).

### 1. `agent.tiers:` → `agent.profiles:`

Rename the `tiers:` key nested under the top-level `agent:` block to `profiles:`.
Keep its indentation, its entire value block (every role entry and every field),
and any comments above or beside it, byte-for-byte.

```yaml
# before
agent:
    tiers:
        doing:
            effort: high

# after
agent:
    profiles:
        doing:
            effort: high
```

- If the file **already** has an `agent.profiles:` key as well as `agent.tiers:`
  (a hand-half-migrated file), make **no change** to that file's `agent:` block —
  merging the two is ambiguous, and renaming `tiers:` to anything else would drop
  the per-role legacy fallback the binary still reads. Leave both keys exactly as
  they are and print
  `Warning: <path> carries BOTH agent.profiles and agent.tiers — left as-is; agent.profiles wins at read time. Merge them by hand.`
  (The binary reads `agent.profiles` first and falls back to `agent.tiers` per role,
  so the file keeps working either way.)
- **Default-tier-inheritance warning.** If the renamed block carries a `default:`
  role entry with a `model:` or `effort:` **and** at least one other role entry that
  omits that same field, print:
  `Warning: <path> relied on agent.tiers.default re-basing other tiers; agent.profiles has no cross-role inheritance. Set agent.session/agent.workers for a provider choice, or providers.<name>.profiles.default for a model/effort choice.`
  Carry the values verbatim regardless — the migration does not guess the intent.

### 2. Flat provider fill → `providers.<name>.profiles.default`

For each live `providers.<name>:` entry carrying a `model:` and/or `effort:` key
**directly** beneath it, move those keys under a `profiles.default:` child and delete
them from their old position:

```yaml
# before
providers:
    codex:
        dispatch_command: codex exec -m {model}
        model: gpt-5.3-codex
        effort: high

# after
providers:
    codex:
        dispatch_command: codex exec -m {model}
        profiles:
            default:
                model: gpt-5.3-codex
                effort: high
```

- Preserve any comment attached to a moved line by moving it with the line.
- If the provider **already** has a `profiles.default:` entry, do not overwrite it:
  fill only the fields it is missing, drop the flat keys, and print
  `Warning: <path> providers.<name> carried both a flat fill and profiles.default — kept profiles.default, dropped the duplicate flat <field>.`
- Leave `session_command` / `dispatch_command` and every other provider key in place.
- **Reach warning — a flat fill on a provider that ships built-in per-role fills.**
  All three built-ins carry `providers.<name>.profiles.<role>` in the binary's embedded
  defaults, and 2.17.0 reads a flat fill as an alias for
  `providers.<name>.profiles.default` — so this move does not change resolution, but the
  **2.17.0 upgrade** already changed which roles the value reaches. Under 2.17.0 a flat
  fill reaches the `default` role (the user's value outranks the built-in
  `profiles.default`) **plus every role/field the provider ships no `profiles.<role>`
  fill for**, and is outranked everywhere it does — the merge is per FIELD, so codex's
  `doing: { effort: xhigh }` row (no `model`) takes the user's model but keeps the
  built-in effort. Two directions:
  - **claude** (exhaustive six-role map): a gain of one role. The flat fill was inert
    under 2.16.19 — every built-in tier set its own model and effort — and now fills the
    `default` role.
  - **codex / gemini** (sparse maps): a LOSS. Under 2.16.19 these providers shipped no
    fills at all, so a flat `providers.codex.model` was the only fill and applied to
    EVERY role. Under 2.17.0 it stops applying wherever fab-kit now ships a role fill —
    for codex, `fast`'s model and `doing`/`review`/`fast`'s effort; for gemini, `fast`'s
    model.

  Carry the value verbatim, and print:
  `Warning: <path> providers.<name> carries a flat fill. 2.17.0 reads it as providers.<name>.profiles.default: it now fills the default role plus every role/field <name> ships no built-in fill for, and is outranked everywhere <name> does — for codex/gemini, which shipped no fills before 2.17.0, that means it no longer applies to every role. Check with 'fab resolve-agent <stage>', and move it under the role you meant if the reach is wrong.`
  A provider fab-kit ships nothing for (a project-defined `providers:` entry) has no
  built-in fills to outrank, so its reach is unchanged and no warning is printed.

### 3. Report

Print one line per rewritten file:
`Rewrote <path> to the agent.profiles schema.`

Files that exist but carry no target key are skipped silently (this is what makes the
per-file step idempotent and re-run-safe).

## Verification

1. Neither file carries a live `tiers:` key under `agent:`:
   `yq '.agent.tiers' fab/project/config.yaml` prints `null` (same for
   `~/.fab-kit/config.yaml` when present).
2. Neither file carries a live `model:`/`effort:` directly under a `providers.<name>:`
   entry: `yq '.providers | to_entries | map(select(.value.model or .value.effort)) | length'`
   prints `0`.
3. Values survived: every role that had an entry under `agent.tiers` has the same
   entry under `agent.profiles`, and every flat provider fill appears under that
   provider's `profiles.default`.
4. YAML still parses: `yq '.' fab/project/config.yaml` succeeds (exit 0).
5. Resolution across the rewrite is unchanged **when both layers are rewritten together**
   (the sweep above, and the only-layer case of a project file with no
   `~/.fab-kit/config.yaml`): 2.17.0 reads both old spellings, so the rewrite is a no-op
   to the resolver. `fab resolve-agent <stage>` prints the same
   `model=`/`effort=`/`provider=` lines as it did before the rewrite — spot-check
   `apply` and `intake` (different roles, so they exercise both the per-role and the
   `profiles.default` rungs).

   **Mixed-layer exception** (third thing to check, alongside the two warnings above).
   The flat-fill alias resolves AFTER the scope cascade, so where one scope carries a
   provider's fill in the NEW spelling and the other in the FLAT one, the SPELLING
   decides, not the scope: a system-layer `providers.<name>.profiles.default` beats a
   project-layer flat `providers.<name>.model` per field (the flat value fills only the
   fields `profiles.default` leaves empty), inverting the documented project > system
   precedence. That inversion is pre-existing — it is the provider-side twin of the
   `agent.profiles`/`agent.tiers` limitation on `Config.GetAgentProfile` — but rewriting
   only the project layer flips the winner back to the project's value, so resolution
   DOES change in that one shape. It cannot arise from this migration's own sweep (which
   rewrites both files); it needs a system layer already hand-written on the `profiles`
   spelling. If you have one, re-check `fab resolve-agent intake` (the `default` role,
   where a flat fill lands) after the rewrite and keep whichever value you meant.

   What the two warnings flag is the **2.17.0 upgrade's** effect, which this migration
   surfaces rather than causes. Where step 2's reach warning fired, confirm the value
   still lands where you want it. On **claude** (exhaustive map) it reaches exactly one
   role: `fab resolve-agent intake` (the `default` role) prints the flat fill's
   model/effort instead of claude's built-in `default` fill, while `apply`, `review`,
   `ship`, `hydrate`, and `review-pr` stay on their own built-in fills. On the **sparse**
   codex/gemini maps the reach NARROWS — under 2.16.19 those providers shipped no fills,
   so the flat value reached every role; now it reaches only the roles/fields they omit,
   and e.g. `fab resolve-agent ship` (the `fast` role) prints the provider's own `fast`
   fill rather than the flat value. If that is not what you want, move the value under
   the role it was meant for (`providers.<name>.profiles.<role>`) or repeat it per role.
6. Re-running this migration is a complete no-op: the Pre-check sentinel trips
   (`Skipped: agent config already on the profiles schema.`) and nothing is changed.
