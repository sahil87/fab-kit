# Migration: 2.17.3 to 2.18.0

## Summary

Replace the live `dispatch.watchable` boolean with the `dispatch.mode` preference:

- `watchable: true` becomes `mode: pane`.
- `watchable: false` is deleted; an absent mode uses the new `native` default.

Sweep both scopes: the project config at `fab/project/config.yaml` and the system
config at `~/.fab-kit/config.yaml`. `dispatch` has `scope: both`, so either file can
carry the old key. This is a user-data schema rewrite and therefore ships as a
versioned migration rather than a read-time alias. The 2.18.0 binary ignores a stale
`watchable` key and resolves an absent mode as `native`.

No `.status.yaml` schema changes, no other config keys change, and no commit is made.
`src/kit/VERSION` is bumped from `2.17.3` to `2.18.0` (minor: config-schema change).

## Pre-check

1. **Nothing to do.** If neither `fab/project/config.yaml` nor
   `~/.fab-kit/config.yaml` exists, skip this migration entirely. Print:
   `Skipped: no config.yaml in either scope.`
2. **Sentinel (idempotency).** Skip when neither file carries a live `watchable:` key
   nested directly under a top-level `dispatch:` block. Print:
   `Skipped: dispatch config already uses the mode schema.`
3. **Live keys only.** A target must be a live YAML key. Never rewrite a commented
   `# watchable:` line. Never edit any content between the
   `# >>> fab reference` and `# <<< end fab reference` managed-fence anchors; `fab
   config upgrade` regenerates that fence from the new registry.

## Changes

Apply the following operation independently to each existing target file that carries
a live `dispatch.watchable` key. Preserve every unrelated key, value, blank line,
comment, indentation choice, and managed-fence byte verbatim. Write each changed file
atomically: create a temporary file in the same directory, preserve the original file
mode, fsync/close it, then rename it over the original only after the complete result
parses as YAML.

### 1. Rewrite `watchable: true`

Replace a live `watchable: true` nested directly under the top-level `dispatch:` block
with `mode: pane`, preserving indentation and any inline comment.

```yaml
# before
dispatch:
  watchable: true
  reap_done: true

# after
dispatch:
  mode: pane
  reap_done: true
```

If the same `dispatch:` block already carries a live `mode:` key, keep that explicit
mode, delete `watchable`, and print:
`Warning: <path> carried both dispatch.mode and dispatch.watchable — kept mode and removed watchable.`
Do not guess or overwrite the user's explicit mode.

### 2. Delete `watchable: false`

Delete a live `watchable: false` nested directly under the top-level `dispatch:`
block. Do not add `mode: native`: absence deliberately inherits the canonical
`native` default. Keep the `dispatch:` mapping when it contains other keys. If
`watchable` was its only live child, remove the now-empty `dispatch:` mapping while
preserving adjacent comments.

If an existing `mode:` key accompanies `watchable: false`, keep the mode and delete
only `watchable` without warning; the explicit mode is already authoritative.

### 3. Report

Print one line per rewritten file:
`Rewrote <path> from dispatch.watchable to dispatch.mode.`

Files that exist but carry no live target key are skipped silently. Do not touch
nested mappings also named `dispatch`, quoted/comment text containing `watchable`, or
any unknown boolean spelling; malformed or non-boolean live values must abort that
file's rewrite with an error and leave the original file intact.

## Verification

1. Neither scope contains a live legacy key:
   `yq '.dispatch.watchable' fab/project/config.yaml` prints `null`, and the same
   command prints `null` for `~/.fab-kit/config.yaml` when it exists.
2. A prior `true` value became pane preference:
   `yq '.dispatch.mode' <path>` prints `pane`. A prior `false` value with no existing
   mode now prints `null`, which the binary resolves to `native`.
3. Adjacent dispatch settings such as `column_width` and `reap_done`, unrelated YAML,
   comments, and managed-fence bytes are unchanged.
4. Both rewritten files still parse: `yq '.' <path>` succeeds for each one present.
5. `fab config reference` advertises `dispatch.mode` with default `native`, and `fab
   config upgrade` refreshes only the managed fence with that schema.
6. Re-running this migration is a complete no-op: the sentinel prints
   `Skipped: dispatch config already uses the mode schema.` and neither file changes.
