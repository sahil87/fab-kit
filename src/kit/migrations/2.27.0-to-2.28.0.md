# Migration: 2.27.0 to 2.28.0

> The exact version range is a placeholder — the slot this change ships in is
> release-owned and set at release time.

## Summary

`.status.yaml` gains an optional top-level `base_branch` field — a plain
branch name (e.g. `main` or a stacked parent branch) recording which branch
the change's diff, Impact numbers, review scope, and PR target are measured
against. Two new verbs manage it:

- `fab status set-base-branch <change> <branch>` — writes the field under the
  status flock. A non-empty branch is required; remote existence is not
  validated (an operator may record a dependency branch that has not been
  pushed yet).
- `fab status get-base-branch <change> [--json]` — prints the recorded value
  (empty line when absent); `--json` emits `{"base_branch":"…"}` (absent →
  `{"base_branch":""}`), joining the read-only `--json` query surface.

The field is written by the branch-creation skills (`/git-branch` Step 4,
`/fab-new` Step 11) when the change's branch is created, and by the operator's
`stacked-prs` mode with the dependency's branch. Consumers (`fab pr-meta`,
the `true_impact` stage-finish write, the review dispatch, `/fab-adopt`,
`/git-pr --base`) resolve the base as: the recorded `base_branch` when set and
`origin/<base_branch>` resolves, else `origin/HEAD`'s target, else
`origin/main`, else `origin/master` — fail-open throughout, so a change with
no `base_branch` behaves exactly as before, and a recorded base whose branch
was deleted (e.g. after a stacked dependency merged) falls back to the
default-branch chain instead of erroring.

**This migration performs no file edits.** The field is optional and absent on
every existing change; every consumer falls back to the resolved default
branch, so there is nothing to rewrite.

## Pre-check

1. Run `fab status get-base-branch <any-change>`. Exit 0 with an empty line
   means the field is absent (expected on every pre-upgrade change) — nothing
   further to do; this migration is a no-op.

## Changes

None. This migration intentionally performs no file edits — the schema
addition is optional and fail-open (see Summary). Do not hand-edit
`.status.yaml`; use `fab status set-base-branch`.

## Verification

1. `fab status validate-status-file <change>` exits 0 on an untouched change
   (the new key is optional).
2. Round-trip: `fab status set-base-branch <change> main` then
   `fab status get-base-branch <change>` prints `main`
   (`--json` prints `{"base_branch":"main"}`).
