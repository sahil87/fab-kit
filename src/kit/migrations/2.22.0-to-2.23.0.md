# Migration: 2.22.0 to 2.23.0

## Summary

Strip the historical blanket agent-directory ignores from the root `.gitignore`
and regenerate the per-target `.gitignore` manifests, so fab-managed projects
can commit their own content under `.claude/`, `.agents/`, and `.opencode/`.

Up to 2.22.0 the scaffold fragment (`src/kit/scaffold/fragment-.gitignore`)
line-ensured six directory-level ignores into every fab project's root
`.gitignore`:

```
/.agents
/.claude
/.cursor
/.opencode
/.codex
/.kimi
```

These were meant to hide fab's deployed skill copies, but they ignore the
**entire** directories — nothing under `.claude/` or `.agents/` can be
committed: not a team's own `.claude/skills/*`, not `.claude/agents/*`, not
`.claude/settings.json`, not project-level skills under `.agents/skills/`.
fab never writes to `.cursor`, `.codex`, or `.kimi` at all; ignoring them was
collateral.

As of 2.23.0 the mechanism is inverted: the fragment ships **no** directory
tokens (its only agent-related line is the non-directory
`/.claude/settings.local.json`, a per-developer Claude Code file), and
`fab sync` writes a **generated `.gitignore` inside each fired deploy target**
(`.claude/skills/`, `.agents/skills/`, `.opencode/commands/`) listing exactly
the skills it deployed there — one anchored entry per skill (`/{name}/` for
directory targets, `/{name}.md` for the flat one), plus the self-entry
`/.gitignore`. That generated file doubles as fab's ownership manifest: stale
pruning removes an entry only when the previous manifest recorded it AND the
current kit no longer ships it. Anything fab never recorded — user skills,
user commands — is never pruned and never ignored.

Because `lineEnsureMerge` is additive and never removes lines, existing
projects keep the six historical directory lines until this migration strips
them. This is a **user-data restructure** (it edits the user's root
`.gitignore`), so it ships as a migration per the constitution. It is
sentinel-guarded and idempotent: a re-run after success is a complete no-op
(no historical tokens remain, and the manifests exist).

`src/kit/VERSION` is bumped `2.22.0` → `2.23.0` (minor — a behaviour change to
`fab sync` plus a migration; no `.status.yaml` schema change).

## Pre-check

1. **Not a git repository, or no root `.gitignore`** — skip this migration
   entirely. Print:
   `Skipped: not a git repository or no root .gitignore present.`
2. **Sentinel (idempotency).** Skip when the migration is already complete:
   the root `.gitignore` contains **no** line whose directory token normalizes
   to one of the seven historical tokens (see step 1 below) **and** every
   currently-fired deploy target already carries its generated `.gitignore`
   manifest. Print:
   `Skipped: historical agent-dir ignores already stripped and manifests present.`
   (Re-running is a complete no-op.)

## Changes

Apply only when the Pre-check did not trip.

### 1. Strip the historical blanket lines from the root `.gitignore`

The removal set is exactly the seven directory tokens the fragment (or this
repo's own `.gitignore`) historically shipped:

```
/.agents   /.claude   /.cursor   /.opencode   /.codex   /.kimi   /.gemini
```

Match under **directory-token equivalence**: leading slash optional, trailing
`/` or `/*` tolerated — so `/.agents`, `.agents/`, `/.opencode/*` and
`.opencode` are all the same token and all removed. Also remove the
`# Optional - ignore agent specific folders` header comment **when it is the
immediately preceding line** of a removed block.

Hard carve-outs:

- **`!` negation lines are never touched** (e.g. `!/.claude/commands/` stays).
- **No other line is touched** — a token that is not one of the seven stays,
  even if it looks similar (`/.claude-old/`, `/agents/`).
- **Print every removed line** so the user can re-add anything they had placed
  intentionally.

### 2. Run `fab sync`

Regenerate the deployed skill copies and write the three generated manifests
(`{target}/.gitignore`) for whichever targets fire in this checkout.

### 3. One-time stale sweep (confirm before deleting anything)

For each fired target, list every entry that is **absent from the target's new
manifest** — these are candidates for being stale pre-manifest fab skills (or
the user's own content). Present the list to the user and remove **only** the
entries the user confirms; delete nothing without confirmation. This is the
only non-mechanical step: the no-manifest sync run deliberately refuses to
guess ownership, so pre-existing stale fab entries would otherwise linger.

### 4. Worktree sweep

The root `.gitignore` edit is tracked and lands once, but the generated
manifests are **per-checkout sync output**. Print:

```
Other worktrees of this repo will show fab skills as untracked until each runs 'fab sync'.
```

Then offer to run `fab sync` in each sibling checkout listed by
`git worktree list --porcelain` (the main checkout is the first entry and has
just been synced by step 2 — sync the remaining ones only, on confirmation).
New worktrees are covered already (`wt init` runs `fab sync`); only
pre-existing ones need this.

## Verification

1. The root `.gitignore` contains none of the seven historical tokens under
   the directory-token equivalence, and every removed line was printed.
2. `git status --porcelain .claude .agents .opencode` shows **no** fab-deployed
   skill path as untracked. If it does, identify which fired target is missing
   its `{target}/.gitignore` manifest, report it, and stop.
3. `git check-ignore -q .claude/settings.local.json` exits **0** (the fragment's
   non-directory line covers it — merge-additive, so it arrives on the step-2
   sync if it was not already present).
4. Re-running this migration is a complete no-op: the Pre-check sentinel trips
   and prints the skip line; no `.gitignore` line changes, no sync output
   differs, and the stale sweep offers nothing.
