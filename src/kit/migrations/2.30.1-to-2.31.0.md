# Migration: 2.30.1 to 2.31.0

> The exact version range is a placeholder — the slot this change ships in is
> release-owned and set at release time.

## Summary

Rename "provider" to **CLI** across the agent configuration. The things fab
launches (claude, codex, agy, kimi, or a tool you defined) are CLI tools, not
model providers — the tools themselves use "provider" for the model vendor, so the
old word collided with theirs in every config file and conversation.

1. The top-level `providers:` table → `clis:` (every entry, leaf and comment
   carried verbatim)
2. `agent.profiles.<role>.provider:` → `agent.profiles.<role>.cli:` (and the legacy
   `agent.tiers.<role>.provider:` → `cli:` if that spelling is still present)

Pure key renames. Both scopes are swept: the project's `fab/project/config.yaml`
**and** the system config `~/.fab-kit/config.yaml` (the table and the profiles are
`scope: both`, so either file can carry them — a migration that touches only one
location strands the other).

**Why a migration and not just the read-time alias.** The 2.31.0 binary reads
*both* spellings — per field, the new spelling winning, silently — so nothing
breaks before this migration runs. The old spellings stay readable, and
`fab config set`/`unset` keeps accepting them (writing the new key and warning
`<old> is deprecated, wrote <new>`), for **one minor release** after the one that
ships this rename; they are removed in a later change. `fab config upgrade`
carries a live top-level `providers:` key to `clis:` on its own, but it cannot
touch the nested `.provider` leaf or merge two live blocks. This migration is what
rewrites the files, and as a user-data restructure it ships as a migration rather
than an ad-hoc script.

**Out of scope — names that stay.** Only fab's own table and role leaf move.
Where "provider" means a model vendor — for instance the `[providers.<vendor>]`
tables in kimi's own `~/.kimi-code/config.toml` — nothing changes. The
already-deprecated `session_command` / `dispatch_command` keys keep working under
`clis.<name>` exactly as they did under `providers.<name>`.

**Other spellings the binary still accepts for the window** (nothing to migrate in
the files, but worth renaming in your own scripts): the `--provider` flag of
`fab agent` / `fab resolve-agent` / `fab pane open` (hidden; behaves as `--cli` and
prints `--provider is deprecated, use --cli` on stderr), and the duplicate
`provider:` keys that `fab agent -o yaml` emits next to `cli:` (and next to
`source.cli:`). `fab resolve-agent`'s `provider=<name>` output line is unchanged.

No `.status.yaml` schema change, no binary capability pre-check (pure YAML
editing), no `fab/` data change beyond `config.yaml`, and no commit (the project
config is committed by the user in their own change; the system config is not in
git).

`src/kit/VERSION` is bumped `2.30.1` → `2.31.0` at release (minor — a config-schema
rename; migration name FROM=released, TO=next, per the `2.18.1-to-2.19.0`
precedent).

## Pre-check

1. **Nothing to do.** If neither `fab/project/config.yaml` nor
   `~/.fab-kit/config.yaml` exists, skip this migration entirely. Print:
   `Skipped: no config.yaml in either scope.`
2. **Sentinel (idempotency).** Skip when **neither** file carries a target key —
   no live top-level `providers:` key and no `provider:` leaf under
   `agent.profiles.<role>` / `agent.tiers.<role>` in either file. Print:
   `Skipped: agent config already on the clis / cli spellings.`
   (Re-running is a complete no-op.)
3. **Live keys only.** A target key must be a **live** YAML key — commented lines
   (`#   operator: { provider: codex }`) are reference scaffold, never rewritten.
   The managed fence between the `# >>> fab reference` / `# <<< end fab reference`
   anchors is entirely commented and is regenerated by `fab config upgrade`;
   leave it untouched.
4. **Environment.** Check whether the `FAB_PROVIDERS` environment variable is set
   in the current shell (`printenv FAB_PROVIDERS`). The migration cannot edit your
   shell profile — if it is set, report it (see Report) so the user renames it to
   `FAB_CLIS` themselves.

## Changes

Apply to **each** of `fab/project/config.yaml` and `~/.fab-kit/config.yaml` that
exists and carries a target key. Preserve every other key, value, comment, and the
file's indentation style verbatim. Use an **atomic write** (temp file in the same
directory, then `rename`).

### 1. `providers:` → `clis:`

Rename the live top-level `providers:` key to `clis:`; the whole value block
(every entry, its leaves and any comment inside it) is carried byte-for-byte.

```yaml
# before
providers:
    codex:
        headless_command: codex exec -m {model}
        profiles:
            review: { model: gpt-5.6-sol }

# after
clis:
    codex:
        headless_command: codex exec -m {model}
        profiles:
            review: { model: gpt-5.6-sol }
```

- If the file carries **both** a live `providers:` and a live `clis:` key, that is an
  ordinary half-migrated state — for instance `fab config set clis.<name>.<leaf>`
  against a file still holding `providers:` writes a `clis:` block beside it and
  removes only the same-path old leaf — so **merge** instead of renaming: move each
  entry of the `providers:` block into `clis:`, and where the same `<name>.<leaf>`
  exists under both, keep the `clis:` value (the new spelling wins per leaf, as it
  does in the binary). Then delete the `providers:` block. Print
  `Warning: <path> carried both providers and clis — merged providers into clis (clis values kept), removed providers.`
  Do not rename `providers:` over a live `clis:` key — that would leave two
  top-level keys named `clis:`.

### 2. `agent.profiles.<role>.provider:` → `.cli:`

For every role entry under `agent.profiles:` (and `agent.tiers:` when still
present), rename a live `provider:` leaf to `cli:`; keep its indentation, value and
any comment byte-for-byte. A flow-style entry (`review: { provider: codex }`) is
renamed in place the same way.

```yaml
# before
agent:
    profiles:
        review: { provider: codex, effort: high }
        doing:
            provider: kimi

# after
agent:
    profiles:
        review: { cli: codex, effort: high }
        doing:
            cli: kimi
```

- If a role entry **already** has a `cli:` key as well as `provider:`, drop the
  deprecated duplicate (the binary prefers `cli`, so resolution is unchanged) and
  print
  `Warning: <path> agent.profiles.<role> carried both cli and provider — kept cli, dropped the deprecated provider.`
  If the existing `cli:` value is empty, keep the `provider:` value under `cli:`
  instead (an empty new leaf falls through to the old one in the binary).

### 3. Report

Print one line per rewritten file:
`Rewrote <path> to the clis / cli spellings.`

Files that exist but carry no target key are skipped silently (this is what makes
the per-file step idempotent and re-run-safe).

If `FAB_PROVIDERS` is set in the environment (Pre-check step 4), also print:
`Note: the FAB_PROVIDERS environment variable is deprecated — rename it to FAB_CLIS in your shell profile. fab still reads FAB_PROVIDERS for one minor release (FAB_CLIS wins when both are set).`
Do not edit shell profiles.

## Verification

1. Neither file carries a live deprecated key: `yq 'has("providers")'` prints
   `false` for `fab/project/config.yaml` (same for `~/.fab-kit/config.yaml` when
   present), and
   `yq '[.agent.profiles // {} | to_entries[] | select(.value.provider)] | length'`
   prints `0`.
2. Values survived: every renamed key's value is byte-identical to what the old key
   carried, and no other key moved.
3. YAML still parses: `yq '.' fab/project/config.yaml` succeeds (exit 0), and there
   is exactly one live top-level `clis:` key.
4. Resolution across the rewrite is unchanged: the binary reads both spellings with
   new-spelling-wins, so the rewrite is a no-op to the resolver.
   `fab agent <stage> -o yaml` prints the same `cli:`/`model:`/`effort:`/`command:`
   values as before the rewrite — spot-check `apply` (a Tier-2 role).
5. `fab config set clis.<name>.headless_command …` and
   `fab config set agent.profiles.<role>.cli …` are accepted without a deprecation
   warning; `fab config set agent.profiles.<role>.provider …` still works but
   writes `.cli` and warns `… is deprecated, wrote …`.
6. `fab setup check` reports no `is deprecated; rename to …` warnings for either config
   file.
7. Re-running this migration is a complete no-op: the Pre-check sentinel trips
   (`Skipped: agent config already on the clis / cli spellings.`) and nothing is
   changed.
